# 학습용 제작과 실제 개발을 분리하는 운영

[학습 자료 홈](README.md) · [수업 양식](templates/LESSON.md) · [마일스톤 양식](templates/MILESTONE.md)

**현재 상태:** 새 P0 참고 제작을 진행 중이다. 실제 브랜치·출발 SHA·수업 검증 범위는 [P0 학습 시작](P0/README.md)과 [이번 작업 기록](../docs/production/P0_REFERENCE_RUN.md)에 관리한다. 참고 제작과 개발자 A·B의 실제 진행을 분리하며, 새 P0 필수 검수가 완료되기 전에는 P1로 넘어가지 않는다.

## 1. 두 번의 개발 과정

| 과정 | 작성자 | 하는 일 | 산출물 |
|---|---|---|---|
| 참고용 제작 | Codex가 A·B 역할을 구분해 수행 | 각 역할의 코드·Unreal 설정을 단계별 작성하고 중간 통합 | A 학습 자료, B 학습 자료, 검증된 통합 참고본 |
| 실제 학습 개발 | 개발자 A·B | 각자 자료를 읽고 직접 작성하며 상대 산출물과 통합 | 각자의 구현 이력과 실제 통합 프로젝트 |

A 학습용과 B 학습용은 두 개의 독립된 전체 게임이 아니다. 하나의 게임을 완성하는 두 담당 경로다. 단일 역할의 전체 완성을 기다리지 않고 공통 계약→첫 기능→작은 통합을 반복한다.

학습자가 완성된 참고 브랜치를 자기 개발 브랜치로 그대로 사용하면 이미 구현된 상태로 시작하게 된다. 실제 개발 브랜치는 해당 과정의 출발점에서 시작하고, 참고본은 비교 대상으로 유지한다.

## 2. 브랜치·폴더·기준점

아래 이름은 [정식 브랜치 명명 기준](../docs/WORKFLOW.md)에 따라 작성 도구 표시 없이 용도/내용으로 정한 예시다. 현재 생성된 브랜치·태그·worktree 목록이 아니다. 실제 이름과 SHA는 마일스톤 README에 기록한다.

| 용도 | P0 예시 | P1 예시 |
|---|---|---|
| Codex의 A 참고 구현 | `reference/p0-a` | `reference/p1-a` |
| Codex의 B 참고 구현 | `reference/p0-b` | `reference/p1-b` |
| 참고 구현 통합 | `reference/p0-integration` | `reference/p1-integration` |
| 개발자 A의 실제 구현 | `learn/p0-a` | `learn/p1-a` |
| 개발자 B의 실제 구현 | `learn/p0-b` | `learn/p1-b` |
| 실제 구현 통합 | `learn/p0-integration` | `learn/p1-integration` |

같은 PC에서 비교·제작할 때 역할별 worktree 폴더를 사용할 수 있다. 다른 PC에서는 같은 저장소를 각각 clone하고 해당 역할 브랜치에서 작업한다. Unreal 프로젝트/모듈 이름은 유지하며 파일 경로·열린 프로젝트·현재 브랜치를 확인한다.

각 기준점에는 브랜치명만 적지 않고 전체 커밋 SHA를 남긴다. 검증된 참고본에는 태그/보관본도 연결한다. 검증 후 수정이 필요하면 새 기준점을 만들고 이전 학습 기록을 보존한다.

## 3. P0에서 P1·P2로 이어가는 기준

P0의 참고/실제 개발은 동일한 최초 공통 출발 커밋을 사용할 수 있다. 현재 [P0 재기획](../docs/design/P0_REPLAN.md)에 따라 공통 기반도 A/B가 각 브랜치에서 직접 구현하고, 통합할 때 계약과 차이를 비교하여 하나로 정리한다. 새 COMMON.md에는 이 학습 범위와 제공하는 데이터 예시·검증 픽스처·상대 기능 Stub의 경계를 명시한다. 제공 파일로 공통 기반의 직접 구현 과정을 대체하지 않는다.

P1부터는 두 과정의 출발 커밋이 일반적으로 다르다.

- 참고용 P1의 출발점: 검증된 참고용 P0 통합 완료 커밋.
- 실제 개발 P1의 출발점: A·B가 직접 완성하고 검증한 실제 P0 통합 완료 커밋.

실제 개발을 참고 완성본으로 덮어써 SHA를 맞추지 않는다. 각 과정 안에서 A와 B가 같은 출발점을 공유하고, 과정 사이에는 기능·공통 API·데이터 버전·실행 결과가 호환되는지 대조한다. P2와 이후 단계에도 같은 규칙을 적용한다.

이전 실제 개발 단계가 완료되지 않았다면 다음 단계의 학습 진입을 완료 표시하지 않는다. 참고본 제작이 먼저 진행됐다는 이유로 실제 개발 진척을 올리지 않는다. DEC-049의 P2 사전 기술 검증과 P1 핵심 통과 후 독립 서비스 연결은 일정상 병행 작업이며, P1 잔여 연출/안내까지 검수한 전체 완료나 P2 학습 통과를 자동으로 뜻하지 않는다.

## 4. 수업 한 개를 제작하는 순서

1. 상위 TASK·학습 목표·시작 기준점·필요한 상대 산출물을 정한다.
2. 해당 역할의 변경을 구현하고 코드와 Unreal 설정 순서를 함께 기록한다.
3. Editor/PIE/패키지 등 필요한 검사를 실제 실행한다. 실패했다면 수정 과정과 재현 방법도 남긴다.
4. 완료 커밋·에셋 경로·설정값·정상/실패 증거를 수업에 연결한다.
5. 시작 기준점에서 설명대로 재현 가능한지 확인한 뒤 수업을 Verified로 표시한다.
6. 실제 개발자는 같은 단계의 자기 출발점에서 재현하고, 자기 커밋·실행 결과를 별도로 기록한다.

아직 없는 클래스/에셋/API는 설계 예정으로 표시한다. 검증되지 않은 예시 코드를 완성 코드라고 표기하지 않는다. Code와 에디터 조작 중 한쪽만 기록해서 단계 완료로 표시하지 않는다.

## 5. 상대 산출물을 받는 방법

참고용 A/B는 상대 참고 브랜치의 합의된 변경을 받아 통합한다. 실제 개발자 A/B는 상대가 직접 작성한 변경을 받는다. 참고용 전체 완성 코드를 실제 개발 통합에 병합해 학습 단계를 건너뛰지 않는다.

수업마다 제공 코드와 직접 작성할 코드를 구분한다. 공통 헤더·비활성 최소 구현·검증 픽스처를 제공한다면 이유·파일·버전·제거 시점을 기록한다. 상대 기능을 기다리는 경우에도 최소 선언과 슬롯 계약은 먼저 교환한다.

준비된 실습 시작본을 제공할 때는 Blueprint 부모·직렬화된 프로퍼티·에셋 참조를 보존해 빌드 가능한 상태를 만든다. 완성 코드 파일을 무작정 삭제해 시작본을 만들지 않는다. 필수 실행 자산은 해당 프로젝트의 Source/Content/Config에 두고 학습 문서 폴더에서 로드하지 않는다.

### 5.1 병합 빈도

공통 계약→첫 소환/전투→작은 기능 순으로 반나절~2일 크기의 변경을 같은 과정의 통합 브랜치에 수시 병합한다. 수요일 중간 통합과 금요일 공동 실행에서 통합 SHA·입력 SHA·실패/수정 근거를 남긴다. 준비된 변경을 단계 종료까지 쌓아두지 않으며, 검증된 통합 변경을 양쪽 역할 브랜치에 반영한다.

첫 G0 병합9/23, 경로/첫 전투10/2, 핵심 조작/웨이브10/9, P0 PC/Android10/16이 목표다. 휴무는 직전 근무일로 옮기고 검수 실패 시 완료 표시를 보류한다. main 반영은 정식 Git/PR 기준을 따르며 참고 통합 성공이 실제 학습 통합 성공을 대체하지 않는다.

## 6. 제작 상태와 실제 개발 상태

| 상태 | 참고 자료 제작 | 실제 학습 개발 |
|---|---|---|
| Planned | 목차/선행 조건만 있음 | 시작 전 |
| Draft | 코드 또는 설명 작성 중, 재현 검증 전 | 구현/학습 중 |
| Verified | 기준 커밋과 실제 실행·재현 증거 확보 | 자기 구현의 실행·통합 증거 확보 |

각 마일스톤과 수업에 두 상태를 따로 쓴다. Verified에는 커밋·실행 범위·증거가 필요하다. 참고 자료의 제작/검수 기록은 학습 진행용이며 제품 작업 보드의 Done을 자동 변경하지 않는다. 제품 완료에 사용한 실행 증거는 정식 검수 기록에도 보관한다.

## 7. 정식 문서의 원본 유지

게임 규칙 변경·공통 API 확정·빌드 절차·제품 버그 수정의 결론은 먼저 정식 명세/설계에 반영한다. 학습 자료는 그 문서와 실제 구현 커밋을 인용한다. 같은 규칙을 학습본 안에서만 수정하지 않는다.

각 수업은 코드 흐름 설명→직접 재현→실패 사례 확인→작은 변형→상대 리뷰로 마무리한다. 실습 변형은 별도 변경으로 유지하며 원작 규칙이나 제품 요구사항을 자동 변경하지 않는다.
