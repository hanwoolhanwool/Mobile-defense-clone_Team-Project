# 게임 제작·검증 자동화 기능 설계

[기획 허브](../README.md) · [에디터 기능 설계](EDITOR_TOOLS.md) · [게임 구현 구조](ARCHITECTURE.md) · [QA 기대 결과](../BACKLOG_QA.md) · [검수 기록](../production/TEST_RUNS.md)

## 1. 목적과 적용 기준

데이터 수정 이후 생성·임포트·규칙 검증·반복 전투·성능 측정을 연결하여, 사람이 같은 준비와 확인을 반복하는 시간을 줄인다. 첫 목표는 **데이터 검증·임포트 자동화 + 핵심 규칙 회귀 테스트 + 재현 가능한 결과 기록**이다.

이 문서는 사용자의 에디터·자동화 기능 문서화 요청에 따른 확장 설계 초안이다. 2인 협동, 30웨이브, 소환·합성·제작의 게임 기획을 기준으로 하며 실제 게임의 구현 완료나 테스트 통과를 뜻하지 않는다. 기능별 게임 규칙은 기존 명세가 원본이다.

자동화는 개발·QA·밸런스 검증을 위한 것이다. 플레이어 대상 자동 전투, 운영 계정 보상 지급, 스토어 자동 출시 기능은 포함하지 않는다. 이 문서 작성으로 CI 작업이나 예약 실행을 활성화하지 않는다.

## 2. 현재 기반과 추가할 범위

DEC-019의 P0 검증 범위와 DEC-021/DEC-022의 [원작 대조 기준](../product/ORIGINAL_REFERENCE.md)을 적용한다. 아래 기존 수치·보드·교환·잠금 사례는 자체 초안의 검사 예시다. 각 시나리오는 프로파일과 근거 상태를 고정하고 미확인 규칙의 실험 결과를 원작 재현 성공으로 표시하지 않는다. 전체 도구 구축은 P0의 새로운 통과 조건이 아니다.

| 구분 | 확인한 파일·상태 | 확장 방향 |
|---|---|---|
| 데이터 생성 | [build-design-data.mjs](../../tools/build-design-data.mjs)가 8개 DataTable JSON과 GameRules 생성 | 편집 원본 분리 후 생성 결과의 최신 여부·임포트 확인 |
| 데이터 검사 | [validate-design-data.mjs](../../tools/validate-design-data.mjs)가 참조·확률·수식·초기 경제 일관성 검사 | 일반 유효성, 버전별 기대값, 실제 런타임 검증 분리 |
| 기획 읽기본 생성 | [build-planning.mjs](../../tools/build-planning.mjs)가 기존 20장 읽기본 생성 | 기존 문서 관리 흐름 유지 |
| 기획 검사 | [validate-planning.mjs](../../tools/validate-planning.mjs)가 링크·메타데이터·작업·QA·읽기본 검사 | 개발 도구 문서 링크도 기존 문서 검사에 포함 |
| 게임 실행 증거 | [검수 기록](../production/TEST_RUNS.md)에 게임 기능·기기 테스트 실행 증거 미등록 | 실제 실행한 빌드·환경·관찰값·로그 기록 |

기존 JSON 검사 통과는 UE 임포트, 컴파일, 전투, 네트워크, 모바일 성능의 통과를 의미하지 않는다. 기존 스크립트와 같은 계산을 반복해서 검사하는 것만으로 게임 코드와의 일치를 증명하지 않는다.

현재 `build-design-data.mjs`는 고정된 `data/` 경로를 덮어쓰고, `validate-design-data.mjs`도 `docs/VALIDATION_REPORT.md`를 작성한다. 둘 다 읽기 전용 검사로 호출하지 않는다. 임시 출력 경로·검사 전용 모드·구조화 결과는 TASK-TOOLS-01의 추가 구현 범위다. 이번 문서 검토에서는 이 스크립트를 변경하거나 실행하지 않는다.

## 3. 기능 목록과 실행 계층

| ID | 기능 | 우선순위 | 주요 산출물 |
|---|---|---|---|
| AT-F01 | 데이터 검증·임포트 | 최우선 | 필드별 오류, 생성·임포트 결과, 로드 데이터 비교 |
| AT-F02 | 핵심 규칙 회귀 테스트 | 최우선 | QA 항목별 결과와 상태 변화 증거 |
| AT-F03 | 확률·경제 시뮬레이션 | 높음 | 획득 시점·비용·미획득 비율의 분포 |
| AT-F04 | 봇 전투·밸런스 비교 | 높음 | 시드·정책별 전투 결과와 변경 전후 차이 |
| AT-F05 | 협동·재접속 테스트 | 높음, 네트워크 구현에 따라 단계 적용 | 서버·클라이언트 상태 비교, 이탈·복귀 기록 |
| AT-F06 | 빌드·성능 검사 | 중간, 실기기 빌드 기반 확보 후 | 테스트 빌드, 성능 추적, 오류·크래시 자료 |

```text
원본 및 기획 정적 검사
 → 데이터 생성·UE 임포트·에셋 검사
 → 실제 게임 규칙 회귀 검사
 → 확률·경제 반복 실행 / 봇 전투 비교
 → 패키징 빌드의 협동·기기·성능 검사
 → 결과 묶음 저장·이전 실행 비교
```

모든 변경에 모든 계층을 실행하지 않는다. 영향을 받는 빠른 검사를 먼저 수행하고 긴 전투·기기 검사는 별도 실행 묶음으로 관리한다. 선행 단계 실패로 실행하지 못한 항목은 통과로 집계하지 않는다.

## 4. 기능별 동작

### 4.1 AT-F01 — 데이터 검증·임포트

검사를 세 종류로 나눈다.

| 검사 종류 | 사례 | 처리 |
|---|---|---|
| 일반 데이터 유효성 | 필수 필드, 타입, 중복 ID, 존재하지 않는 참조, 가중치 합계 | 적용 전 오류로 처리 |
| 버전별 게임 기준 | 수호자 20종, 30웨이브, 가격 공식, 보스 구간 | 해당 RulesVersion의 기대값과 비교 |
| 런타임 일치 | 생성한 스탯·참조와 UE에서 실제 로드한 값 | 구조체 누락·변환·임포트·오래된 에셋 문제 검출 |

현재 두 검증 스크립트는 유용한 기반이지만, 데이터 검증기는 고정 밸런스 기대값과 일반 오류 검사를 함께 수행한다. 이를 분리해 버전별 기대값을 명시한다. 일반 데이터 유효성 검사를 통과했다고 밸런스가 적절하다고 판정하지 않는다.

편집 원본 저장 이후 생성·임포트·에셋 검사를 수행한다. 다중 파일·에셋 반영 도중 실패하면 실패 단계를 남기고 부분 적용본을 테스트에 사용하지 않는다. 복구 방식은 [에디터 저장 원칙](EDITOR_TOOLS.md)을 따른다.

CI에서 생성물의 최신 여부를 확인할 때는 임시 경로에 생성한 결과를 저장소의 생성물과 비교한다. 기존 생성기는 파일을 덮어쓰므로, 임시 출력 또는 검사 전용 모드 구현 전에는 생성 명령을 읽기 전용 검사로 취급하지 않는다.

### 4.2 AT-F02 — 핵심 규칙 회귀 테스트

게임의 실제 서버 명령·전투 스텝·경제·보드 처리 코드를 실행하고 기대 결과와 비교한다. 초기 상태 주입과 검증 대상 행동을 구분한다. 명령 검증을 시험하면서 골드·개체를 직접 변경해 성공한 것으로 처리하지 않는다.

첫 자동화 묶음은 아래 10개를 제안한다. P0와 전체 규칙의 지원 기능이 다르므로 실행 대상 프로파일을 각 시나리오에 명시한다.

| 기존 QA | 초기 조건·행동 | 관찰할 결과 |
|---|---|---|
| [QA-ECO-01](../BACKLOG_QA.md#QA-ECO-01) | 140골드로 일반 소환 5회 | 총 120 소비, 잔여 20, 다음 가격 30 |
| [QA-BOARD-01](../BACKLOG_QA.md#QA-BOARD-01) | 12칸 점유, 일부 스택 여유 상태에서 소환 | 빈 칸 규칙으로 거절, 재화·RNG·카운터 불변 |
| [QA-BOARD-03](../BACKLOG_QA.md#QA-BOARD-03) | 같은 InstanceId를 세 번 넣어 합성 | 거절, 개체·재화·보드 불변 |
| [QA-BOARD-07](../BACKLOG_QA.md#QA-BOARD-07) | 같은 개체를 합성과 판매에 연속 사용 | 첫 확정 명령만 유효, 중복 소비 없음 |
| [QA-RNG-03](../BACKLOG_QA.md#QA-RNG-03) | 전체 규칙에서 일반 14회 연속 후 다음 소환 | 보장 프로파일 사용, 허용 등급, 카운터 초기화 |
| [QA-RNG-05](../BACKLOG_QA.md#QA-RNG-05) | 보장 직전 자원 부족 또는 빈 칸 없음 | 추첨·보장·소환 횟수·재화가 변하지 않음 |
| [QA-TIME-01](../BACKLOG_QA.md#QA-TIME-01) | 적 100개 상태 2.95초 뒤 99개 | 과밀 누적 0, 패배하지 않음 |
| [QA-TIME-02](../BACKLOG_QA.md#QA-TIME-02) | 적 100개 상태 연속 3.00초 | 패배 한 번 확정 |
| [QA-TIME-03](../BACKLOG_QA.md#QA-TIME-03) | 마지막 보스가 마감 시각에 사망 | 해당 시각 타격 처리 후 보스 조건 통과 |
| [QA-NET-03](../BACKLOG_QA.md#QA-NET-03) | 같은 세대·RequestId·내용 20회 재전송 | 처리 중 Pending, 완료 후 원래 응답. Phase/Revision 변경 뒤에도 재실행·중복 소비·상태 되돌림 없음 |

시간 경계는 서버 논리 시간과 예약 타격 시각을 사용한다. 테스트 PC의 실제 대기 시간만으로 2.95초·3.00초 판정을 만들지 않는다. 보스 구간 성공과 최종 매치 승리를 구분하며 최종 잔여 적 규칙도 후속 검사에 포함한다.

이후 신화 제작 공간·잠금, 웨이브 스폰 배분, 상태이상, 이동 쿨다운, 최종 보상 중복, 결과 확정 후 명령 거절로 확장한다. 기존 QA의 기대 결과를 원본으로 유지하고 테스트 코드·보고서에서 QA ID로 연결한다.

DEC-020 명령 구현 시 [QA-CMD-01](../BACKLOG_QA.md#QA-CMD-01)~[QA-CMD-03](../BACKLOG_QA.md#QA-CMD-03), [QA-NET-09](../BACKLOG_QA.md#QA-NET-09)/[QA-NET-10](../BACKLOG_QA.md#QA-NET-10)을 추가 회귀로 연결한다. payload·선택 기준·MoveMode·원하는 설정값과 같은 번호의 내용 충돌·결과 캐시 퇴출을 검사한다. Result 상태에서는 새 게임 명령을 거절하되 이미 확정된 같은 요청의 재확인은 원래 결과를 반환한다. 이 항목들은 구현 후 실행할 검수 명세이며 현재 실행 증거가 아니다.

P1 상태이상 실행기 검수에는 [QA-DMG-11](../BACKLOG_QA.md#QA-DMG-11)~[QA-DMG-14](../BACKLOG_QA.md#QA-DMG-14)를 추가한다. [화상 종료 경계](../design/BATTLE.md)의 예약 시각·만료 시각·원천별 활성/억제·피해 횟수를 실제 전투 코드에서 관찰하고 정상 스텝과 지연 처리를 비교한다. JSON의 지속시간 곱셈 검사만으로 마지막 틱 성공을 판정하지 않는다. 이 묶음은 기존 자체 설계의 기술 회귀 기준이며 원작 스킬 재현 증거 또는 P0 완료 조건이 아니다.

### 4.3 AT-F03 — 확률·경제 시뮬레이션

첫 단계는 렌더링 없이 경제·추첨 로직을 반복 실행한다. 입력은 데이터 버전, 시드 묶음, 실행 수, 소환·강화·합성 정책, 자원 공급 조건, 실행 종료 조건이다.

- 비보장 기본 추첨과 보장을 포함한 연속 플레이를 별도 실험으로 실행한다.
- 기본 분포는 [QA-RNG-06](../BACKLOG_QA.md#QA-RNG-06)의 별도 10만 회 기준을 연결한다. 기대 분포·표본 수·허용 오차 또는 통계 기준을 실행 전에 고정한다.
- 비용·획득 시점은 평균, 중앙값, p10/p90, 미획득 실행 수·비율을 함께 표시한다. 미획득 실행을 제외한 평균에는 조건부 평균이라는 표시를 붙인다.
- 자원 공급이 가정이면 `모든 일반 적을 제때 처치한 수입 상한`처럼 조건을 명시한다. 경제상 구매 가능성을 전투 생존·신화 획득 보장으로 해석하지 않는다.
- 보장 카운터, 소환 횟수에 따른 가격, 보드 공간, 잠금·교환 한도를 정책 실행에 반영한다.

실제 경제 코드와 공통 구현을 쓰는 것을 목표로 한다. 별도 언어의 분석 모델을 먼저 만들면 대표 입력·경계값을 실제 게임과 대조하고 결과에 `분석 모델`이라고 표시한다.

### 4.4 AT-F04 — 봇 전투·밸런스 비교

경제 시뮬레이션 다음 단계로 실제 전투 로직을 반복 실행한다. 봇은 [협동 명세](../design/COOP_META.md)의 행동 정책을 시작점으로 하고 사람과 같은 서버 명령 검증 경로를 사용한다.

- 입력: 시작 상태, 시드 묶음, 양쪽 봇 정책·판단 간격, 데이터 버전, 반복 수.
- 지표: 성공률, 실패 웨이브·이유, 보스 잔여 HP, 최초 전설·신화 시점, 과밀 체류, 보드 포화 시간, 지출·피해·지원 기여.
- 비교: 데이터 변경 전후에 같은 시드 묶음·정책·시나리오·실행 환경을 사용하고 실제 변경 항목을 기록한다.
- 정책 다양성: 기본·소환 우선·강화 우선·지원 조합처럼 명시적인 정책으로 확장한다. 한 봇 정책의 약점을 게임 전체 문제로 단정하지 않는다.
- 실행: 고정 논리 스텝을 유지한다. 배속·렌더링 생략 실행은 정상 속도의 기준 실행과 결과를 대조한 뒤 사용한다.

봇 승률은 자동 비교 지표다. 신규 플레이어·숙련 팀의 실제 승률 목표를 대신하지 않는다. 데이터 변경으로 추첨 호출 횟수와 행동이 달라질 수 있으므로 같은 시드가 같은 경로의 전투를 보장하지는 않는다.

### 4.5 AT-F05 — 협동·재접속 테스트

먼저 리슨 서버 세션, 이후 전용 서버 세션을 자동 실행한다. 리슨 서버는 호스트 프로세스가 서버와 플레이어 한 명을 겸하고 원격 클라이언트 한 개가 참여한다. 전용 서버는 서버 한 개와 클라이언트 두 개를 실행한다.

| 실행 묶음 | 시나리오 | 검증 |
|---|---|---|
| 연결·명령 | 두 플레이어 동시 소환·합성, 중복 RequestId, 오래된 BoardRevision | 서버 결과와 각 클라이언트에 보여야 하는 상태 일치 |
| 지연·손실 | RTT 150ms·손실 1%, RTT 300ms·손실 3% | 중복 소비 없음, 회복 후 상태 수렴, 처리중 UI |
| 이탈·봇 | 전용 서버에서 연결 단절 5초 | 전투 지속, 봇 인계, 인계 시간 기록 |
| 재접속 | 30초 뒤 복귀, 60초 초과 복귀, 이전 ConnectionEpoch 명령 | 전체 상태 복원·봇 중지 또는 규칙에 따른 거절 |
| 결과·저장 | 결과 응답 유실·재시도, 앱 재진입 | MatchId·AccountId 기준 보상 한 번 |

RTT는 왕복 시간 기준이다. 도구의 입력이 편도 지연이면 값으로 환산하고 실제 측정 RTT도 남긴다. 리슨 서버의 호스트 종료는 세션 종료로 검사하며, 전용 서버용 재접속 기대 결과를 그대로 적용하지 않는다.

개인 경제 정보처럼 소유자에게만 복제되는 값은 해당 소유 클라이언트에서 비교한다. 모든 클라이언트에 같은 비공개 상태가 있어야 한다고 검사하지 않는다. 계정 저장 검사는 별도 테스트 프로필·저장 공간을 사용한다.

관련 기준: [QA-NET-01](../BACKLOG_QA.md#QA-NET-01), [QA-NET-02](../BACKLOG_QA.md#QA-NET-02), [QA-REJOIN-02](../BACKLOG_QA.md#QA-REJOIN-02), [QA-SAVE-01](../BACKLOG_QA.md#QA-SAVE-01).

### 4.6 AT-F06 — 빌드·성능 검사

빌드 단계와 실행 단계를 분리한다. 설치된 UE·플랫폼 SDK에 맞는 빌드 명령으로 테스트용 패키지를 만들고, 성공한 산출물을 기기 실행 단계에 넘긴다. 첫 대상은 Windows Development와 Android 검증 빌드이며 iOS는 해당 빌드 환경이 준비된 뒤 추가한다.

- 빌드: 컴파일·쿠킹·패키징 결과, 엔진·SDK 버전, 빌드 ID, 로그 수집.
- 기본 실행: 실행→전장 진입→짧은 테스트→종료까지 성공 여부 확인.
- 부하: 수호자 72개·적 128개·스킬 동시 실행 상태로 20분 측정.
- 반복 생성: 적 생성·사망 2,000회로 메모리 지속 증가, 남은 타이머, 재사용 세대 오염 확인.
- 표현 비교: 낮은 VFX·30FPS 설정에서도 논리 피해·경고·조작 유지 확인.

128개 적을 유지하는 부하 시나리오는 일반 과밀 패배 때문에 3초 만에 끝나지 않도록 전용 시험장을 사용한다. 종료 판정을 우회하는 경우 RunManifest에 기록하고 승패 규칙 검사와 분리한다. 수호자 72개는 현재 스택 규칙에 맞는 실제 개체 구성으로 만든다.

기록할 지표는 프레임 평균·p95·최대, 게임/렌더/GPU 시간, 메모리 변화, 서버 스텝 시간, 지원 기기의 열 상태다. 열 상태를 읽을 수 없으면 미측정으로 표시한다. 기준 기기·해상도·그래픽 설정·측정 구간을 고정하고 에디터 FPS를 모바일 성능으로 보고하지 않는다.

초기 목표는 [기술 명세](ARCHITECTURE.md)의 30FPS·p95 33.3ms, 선택 60FPS·p95 16.7ms 등을 따른다. 현재 값은 실측으로 확정된 보증치가 아니므로 초기에는 보고 지표로 사용하고, 기준 기기 실측 후 성능 통과 기준을 확정한다.

## 5. 에디터·자동화 공유 실행 계약

<a id="shared-test-contract"></a>

아래 이름과 저장 경로는 구현 제안이다. 현재 해당 파일·API가 존재한다는 뜻은 아니다. 에디터는 이 계약을 소비하고 별도 형식으로 복제하지 않는다.

| 계약 | 필수 내용 |
|---|---|
| TestScenario | ScenarioId·버전, 대상 프로파일, 시작 프리셋 또는 스냅샷 참조, 시드, 플레이어/봇 정책, 시간·스텝별 행동, 기대 결과, 제한 시간, 기능 요구 조건 |
| InitialPreset | 시작 웨이브, 양쪽 보드·개체·재화·강화·잠금·보장 카운터, 초기 적·기준 시간. 지정하지 않은 값의 기본값도 버전으로 관리 |
| RuntimeSnapshot | 상태 형식 버전, BuildVersion·RulesVersion·DataHash, 서버 스텝·경과 시간, 매치 단계, 예약 스폰·피해·보상, 개체·적·경로 거리, 타이머·효과·표적, 과밀 누적, 플레이어 경제·보드 Revision, RNG 스트림 상태, ID 할당 상태, 논리 명령 중복 처리 상태 |
| InputLog | 로그 형식 버전, 서버 수신 순서·적용 스텝, RequestId·ConnectionEpoch, 발신 역할, DEC-020의 CommandType·ExpectedBoardRevision·명령별 payload, 정규화한 내용·결과 코드·응답 Revision·EventId. 실제 연결 객체·인증 토큰은 저장하지 않음 |
| RunManifest | RunId, 시나리오·정책 버전, QA ID, BuildVersion, Git 커밋·Dirty 여부·소스 변경 식별값, RulesVersion·DataHash, 시드, 엔진·기기·OS·해상도·네트워크 설정, 시작·종료 시간, 테스트 오버라이드 |
| RunResult | 항목별 Pass/Fail/NotRun, 실제값·기대값, 오류 유형, 지표, 실행 수·실패 수, 로그·스냅샷·이미지·성능 추적 참조 |

스냅샷은 논리 스텝 경계에서 저장하고, 진행 중인 명령의 처리 상태를 명시한다. 복원 시 새 테스트 세션에 논리 상태를 구성하고 복제 상태를 다시 전달한다. 실제 네트워크 연결을 직렬화하여 되살리는 방식으로 설계하지 않는다.

첫 버전은 InitialPreset과 InputLog를 지원한다. RuntimeSnapshot은 모든 지원 상태를 수집·검증할 수 있는 단계에서 도입하며, 미지원 스킬·버전 불일치가 있으면 복원을 거절한다. 동일 시드만으로 전체 3D 전투가 비트 단위로 같다고 약속하지 않는다.

저장 위치 제안은 버전 관리 대상 시나리오 `tests/scenarios/`, 실행 산출물 `Saved/Automation/<RunId>/`다. 큰 로그·영상·기기 추적은 산출물로 관리하고, 사람이 검토한 실행 요약과 보존할 증거 위치를 [검수 기록](../production/TEST_RUNS.md)에 연결한다.

### 5.1 첫 실행 형식의 필수 조건

공유 형식의 초안 버전은 `SchemaVersion=1`로 한다. 아래 필드는 구현 시 검증할 계약이며 실제 스키마 파일·로더·CLI는 아직 없다. 알 수 없는 버전, 필수 필드 누락, 허용 목록 밖 필드는 실행 전에 오류로 반환한다. 선택 필드의 기본값은 스키마 버전으로 고정하며 런타임 환경에 따라 조용히 바꾸지 않는다.

| 계약 | 구체 조건 |
|---|---|
| TestScenario | ScenarioId·ScenarioVersion, Profile(P0/P1/P2), EvidenceBasis(InternalDraft/OriginalVerified), 근거 문서(원작 검증은 관찰 ID 포함), RequiredFeatures 문자열 목록, QaIds 목록, Preset 참조·해시, uint32 Seed, Actions, Assertions, MaxSteps 양의 정수, TimeoutSeconds 양의 수 |
| Actions | 각 행동에 StepIndex(0 이상 정수)·Sequence(동일 스텝 내 순번)·발신 플레이어·실제 명령 payload. 동일 순서 키 중복은 오류. 초기화 뒤 첫 전투 스텝을 0으로 하며 논리 간격은 현재 0.05초. 일시정지 중에는 인덱스 증가 없음 |
| Assertions | QA별 관찰 위치·필드·연산자·기대값. 정수·ID·횟수는 정확 비교, 실수는 시나리오에 사전 지정한 허용 오차 사용. 기대값과 비교 조건은 실행 뒤 수정하지 않음 |
| RunManifest | 기존 필수 정보에 SchemaVersion, ScenarioHash, PresetHash, SourceRevision, AppliedDataHash, 요청한/적용한 프로파일·기능 목록, PlannedQaIds, ParentRunId(재실행일 때), 단계별 제한 시간 포함 |
| RunResult | RunId, 전체 Pass/Fail/NotRun, QA별 상태·ReasonCode·기대값·관찰값·증거 참조, Planned/Passed/Failed/NotRun 개수, 단계별 결과, CleanupStatus. 미실행 항목도 목록에서 제외하지 않음 |

InitialPreset의 기본값 적용이 끝난 전체 상태를 실행 산출물에 저장한다. 프리셋 초기화와 행동 수행을 분리하고, P0에서 스킬·강화 등 미지원 기능을 요구하면 자동으로 P1로 바꾸지 않고 NotRun/UnsupportedProfile로 기록한다. 원작 검증용 실행이 InternalDraft 규칙에 의존하면 NotRun/UnverifiedRule로 기록한다. 내부 기술 회귀와 원작 대조는 각각 별도 결과를 갖는다.

SourceRevision은 편집 원본 파일 묶음, DataHash는 생성한 전체 규칙·테이블 묶음, AppliedDataHash는 UE 재로드·값 비교를 통과한 그 데이터 묶음의 식별값이다. 생성 바이트 비교용 해시는 상대 경로를 정렬한 목록과 각 파일 SHA-256으로 계산한다. 시나리오·프리셋도 저장된 파일 바이트의 SHA-256을 남긴다. UTF-8·LF·키/행 정렬을 생성기에서 고정하며, UE 로드 비교는 JSON 텍스트 순서가 아닌 타입·값·참조를 비교한다. SourceRevision, 생성기 버전, DataHash와 런타임 오버라이드를 모두 기록해 같은 RulesVersion 안의 변경도 식별한다.

### 5.2 실행 수명과 산출물

실행은 `요청 검사 → 자원 확보 → 초기화 → 행동·관찰 → 중간 결과 저장 → 정리 → 최종 결과 확정` 순서다. RunId는 각 실행마다 새로 만들고 기존 폴더를 덮어쓰지 않는다. 동일 RunId 재조회는 기존 상태를 반환하며 재실행은 ParentRunId를 가진 새 요청이다. 실행 경로 제안은 `Saved/Automation/<RunId>/` 아래 `manifest.json`, `resolved-preset.json`, `input-log.jsonl`, `result.json`, `logs/`다. 필수 결과는 임시 파일 작성 후 교체하고, 중간 결과는 완료 결과와 구분한다. CleanupStatus를 반영한 최종 결과가 저장되기 전에는 성공을 반환하지 않는다.

시간 한도는 게임 내 MaxSteps와 프로세스 감시용 TimeoutSeconds를 각각 사용한다. 초기화·실행·정리 제한 시간을 RunManifest에 기록한다. 게임 테스트 자체가 타임아웃 검수 대상이면 예상 시간 초과를 관찰한 결과로 판정하고, 실행기 감시 시간 초과와 구분한다.

취소하면 이미 끝난 QA 결과를 보존하고 진행 중·미시작 QA는 NotRun/Cancelled로 남긴다. 앞서 실패한 항목을 취소로 덮어쓰지 않는다. 실행기가 만든 PID·포트·임시 저장 영역·기기 임대만 추적해 정리하고 사용자가 열어 둔 에디터나 다른 실행을 종료하지 않는다. 같은 프로젝트 적용·같은 기기 사용은 배타적으로 확보하며 병렬 실행마다 저장 프로필·포트를 분리한다. 정리 실패도 Fail/CleanupError로 남기고 해당 자원을 다음 실행에 재사용하지 않는다.

전체 Pass는 계획한 필수 QA가 1개 이상이며 전부 Pass이고 초기화·증거 저장·정리까지 성공했을 때만 가능하다. 항목 실패 또는 실행 인프라 실패가 있으면 전체 Fail, 실패는 없지만 필수 NotRun이 하나라도 있거나 선택된 필수 QA가 0개이면 전체 NotRun이다. 지원 범위 밖의 QA는 실행 전 선택 목록에서 제외 사유를 기록하거나, 이미 PlannedQaIds에 포함했다면 NotRun으로 남긴다. `Planned = Passed + Failed + NotRun`을 검사한다.

향후 CLI의 종료 코드는 0=전체 Pass, 1=전체 Fail, 2=전체 NotRun으로 제안한다. 잘못된 요청·스키마·결과 누락은 Fail/ContractError이며, 실제 게임을 시작하지 못한 하위 QA는 NotRun이다. 이 종료 코드는 현재 Node 스크립트에 구현된 것으로 가정하지 않는다. 재실행 전에 생성물·로드 데이터·프로파일 해시를 다시 확인한다.

## 6. 실행 조건과 결과 처리

| 실행 시점 제안 | 실행 범위 | 실패 처리 |
|---|---|---|
| 에디터 적용 전 | 변경 데이터의 유효성·참조 검사 | 적용 중단, 오류 필드 표시 |
| 개발자 수동 실행 | 선택 QA·프리셋·시드 비교 | 실행 ID와 재현 자료 제공 |
| 코드·데이터 변경 검토 시 | 문서·데이터 검사, 빠른 규칙 회귀 | 필수 검사 실패를 변경 검토에 표시 |
| 정기 실행 | 확률·경제, 봇 묶음, 협동, 장시간 기기 테스트 | 새 실패·성능 악화와 비교 자료 보고 |
| 배포 후보 확인 | 대상 플랫폼 패키징·기능·실기기 검사 | 미검증·실패 항목을 포함한 검수 결과 제공 |

이 표는 향후 실행 정책 제안이며 예약 시각·CI 제공자·실행 기기는 아직 정하지 않았다. 느린 테스트를 병렬 실행할 때는 포트·기기·임시 저장 공간·테스트 프로필을 분리한다.

- **Pass:** 기대 결과를 모두 관찰하고 필요한 증거를 수집했다.
- **Fail:** 기대 결과 불일치, 크래시, 시작 후 타임아웃, 필수 증거 수집 실패가 발생했다. 게임·빌드·환경 오류를 유형으로 구분한다.
- **NotRun:** 선행 실패·기기 부재·미지원 프로파일·취소로 검사하지 못했다. 사유를 남기며 통과율 계산에 숨기지 않는다.
- 재실행은 새 RunId로 남기고 최초 실패를 보존한다. 통과할 때까지 반복한 최종 결과만 보고하지 않는다.
- 임의 분포나 성능 변동은 반복 수·비교 조건·허용 범위를 함께 검토한다. 기준 변경은 결과를 본 뒤 조용히 수정하지 않고 변경 이유를 기록한다.
- 정기 실행 알림을 도입하면 새 실패, 의미 있는 결과 변화, 실행 인프라 오류를 중심으로 알린다. 동일한 정상 결과를 매번 메시지로 보낼 필요는 없다.

## 7. 구현 도구와 책임

| 구성 | 도구 방향 | 담당할 일 |
|---|---|---|
| 문서·데이터 정적 검사 | 기존 Node.js 스크립트 확장 | 원본 검사, 생성 결과 비교, 보고서 |
| UE 에셋 검사 | Data Validation | 에셋 참조·타입·프로젝트 규칙 검사 |
| 게임 로직·레벨 검사 | Automation Test Framework·Functional Testing | 실제 명령·전투 상태·레벨 동작 검증 |
| 여러 프로세스·기기 실행 | Gauntlet 검토 | 서버·클라이언트·기기 실행과 결과 수집 |
| 빌드·패키징 | 실제 엔진·플랫폼 환경의 빌드 도구 | 성공한 패키지를 실행 단계에 제공 |

[Data Validation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine)은 에셋 규칙을 명령행 검사에 연결할 수 있다. [Automation Test Framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/automation-test-framework-in-unreal-engine)는 기능·콘텐츠 검사와 Functional Testing 등의 인터페이스를 제공한다. [Gauntlet](https://dev.epicgames.com/documentation/en-us/unreal-engine/gauntlet-automation-framework-overview-in-unreal-engine)은 여러 프로세스로 구성된 세션과 기기 실행을 관리하며 빌드를 직접 생성하는 도구는 아니다.

도구 실행의 성공과 게임 검사의 성공을 구분한다. 프로세스 종료 코드뿐 아니라 예상 테스트 개수·결과 파일·필수 판정 항목을 확인하여 테스트가 하나도 실행되지 않은 경우를 통과 처리하지 않는다.

## 8. 구현 순서와 완료 조건

| 단계 | 범위 | 단계 완료 증거 |
|---|---|---|
| A0 — 기반 정리 | 실행 계약, 현재 스크립트의 검사·쓰기 분리, 데이터 적용 경로 | 동일 원본에서 일치하는 생성·임포트 결과와 RunManifest |
| A1 — 첫 자동화 | AT-F01, 핵심 회귀 10개, 에디터 실행 연동 | 고의로 만든 규칙 오류를 검출하고 원인·재현 조건 기록 |
| A2 — 밸런스 | AT-F03, 실제 전투 봇, 변경 전후 비교 | 같은 시드·정책 묶음으로 비교 보고서 생성 |
| A3 — 협동·기기 | AT-F05, AT-F06, 실행 환경 자동 정리 | 서버·클라이언트 결과 및 패키징 빌드의 기기 측정 증거 |

협동 명령 테스트와 모바일 빌드 검증은 게임 개발 진행에 맞춰 앞당길 수 있다. 전용 서버 재접속과 iOS는 해당 환경이 준비된 후 적용한다. 단계는 계획이며 구현 작업의 상태를 표시하지 않는다.

| ID | 검수 행동 | 기대 결과 |
|---|---|---|
| AT-AC01 | 없는 유닛 참조·잘못된 확률 합계를 넣고 실행 | 필드별 오류와 실패 상태, 다음 적용 단계 미실행 |
| AT-AC02 | 실제 로드된 UE 데이터 한 항목을 원본과 다르게 구성 | 임포트·로드 비교 실패로 식별 |
| AT-AC03 | 중복 명령에서 자원을 두 번 차감하도록 결함을 주입한 테스트 빌드 실행 | 해당 QA 실패, 변경 전후 자원과 요청 로그 보존 |
| AT-AC04 | 같은 버전·프리셋·입력으로 지원 범위 내 재실행 | 명시한 논리 기대값이 일치하며 차이는 로그로 식별 |
| AT-AC05 | 일부 시드에서 신화를 못 얻은 경제 실험 실행 | 미획득 수·비율을 포함한 결과, 실행 수 합계 일치 |
| AT-AC06 | 클라이언트 프로세스 중단 또는 제한 시간 초과 | 실패 원인 기록, 관련 프로세스·기기 자원 정리 |
| AT-AC07 | 선행 빌드 실패 또는 실행된 테스트가 0개 | 후속 항목 NotRun, 전체 성공으로 표시하지 않음 |
| AT-AC08 | 128개 적 부하 시험장에서 20분 실행 | 테스트 오버라이드·기기·프레임·메모리와 측정 구간 기록 |
| AT-AC09 | 같은 실패를 수정 후 재실행 | 이전 실패 RunId 보존, 새 실행과 수정 내용을 연결 |
| AT-AC10 | SchemaVersion 불일치·중복 행동 순서·필수 필드 누락 | ContractError로 실행 전 거절, 게임 상태 변경 없음 |
| AT-AC11 | 계획 QA 3개 중 1개 미실행, 또는 결과 파일의 합계 불일치 | 미실행이면 전체 NotRun, 결과 계약 오류면 전체 Fail. 종료 코드 0으로 보고하지 않음 |
| AT-AC12 | 실행 중 취소·프로세스 중단 후 정리 실패 | 완료 QA·실패 기록 보존, 미완료 QA NotRun, 소유 자원만 정리하고 정리 실패는 전체 Fail |
| AT-AC13 | P0에 화상 시나리오 또는 원작 검증에 미확인 자체 규칙 요청 | UnsupportedProfile/UnverifiedRule로 NotRun, 기능 자동 활성화·원작 통과 표시 없음 |

### 8.1 도구 기능과 개발 작업 연결

<a id="tool-task-map"></a>

아래 네 작업은 개발 도구 확장의 P1 Should 백로그다. 기존 P0 구현·PC/Android 수동 검증을 기다리게 하는 선행 조건으로 추가하지 않는다. 담당자·소요일은 아직 미정이다. 기존 10일/P1 일정 추정에는 도구 확장 공수를 포함한 것으로 간주하지 않고 착수 시 재산정한다.

| 작업 | 기능·범위 | 선행 구현·검수 |
|---|---|---|
| [TASK-TOOLS-01](../BACKLOG_QA.md#TASK-TOOLS-01) | AT-F01, ED-F02/03/04 공통 저장·생성·임포트 서비스. 원본 이관·임시 출력·복구 기록 | TASK-DATA-01. ED-AC02~05/10/11, AT-AC01/02 |
| [TASK-TOOLS-02](../BACKLOG_QA.md#TASK-TOOLS-02) | ED-F01 및 ED-F02/03 첫 네 탭. 초기 프리셋·스텝 실행·로드 값 표시 | TASK-TOOLS-01, TASK-WAVE-01. ED-AC01/06/08, 기능별 실제 게임 QA |
| [TASK-TOOLS-03](../BACKLOG_QA.md#TASK-TOOLS-03) | AT-F02 공통 실행기·실행 계약·결과 집계·취소·자원 정리, 에디터 연동 | TASK-TOOLS-01, TASK-TEST-01. AT-AC03/04/06/07/09~13, 프로파일별 첫 회귀 묶음 |
| [TASK-TOOLS-04](../BACKLOG_QA.md#TASK-TOOLS-04) | ED-F03 스킬 확장, ED-F04/05/06, AT-F03/04, RuntimeSnapshot·변경 비교 | TASK-TOOLS-02/03, TASK-COMBAT-02, TASK-ECON-02, TASK-BOT-01, TASK-ART-01. ED-AC07/09, AT-AC05 및 기능별 QA |

AT-F05의 로컬 2인 자동화 연결은 TASK-TEST-01과 TASK-TOOLS-03에서, 전용 서버·재접속은 P2의 TASK-SERVER-01/TASK-REJOIN-01에서 연결한다. AT-F06의 빌드·실기기 계측은 TASK-MOB-01/TASK-PERF-01, 외형 에셋 제작은 TASK-ART-02/03 및 TASK-FX-01이 담당한다. 도구 자동 실행 구현 전의 수동 검증도 기존 완료 기준에 맞는 증거가 있으면 유효하다. 같은 기능의 게임 구현과 도구 연결을 중복 완료로 계산하지 않는다.

## 9. 구현 전 확인할 사항

- 실제 게임의 전투·경제·보드 명령 인터페이스와 테스트 빌드 가능 여부.
- CI 실행 환경, 엔진·SDK 설치 방식, 사용할 실기기와 결과 보존 위치.
- 봇 정책·시드 묶음의 크기, 확률 검사 기준, 성능 기준 기기와 반복 측정 조건.
- 초기 상태 프리셋 이후 중간 스냅샷을 지원할 범위와 버전 호환 정책.
- 세부 작업·담당자·일정은 [작업 보드](../production/BOARD.md)에 등록하고 실제 실행 증거가 생긴 뒤 완료 처리한다.
