# 개발자 B 구현 설계 — 경제·보드

**현행 규칙:** [P0 재기획](../design/P0_REPLAN.md)의 DEC-043~047을 따른다. P0 16종·100/20·보스2/60초, P1 80웨이브·사냥/미션/던전·보물/유물/펫 실제 시스템. 고유 콘텐츠는 컨셉 후 결정하며 기존 날짜/공수는 재산정 대상이다.

**초기화 후 상태:** 기존 P0 구현과 학습 자료는 삭제됐다. 이 문서는 새로 작성할 기능의 설계이며 구현 완료본이 아니다. [초기화 내역](../production/P0_RESET.md).

**새 착수 기준(2026-09-16):** [촬영본 기반 P0 재기획](../design/P0_REPLAN.md)의 G0~G4와 PLAN 검수를 먼저 적용한다. 종전 12칸/치수/경제 수치에 대한 통과는 기존 프로토타입 결과다. 새 레이아웃은 확정된 Rows×Columns 전체를 검사하고 원작 조작 근거를 연결한다. 이번 개정은 게임 데이터·코드나 기존 실행 결과를 바꾸지 않는다.

[공통 구현 계약](IMPLEMENTATION_SHARED.md) · [A 구현 설계](IMPLEMENTATION_A.md) · [역할 분담](../production/TEAM_ROLES.md) · [초기 설정](../GETTING_STARTED.md#setup)

**P0~P2 실행 순서·주별 일정·산출물:** [B 개발 문서](../production/DEVELOPMENT_B.md). 이 구현 설계는 P0의 클래스·API·Unreal 설정 상세를 담당하며 전체 범위/마감은 [개발 계획서](../production/DEVELOPMENT_PLAN.md)를 따른다.

## 1. 내가 완성해야 할 결과

**소환 버튼 한 번이 서버에서 한 번의 재화 차감과 배치로 확정되고, 이동·합성·판매 결과가 두 화면에서 일치하게 만든다.** 전장·카메라·입력·HUD 구성과 PC 패키징 2인·지연 검수도 B가 맡는다.

이 문서는 개발자 B가 실제 작성할 순서로 구성한 설계다. 코드·에셋·설정과 제안 API는 구현 예정이며 완료된 프로젝트 사용 설명서가 아니다. [공통 계약](IMPLEMENTATION_SHARED.md#contracts)은 A/B 사이의 호출 경계, [아키텍처 15.5~16.2](ARCHITECTURE.md#implementation-rules)는 상태 원본·공동 확정·요청 처리의 원본이다.

P0의 골드 소환·배치·이동·합성·판매·기본 HUD·짧은 안내부터 구현한다. P1의 도전·제작·강화와 원작 근거가 미확인인 기능은 버튼이나 예약 enum이 있다는 이유로 활성화하지 않는다. 보드 차원은 DEC-039의 가로 6칸×세로 3칸(개인 18칸·전체 36칸)을 적용한다. 가격·배치 불가·이동/판매는 DEC-043~046을 구현한다. 물리 치수는 현재 시험 데이터로 검수하고 [원작 대조](../product/ORIGINAL_REFERENCE.md)의 역사적 관찰과 구분한다. 기존 24칸·자체 비용표를 원작 확정값으로 넣지 않는다.

## 4. B-01 — 전장·좌표·카메라 만들기

**완료할 동작:** 화면에서 선택한 위치가 두 플레이어 관점 모두에서 올바른 자기 보드의 논리 칸으로 변환된다.

**현재 구도 기준 — DEC-040:** [v2 요소별 좌표·크기](../design/BOARD_UI.md#ingame-ui-v2)를 사용한다. 기준 프레임 1080×2340, 칸 120×120px·통로 폭 120px, 각 보드 720×360px·전장 960×1080px다. 전장은 공통 배율로 맞춰 칸 정사각형과 모든 길 폭을 유지한다. 이 px를 월드 cm로 복사하지 않으며 서버 경로·CellId·전투 판정은 화면비와 분리한다.

1. 확인된 보드의 행/열·칸 간격·소유·배치 조건을 데이터로 받는다. 원작 관찰 기록과 연결하고 미확인 값은 구현 확정에서 분리한다.
2. BoardManager의 서버 원본에 칸·개체·소유 정보를 둔다. 칸 좌표는 `(PlayerIndex, CellId)`로 조회하며 화면 픽셀이나 카메라 방향을 원본 ID로 쓰지 않는다.
3. `TryGetCellTransform`과 화면→월드→보드의 변환을 구현한다. 경계 밖·상대 보드·UI 위 입력은 배치 요청으로 제출하지 않는다. 서버도 별도로 범위/소유권을 확인한다.
4. CameraPawn에서 두 보드와 경로가 보이는 프레이밍을 구성한다. DEC-031에 따라 자기 보드는 아래, 두 생성점은 왼쪽을 유지한다. 참고 구현은 LDLocalPlayer.GetProjectionData에서 플레이어 1의 뷰 X축을 반전한다. LocalPlayerClassName 등록·렌더링·클릭/드래그 역투영·상대 보드 거절을 양쪽 실제 창에서 검사한다. 화면 방향이 바뀌어도 논리 CellId는 유지한다.
5. DEC-030의 Lower/Upper 두 닫힌 Spline과 좌측 위·아래 스폰 위치를 맵에 연결한다. 같은 방향의 중앙 구간은 한 번만 표시한다. DEC-033에 따라 출구에서 각자 생성 보드 둘레로 분기해 복귀하는 두 폐곡선을 유지한다. DEC-040의 정사각형 칸·동일 폭 길을 유지하면서 3D 가시성·터치·화면비에 맞춰 전체 크기와 카메라를 조정한다. A에게 Path.Routes/SharedSegmentCm 계약을 전달한다. 서버/클라이언트에서 경로 해석이 같아야 하며 경로 참조 누락을 원점 스폰으로 대체하지 않는다.

**Unreal 작업 순서**

| 만들거나 설정할 대상 | 위치·설정 | 확인할 결과 |
|---|---|---|
| `BP_Board` | `/Game/LD/Board/`, 부모 ALDBoardManager | 확인된 좌표 데이터와 표시 타일 연결. Construction Script는 규칙/재화를 변경하지 않음 |
| `BP_CameraPawn` | `/Game/LD/Core/`, 부모 ALDCameraPawn | CameraComponent와 프레이밍 설정. 자기 관점 적용 |
| `L_TestBoard` | `/Game/LD/Tests/TestMaps/` | 테스트용 보드·경로·카메라 확인 가능 |
| `L_Workshop` | `/Game/LD/Maps/` | 통합 시 A의 BP_GameMode를 GameMode Override로 연결 |
| 화면과 선택 판정 | SafeArea·DPI·Trace 대상 확인 | 실제 표시 위치와 선택 위치 일치, 장식 메시가 칸 판정을 가리지 않음 |

보드의 authoritative 인스턴스를 맵에서 사용한다면 GameMode가 그 인스턴스를 찾아 검증하고 중복 생성하지 않는다. 스폰 방식으로 정하면 맵에는 해당 원본 액터를 중복 배치하지 않는다. 선택 방식과 이유는 첫 PR의 설정 기록에 남긴다.

**검증:** 양쪽 화면의 좌측 상단·좌측 하단 생성, 중앙 왼쪽→오른쪽 합류, 자기 보드 아래, 확정된 자기 Rows×Columns 전 칸 투영/선택 일치·상대 전 칸 조작 거절, 네 모서리·칸 경계·화면 밖·세로 화면비·노치 영역. QA-VIS-02/03에 연결한다. DEC-039의 6열×3행 전수 검사이며 과거 24칸 검사 결과를 승계하지 않는다.

**A에게 전달:** 보드 ID/칸 좌표 조회, 경로/스폰 참조, 유효성 오류, 사용할 맵과 화면 캡처.

## 5. B-02 — 입력·요청·서버 명령 경로 만들기

**완료할 동작:** 로컬 입력이 소유 Controller를 통해 서버에 도착하고, 같은 요청을 재전송해도 별개의 구매가 되지 않는다.

1. 로컬 선택·드래그 상태와 미확정 요청 추적을 Controller 수명에 둔다. 위젯 생성/제거로 RequestId가 초기화되지 않게 한다.
2. ARCHITECTURE 16.2의 FLDCommand·결과·명령별 payload·결과 코드를 실제 네이티브 타입과 직렬화로 옮긴다. 필수값·길이·enum·타입 불일치를 검사한다.
3. 소유 PlayerController의 Server RPC에서 발신자와 참가자 문맥을 서버 상태로 구해 `Submit`에 전달한다. 클라이언트가 가격·결과 유닛·보상·참가자 신원을 지정하지 못하게 한다.
4. CommandProcessor에 처리 중 요청·확정 결과 캐시·연결 세대별 HighestAdmittedRequestId를 둔다. 기존 256개 캐시와 요청 한도·동시 변경 요청 1개 계약을 유지한다.
5. 새 요청은 명세 순서로 검증하고 큐에서 처리한다. 완료된 요청의 중복 조회는 현재 Phase/BoardRevision 검사보다 먼저 수행해 원래 결과를 돌려준다.
6. Result에서도 이미 확정된 동일 요청은 캐시 규칙으로 응답하고 새 변경 요청은 거절한다. 같은 매치에서 Controller가 교체되면 새 연결 세대를 적용하되 경제 원본은 초기화하지 않는다. P2 서비스 재접속 전체 구현과 구분한다.

| 요청 상황 | 처리 결과 |
|---|---|
| 같은 키·같은 내용, 처리 중 | Pending. 추가 소비/추첨 없음 |
| 같은 키·같은 내용, 완료 | 원래 응답 재전달. 새 EventId 생성 없음 |
| 같은 키·다른 내용 | RequestIdConflict. 원래 내용·결과 보존 |
| 캐시 퇴출 후 과거 번호 | RequestExpired. 성공/실패를 새로 추측해 실행하지 않음 |
| 새 요청·오래된 보드 버전 | StaleBoard. 원본 불변, 최신 상태와 사용자 재선택 |
| 새 연결에 이전 세대 요청 | InvalidEpoch. 새 번호로 자동 재제출하지 않음 |

**Unreal 연결:** `/Game/LD/Core/BP_PlayerController`를 ALDPlayerController에서 만든다. `/Game/LD/Input/`에 필요한 IA_Select·IA_Cancel·IMC_Battle·IMC_Menu를 만들고 로컬 플레이어의 Enhanced Input Subsystem에 컨텍스트를 연결한다. 재초기화 때 중복 등록하지 않고 해제 시 자신이 등록한 컨텍스트를 제거한다. [Epic Enhanced Input](https://dev.epicgames.com/documentation/unreal-engine/enhanced-input-in-unreal-engine)

버튼 한 번은 클릭/시작 이벤트에서 한 요청으로 변환한다. 매 프레임 Triggered에 구매를 연결하지 않는다. 터치와 마우스가 동일 동작을 두 번 제출하지 않게 공통 의도 함수로 모은다. UMG가 처리한 터치는 뒤 전장으로 다시 전달하지 않는다. 이 입력 제어는 서버 검증을 대체하지 않는다.

**검증:** QA-CMD-01, QA-NET-03/04/07/09/10. 같은 요청 20회·같은 키 내용 변경·캐시 퇴출·UI 재생성·새 연결을 각각 구분해 기록한다. 서버 미준비와 네트워크 대기는 실패/환불과 구분한다.

**A에게 전달:** 서버 초기화/종료 API, 참가자 문맥 요구, 응답 완료 연결, 단계별 오류·로그 형식.

## 6. B-03 — 경제와 배치를 함께 확정하는 첫 소환

DEC-037의 뭉치 규칙을 첫 소환 단계에 포함한다. 여유 뭉치 우선 추가 → 모두 3마리이면 새 뭉치이며, 기존 뭉치에 추가한 경우에도 개체 수는 1 증가한다. 동시 요청은 확정 직전에 수용량을 재검증해 4마리 뭉치가 생기지 않게 한다. 복수 여유 뭉치 선택과 빈칸 없는 무작위 소환 정책은 확정 전 임의 구현하지 않는다.

**완료할 동작:** 성공 시 재화·보드·RNG가 함께 바뀌고, 어느 준비 단계든 실패하면 모두 원래 상태를 유지한다.

1. EconomyService의 개인 원본을 private으로 보관한다. 재화·소환 횟수·확률 단계·강화·EconomyRevision·참가자별 RNG를 한 참가자 상태로 관리하고 const 조회 또는 값 스냅샷을 제공한다.
2. 비용·프로파일·확률 단계·추첨·다음 상태 계산을 화면/월드 없는 함수로 분리한다. 준비에는 원본 RNG의 복사본을 사용한다.
3. BoardManager는 동일 소유자·동일 UnitId의 여유 뭉치(최대 3)를 먼저 찾고, 없으면 새 뭉치 셀을 준비한다. 기존 뭉치 추가/새 뭉치 생성 구분을 변경안에 기록하고 임시 생성·취소·확정을 구현한다. 이동/합성 전체가 아직 없어도 첫 소환이 보드의 공식 변경 경로를 사용하게 한다.
4. CommandProcessor가 경제 변경안과 보드 변경안을 함께 보유한다. 액터 스폰·필수 에셋·초기화는 확정 전에 준비하고, A의 준비 액터는 비활성 상태를 유지한다.
5. 최종 재검증 뒤 명세대로 상태를 공동 확정하고 그 뒤에만 복제 스냅샷·결과·보드 통지·연출을 게시한다.
6. 거절 이유는 명시적으로 반환하고 성공 응답을 받았다고 클라이언트에서 재화 차감·액터 생성을 다시 하지 않는다.

**내부 API 설계 예시** — 반환형·변경안 필드는 실제 구현 때 정의할 초안이다. `Plan`은 임시 값이며 외부 위젯/Controller에 노출하지 않는다.

| 제공자 | 제안 함수 | 의미 |
|---|---|---|
| EconomyService | `TryPrepareSummon(Context, Rules, OutPlan)` | 경제 원본과 RNG를 바꾸지 않고 다음 값을 계산 |
| BoardManager | `TryPreparePlacement(Context, SummonPlan, OutPlan)` | 원본 보드를 바꾸지 않고 배치·액터를 준비 |
| 두 기능 각각 | `ValidatePrepared(Plan)` | 준비 당시 원본/Revision과 현재 상태를 재검증 |
| 두 기능 각각 | `CommitPrepared(Plan)` | CommandProcessor의 공동 확정 구간에서 검증된 값 반영 |
| BoardManager | `CancelPrepared(Plan)` | 임시 액터·예약 정리. 반복 취소 안전 |
| CommandProcessor | 확정 후 게시 경로 | 두 원본 확정이 끝난 뒤 알림·응답·복제 값 게시 |

```text
소환 의도 → Controller 요청 추적 → Server RPC → CommandProcessor
  → 요청/연결/중복/모드 검사
  → 추첨 전 인구/가능결과 수용 검사 → 경제 변경안 준비 → 보드·비활성 액터 준비
  → 실패: 준비물 취소, 경제·보드·RNG·Revision 불변
  → 성공: 재검증 → 공동 확정 → 복제·응답·보드 변경 통지
```

준비/확정 함수는 EconomyService↔BoardManager를 직접 호출하지 않는다. 확정 구간에 에셋 로딩·Blueprint 이벤트·delegate·외부 I/O를 넣지 않는다. 후반 확정이 실패할 수밖에 없는 구현이라면 전체 복구와 실패 주입 검증을 먼저 설계한다.

**최소 UI:** `/Game/LD/UI/Battle/WBP_SummonButton`에서 OnClicked→Controller의 소환 의도 함수만 호출한다. 가격·잔액·대기는 서버에서 게시한 현재 표시값과 로컬 요청 상태로 보여 준다. 전체 HUD 통합은 B-05지만 이 버튼으로 첫 소환 통합을 먼저 검증한다.

**검증:** 확인된 비용/확률 경계, 자원 부족·배치 불가·액터 준비 실패·최종 재검증 실패·같은 키 반복. 실패마다 재화·보드 목록·RNG·두 Revision·전투 등록 수·성공 이벤트 수를 전후 비교한다. QA-RNG-05·QA-ECO-01·QA-BOARD-01·QA-NET-03 및 ARCH-06의 실패 주입 기준을 적용한다. 기존 숫자 예시는 초안 데이터 검사와 원작 검증을 구분한다.

**A에게 전달:** 확정 유닛 조회·OnBoardCommitted·UnitActor 사용 방식·실패 시 무등록 증거.

## 7. B-04 — 이동·합성·판매와 전투 보상

### 7.1 보드 명령 확장

같은 명령 처리·준비·공동 확정 경로에 기능을 추가한다. 기능별 버튼에서 별도의 상태 변경 경로를 만들지 않는다.

| 동작 | 서버가 확인할 것 | 확정 후 A에게 전달할 것 |
|---|---|---|
| 이동·스택 | 현재 소유/위치·목적지·수용량·확인된 이동 단위/제약 | 같은 InstanceId의 위치 변경. 공격 쿨다운 임의 초기화 없음 |
| 합성 | 서로 다른 3개 ID·동일 소유/UnitId·선택 ID 포함·모드 등급·결과 공간 | 소비 ID 제거와 새 ID/결과 배치. 한 공동 변경의 결과 |
| 판매 | 지정 개체 존재·소유·확인된 판매 조건과 서버 환급 | 해당 ID 제거·갱신된 경제/보드 Revision |

소비 ID 목록은 내용 비교용으로 정규화하되 중복 ID 세 개를 한 개로 정리해 승인하지 않는다. SelectedInstanceId가 결과 기준이며 정렬 첫 번째 ID로 대체하지 않는다. 재료가 사라졌으면 다른 유닛을 자동으로 골라 소비하지 않는다.

이동 중 표시만 임시 위치를 사용할 수 있다. 원본 보드는 서버 확정 전 바꾸지 않고, 취소/거절이면 복제 원본으로 표시를 복원한다. Single 이동은 허용하지 않는다. 잠금·표적 토글·재료 교환의 예약 payload는 별도 채택 전 제품 기능으로 활성화하지 않는다.

### 7.2 A의 처치 결과를 경제 보상으로 반영

`EnqueueCombatReward`는 서버 내부 진입점이다. A가 전달한 MatchId·DeathEventId·적 종류/사망 사실과 서버 규칙으로 수혜자·보상량을 결정한다. 동일 보상을 참가자별로 한 번만 반영하고 소환·판매와 같은 참가자 직렬 처리 순서에 넣는다.

내부 보상은 클라이언트 RequestId를 소비하거나 사용자 RPC로 요청하지 않는다. 전투 결과를 수신하는 delegate 안에서 진행 중인 경제 트랜잭션에 재진입하지 않는다. 최종 처치/웨이브 보상과 종료 순서는 [공통 수명 계약](IMPLEMENTATION_SHARED.md#lifecycle)을 따른다.

**Unreal 연결:** 선택·합성·판매 위젯은 같은 Controller 의도 진입점을 사용한다. 합성/소환 VFX는 확정된 EventId 기준으로 한 번 재생하며 연출 완료 콜백에서 소비·보상을 수행하지 않는다. A의 UnitActor 그래프를 편집해 보드 상태를 따로 보관하지 않는다.

**검증:** QA-BOARD-02/03/04/05/06/07/08, QA-CMD-02의 확인된 기능, QA-ECO-03/04. 가득 찬 보드·소비 후 공간·합성/판매 경쟁·상대 소유·소환과 처치 보상 동시 발생·Result 뒤 통지를 검사한다.

**A에게 전달:** 생성/갱신/제거 델타 구분, 이동 중 전투 제약 입력, 보상 중복 결과와 전후 잔액 로그.

## 8. B-05 — HUD·복제 상태·터치 조작 통합

HUD 슬롯은 [현재 v2 명세](../design/BOARD_UI.md#ingame-ui-v2)의 상단 전투 정보 → 전장 → 선택/상태 → 자원 → 하단 행동 배치를 따른다. 사각형·텍스트를 개별 위젯으로 구성하고 전체 화면 PNG를 UI로 사용하지 않는다. 보스 HP/시간은 예약 영역에, 선택 시 합성·판매는 전장 아래에 표시한다. Figma의 사거리 사각형은 자리표시자이며 실제 사거리 원의 판정값으로 사용하지 않는다. P0에서 후속 버튼은 숨기고 게임 규칙의 수치와 도안 예시 숫자를 구분한다.

자기 뭉치를 클릭/탭하면 합성·판매 버튼과 사거리 원을 표시한다. A가 제공한 실제 전투 사거리·기준 위치를 사용하고 화면마다 반경을 임의 계산하지 않는다. 수량/선택/대상 생존 변화에 맞춰 버튼 상태·범위를 갱신하며 해제 시 이전 UI를 정리한다. 합성 조건·판매 단위/보상은 각각의 확정 규칙을 따른다. QA-BOARD-11~13으로 확인한다.

**완료할 동작:** 서버 결과가 늦거나 순서가 바뀌어 도착해도 화면이 원본 상태로 수렴하고, 터치만으로 P0 조작을 끝낼 수 있다.

1. `/Game/LD/UI/Battle/WBP_HUD`를 구성하고 A의 WBP_BattleStatus·WBP_Result를 합의한 슬롯에 넣는다. B는 HUD 구성과 로컬 연결을, A는 자기 위젯 내부를 담당한다.
2. 소유 로컬 Controller가 HUD를 만들고 현재 복제 상태와 요청 상태를 전달한다. 초기 스냅샷→변경 알림 순서로 연결하고 화면 제거 시 구독을 해제한다.
3. 개인 경제는 Controller 소유자용 복제 스냅샷, 공개 요약은 PlayerState, 배치는 BoardManager, 전투는 GameState/전투 액터에서 읽는다. 복제된 경제 값을 서버 원본으로 역복원하지 않는다.
4. 성공 응답의 NewBoardRevision과 EconomyRevision 이상을 각각 관찰해야 요청 표시를 확정 완료로 바꾼다. 액터 참조가 아직 없으면 ID 기준으로 기다리고 직접 액터를 생성하지 않는다.
5. 오래된 응답이 최신 화면을 되돌리지 않게 한다. RequestExpired는 응답 기준 이상 상태 동기화 뒤 사용자 재선택을 안내하며 새 번호로 자동 실행하지 않는다.
6. 드래그 화면 이탈·두 번째 터치·UI 위 입력·취소·백그라운드 복귀를 처리한다. 입력 취소와 이미 서버에 제출한 명령의 취소를 구분한다.

**Unreal 설정과 연결**

| 항목 | 설정/연결할 내용 | 확인할 결과 |
|---|---|---|
| HUD 루트 | SafeArea, 앵커·크기·DPI 기준 | 노치/하단 시스템 영역과 버튼이 겹치지 않음 |
| 경제·선택 패널 | 잔액·비용·선택 ID의 표시 모델 | 다른 참가자의 개인 상태가 잘못 표시되지 않음 |
| 대기·거절 상태 | 제출 중 중복 입력 제한·실패 이유·재선택 | Pending을 환불/실패로 표시하지 않음 |
| 전투·결과 슬롯 | A 위젯의 입력/해제 계약 | 늦은 생성·재생성·종료 반복에 안전 |
| P0 안내·버튼 | 소환·선택·합성·이동·판매·결과 복귀 | P1/미확인 기능 숨김, 키보드 없이 수행 |
| 입력 소비 | UMG 처리 여부와 전장 입력 경로 | UI 터치가 뒤 칸의 명령으로 중복 전달되지 않음 |

**검증:** QA-MOB-01/04·QA-VIS-02/03, QA-NET-03/05/10, ARCH-06의 역순 복제·UI 수명 사례. 응답→경제→보드, 보드→응답→경제 등 서로 다른 순서와 위젯 재생성을 검사한다. 클라이언트 초기 상태와 리슨 서버 호스트 양쪽에서 확인한다.

**A에게 전달:** HUD 슬롯·소유/구독 수명, 위젯 입력/해제 안내, 좁은 화면 캡처·전투 UI 오류 재현.

## 9. B-06 — PC 2인·지연·실패 검수 주관

빠른 반복은 PIE의 Number of Players=2, Play As Listen Server로 시작한다. 이어서 실제 패키징 두 프로세스 또는 두 장치에서 접속·상태·종료를 확인한다. 단일 프로세스 PIE의 공유 환경만 확인하고 완료하지 않는다. [Epic PIE Multiplayer Options](https://dev.epicgames.com/documentation/unreal-engine/play-in-editor-multiplayer-options-in-unreal-engine)

빌드 명령·패키지 위치·입력 보존은 [BUILD_RUN](BUILD_RUN.md)을 따른다. 기본 빌드 스크립트의 대상 맵과 통합 전투 맵을 대조하고 실제 실행 맵을 로그에 남긴다. 접속 방식·포트·서버/클라이언트 구성을 기록하며 P0 로컬 접속 검증을 P2 계정/매칭 서비스 검증으로 확대하지 않는다.

| 검사 묶음 | 재현 내용 | 남길 증거 |
|---|---|---|
| 기본 통합 | 소환→전투→보상→이동/합성/판매→결과 | 두 프로세스의 최종 상태·참가자·개체 ID·Revision |
| 지연·손실 | QA-NET-01/02의 RTT·손실 조건 | 적용 설정·실측/확인한 네트워크 조건·반복 조작 결과 |
| 중복·내용 충돌 | 같은 요청 반복·같은 키 다른 내용·퇴출된 요청 | 요청 키·결과 코드·소비/추첨 횟수·최종 원본 |
| 실패 주입 | 액터 준비 실패·재검증 실패·재료 소멸 | 경제·보드·RNG·Revision 불변과 준비물 정리 |
| 수명·종료 | UI 재생성·Controller 연결 세대 변경·Result 후 지연 응답 | 중복 구독/소비 없음·최신 상태 복구·종료 오류 없음 |
| P0 경계 | 과밀·보스 마감·최종 잔여 적·11웨이브 미생성 | A와 함께 판정 원인·시각·최종 보상/결과 확인 |

RTT와 엔진 패킷 지연 설정의 값이 같다고 가정하지 말고 적용 항목·실제 조건을 함께 남긴다. 콘솔 설정은 [콘솔 안내](UNREAL_CONSOLE_COMMANDS.md)와 사용 엔진의 도움말로 확인한다. 검수 주관 B는 재현·증거를 정리하고 전투/웨이브 오류는 A가 수정한다. Android 최종 검수에는 B도 참여해 터치/UI 문제를 담당한다.

## 10. 역할별 제출 기준

각 단계에 [공통 제출 기록](IMPLEMENTATION_SHARED.md#delivery)을 남긴다. 입력과 그래프에서 요청의 시작점·서버 검증·원본 변경·복제 표시까지 연결해 설명한다.

| 관찰된 문제 | B가 먼저 볼 곳 | A와 함께 볼 경계 |
|---|---|---|
| 버튼이 반응하지 않음 | 로컬 입력·컨텍스트·대기 상태·Server RPC 소유 | 서버 준비·참가자 연결·Phase |
| 재화만 줄고 유닛이 없음 | 공동 확정·준비 실패·보드/액터 복제 도착 | UnitActor 초기화·표시 활성·전투 등록 |
| 합성이 두 번 되거나 유닛이 손실됨 | 요청 키·처리 큐·소비 목록·Revision 재검증 | 제거/생성 통지 후 전투 목록 |
| 같은 버튼에서 전장도 눌림 | UMG 입력 소비·마우스/터치 중복 경로 | 전투 입력과 무관한 로컬 표시 처리 |
| 위젯을 열면 대기가 사라짐 | Controller 요청 수명·초기 스냅샷·중복 구독 | A 위젯의 초기 표시·해제 |

**B의 P0 제출 체크**

- [ ] 확인된 규칙으로 보드·경제를 구현하고 미확인 기능을 활성화하지 않았다.
- [ ] 요청 키·내용 충돌·캐시 퇴출·연결 세대·새 요청 거절이 구분된다.
- [ ] 실패 시 경제·보드·RNG·Revision이 모두 보존되고 임시 액터가 정리된다.
- [ ] 확정 배치가 A의 전투에 반영되고 처치 보상이 같은 경제 처리 순서로 들어온다.
- [ ] 응답과 복제의 도착 순서·화면 재생성에도 상태가 일치한다.
- [ ] PC 패키징 2인·지연 검수와 A 주관 Android 터치 검수에 참여했다.
- [ ] 코드·에셋·설정·정상/실패 입력과 실제 결과를 단계별로 연결했다.

## 11. P1 이후 이어갈 구현

**미션 화면 — DEC-042:** TASK-UI-02는 [현재 미션 UI](../design/BOARD_UI.md#mission-ui)의 전투 메뉴 진입·960×880px 패널·수집/수량형 목록·보상/상태·스크롤·닫기를 개별 위젯으로 구현한다. 화면 상태는 실제 미션 데이터에서 읽고 예시 5칸/목표 3/진척 숫자를 로직에 고정하지 않는다. 보상 지급·집계·반복 정책은 TASK-ECON-02에서 확인된 계약과 연결하며 위젯 수명이나 완료 배지로 지급을 결정하지 않는다. 재진입 시 최신 상태 표시·상단 전투 정보 보존·UI 입력 소비를 QA-VIS-02/QA-MOB-04로 검사한다.

**채택 화면 — DEC-041:** [신화·강화·룰렛·설정 패널](../design/BOARD_UI.md#ingame-ui-panels)의 개별 요소를 위젯으로 구성한다. 신화의 목록/재료·소환 상태, 강화 4항목, 룰렛 3등급/확률·보정·결과, 설정의 토글·슬라이더·30/60FPS·복귀를 각각 연결한다. 패널 위치/크기와 상단 정보 보존은 기준 도안을 따르고 다른 화면비에서는 SafeArea·터치 크기를 검수한다. 비용/확률/설정 초기값은 확인된 데이터에서 읽으며 도안 예시값을 로직에 하드코딩하지 않는다. TASK-UI-02·TASK-UX-01/SAVE-01의 진입·닫기·재진입·대기/부족·설정 유지와 UI 입력 소비를 검사한다.

P0 이후 TASK-ECON-02의 확인된 도전·신화 제작·강화와 TASK-UI-02의 패널을 같은 명령/공동 확정 경로로 확장한다. 미확인 재료 교환은 백로그에 있다는 이유만으로 구현하지 않는다. TASK-DATA-02의 경제 데이터는 B가 작성하고 A가 구조·로딩·검증을 주관한다.

강화 확정값을 A의 전투 계산으로 전달할 읽기 전용 스냅샷/변경 통지를 먼저 합의한다. UI나 전투가 EconomyService 내부를 직접 수정하는 API를 추가하지 않는다. 보조 봇·튜토리얼·저장·아트·P2는 기존 미배정 상태를 유지하며 P0 공수와 학습 목표를 확인해 별도 배정한다. B에게 전체 통합·QA·아트 작업을 자동으로 추가하지 않는다.

단계별 후속 범위와 촬영 기능 후보는 [로드맵](../production/ROADMAP.md#phase-plan)을 따른다. P1/P2에서도 각자 보드 순환·해상도 독립 판정·N ≥ M 즉시 패배·10배수 보스/시간초과를 회귀한다. 신규 후보의 상위 TASK 연결은 구현 완료나 역할 추가 배정을 뜻하지 않는다.
