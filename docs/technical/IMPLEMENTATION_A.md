# 개발자 A 구현 설계 — 전투·웨이브

**현행 규칙:** [P0 재기획](../design/P0_REPLAN.md)의 DEC-043~047을 따른다. P0 16종·100/20·보스2/60초, P1 80웨이브·사냥/미션/던전·보물/유물/펫 실제 시스템. 고유 콘텐츠는 컨셉 후 결정하며 기존 날짜/공수는 재산정 대상이다.

**초기화 후 상태:** 기존 P0 구현과 학습 자료는 삭제됐다. 이 문서는 새로 작성할 기능의 설계이며 구현 완료본이 아니다. [초기화 내역](../production/P0_RESET.md).

**새 착수 기준(2026-09-16):** [촬영본 기반 P0 재기획](../design/P0_REPLAN.md)의 G0~G4와 PLAN 검수를 먼저 적용한다. 종전 12칸/치수/경제 수치에 대한 통과는 기존 프로토타입 결과다. 새 레이아웃은 확정된 Rows×Columns 전체를 검사하고 원작 조작 근거를 연결한다. 이번 개정은 게임 데이터·코드나 기존 실행 결과를 바꾸지 않는다.

[공통 구현 계약](IMPLEMENTATION_SHARED.md) · [B 구현 설계](IMPLEMENTATION_B.md) · [역할 분담](../production/TEAM_ROLES.md) · [초기 설정](../GETTING_STARTED.md#setup)

**P0~P2 실행 순서·주별 일정·산출물:** [A 개발 문서](../production/DEVELOPMENT_A.md). 이 구현 설계는 P0의 클래스·API·Unreal 설정 상세를 담당하며 전체 범위/마감은 [개발 계획서](../production/DEVELOPMENT_PLAN.md)를 따른다.

## 1. 내가 완성해야 할 결과

**B가 소환·배치한 유닛이 적과 싸우고, 한 번의 처치가 한 번의 보상으로 연결되며, 웨이브와 승패가 두 화면에서 일치하게 만든다.** 전투 정보·결과 UI와 Android 전투 빌드 검수도 A가 맡는다.

이 문서는 개발자 A가 실제 작성할 순서로 구성한 설계다. C++·Blueprint·설정은 구현 예정이며, 현재 해당 코드나 에셋이 완성됐다는 뜻이 아니다. 제안 API는 [공통 계약](IMPLEMENTATION_SHARED.md#contracts)에 모았다. 클래스 책임은 [아키텍처](ARCHITECTURE.md), 데이터 필드는 [DATA_SCHEMA](../DATA_SCHEMA.md)가 원본이다.

P0는 일반~전설 각 4종의 기본 공격·능력치, 10웨이브, 보스 1종과 짧은 안내까지다. 보스 1종은 종류 수이며 등장 개체 수는 해당 웨이브 명세를 따른다. 강화·고유 스킬·정식 튜토리얼은 P1이다. 수치·표적 규칙·이동 중 공격 조건은 [원작 대조](../product/ORIGINAL_REFERENCE.md)에서 확인한 범위를 적용한다. 미확인 수치는 계산 테스트의 초안 입력으로 구분하고 원작 재현 완료로 판정하지 않는다.

소스 경로는 `Source/Mobile_defense_clone/` 기준이다. 필요한 파일을 해당 단계에서 만든다. 기존 TopDown·Strategy·TwinStick Controller를 상속해 디펜스 규칙을 추가하지 않는다.

## 4. A-01 — 데이터를 읽는 최소 경로 만들기

**완료할 동작:** 존재하는 유닛 ID를 조회하면 검증된 행을 받고, 없는 ID·필수 데이터 누락은 구체적인 오류가 된다.

1. DATA_SCHEMA와 `data/README.md`를 대조해 필요한 Row Struct부터 작성한다. RowName인 `Name`을 UPROPERTY로 다시 만들지 않는다. FName 필드를 임의 enum으로 바꿔 JSON 임포트를 깨뜨리지 않는다.
2. 같은 모듈에 필요한 타입을 추가하고 Editor를 빌드한다. 필드/상속/리플렉션 변경은 에디터를 닫고 전체 Editor 빌드로 확인한다.
3. Content Browser의 `/Game/LD/Data/`에 DataTable을 생성/임포트하고 해당 Row Struct를 선택한다. GameRules.json은 DataTable과 같은 방법으로 자동 적용된다고 가정하지 않는다. 기존 명세의 별도 로더/DA_GameRules 경로를 구현한다.
4. 매치 시작 시 P0 규칙을 고정해 GameMode가 보관하고 하위 기능에 읽기 전용으로 전달한다. 전투 도중 원본 DataTable을 편집해도 실행 중 규칙을 바꾸지 않는다.
5. 16종 허용·기본 공격만 활성화·강화 레벨 0을 코드에서 확인한다. SkillId가 존재한다는 이유로 스킬 실행기를 켜지 않는다.

제안 조회 형태는 `bool TryGetUnitRow(FName UnitId, FLDUnitRow& OutRow) const`다. 규칙 로더의 오류에는 파일/에셋·행 ID·필드·원인을 포함한다. 필수 ID 누락은 기본 유닛으로 대체해 매치를 계속하지 않는다.

**검증:** 정상 행, 없는 UnitId, 잘못된 참조, P0 제외 등급, P1 SkillId 존재 시 실행 비활성. 관련 기준은 TASK-DATA-01·QA-RNG-01이며 확률 수치 자체는 확인된 프로파일을 사용한다.

**B에게 전달:** Row Struct 헤더, 실제 DataTable/규칙 에셋 경로, 로딩 API, P0 제한 항목, 정상/실패 입력 예시.

## 5. A-02 — 서버 매치와 공용 상태 연결하기

**완료할 동작:** 두 플레이어가 같은 매치 상태를 받고, 서버 준비 전에는 게임 변경 요청이 실행되지 않는다.

1. GameModeBase/GameStateBase 계열과 PlayerState를 작성한다. Phase는 게임의 Loading·Preparing·Running·Result·Aborted를 표현하는 enum으로 두고 전이는 GameMode의 한 경로로 모은다. AGameMode의 내장 MatchState를 그대로 제공받는다고 가정하지 않는다.
2. [공통 초기화 순서](IMPLEMENTATION_SHARED.md#lifecycle)에 따라 B의 서비스를 생성하고 UPROPERTY 참조로 보관한다. 준비 상태를 검사하는 초기화 함수는 여러 번 불려도 중복 구독·등록을 하지 않는다.
3. 참가자 등록 경로에서 서버가 PlayerIndex와 연결 문맥을 정하고 B의 Controller에 명령 처리 대상을 연결한다. 먼저 접속하고 데이터는 나중에 준비되는 경우도 처리한다.
4. GameState에 WaveIndex·Phase·WaveEndTime·ActiveEnemyCount·MaxEnemyCount·BossDeadline·Result·보스 요약(설계 계약, 실제 타입 적용 검수 필요)을 게시한다. PlayerState에는 개인 경제의 공개 요약만 게시하며 RNG·개인 경제 원본을 넣지 않는다.
5. Result/Aborted 전이는 같은 원인·반복 콜백으로 중복 결과를 생성하지 않게 한다. 종료 시 스폰·전투·delegate·준비 작업을 함께 정리한다.

**Unreal 연결:** `/Game/LD/Core/BP_GameMode`의 부모를 ALDGameMode, BP_GameState의 부모를 ALDGameState로 만든다. BP_GameMode의 Game State Class·Player State Class에 A의 클래스를, Player Controller Class·Default Pawn Class에는 준비된 B의 Controller·CameraPawn을 연결한다. 테스트 맵 World Settings의 GameMode Override로 적용하고 실제 생성 클래스 이름을 로그로 확인한다.

GameMode는 서버에만 존재하므로 A의 위젯도 GameState를 읽는다. PostLogin은 PlayerController의 복제 함수 호출이 가능한 첫 지점이며, 여기서도 별도의 데이터/서비스 준비 조건을 확인한다. [Epic Game Mode and Game State](https://dev.epicgames.com/documentation/unreal-engine/game-mode-and-game-state-in-unreal-engine)

**검증:** 접속 순서 변경·필수 데이터 누락·중복 초기화·종료 직후 콜백, 두 클라이언트 공용 상태 일치. B의 명령 준비가 미완료라면 비활성 이유가 명시돼야 한다.

**B에게 전달:** 매치/참가자 문맥과 초기화 완료 조건, GameMode 에셋, 복제 항목·변경 알림, 종료 호출 순서.

## 6. A-03 — B의 소환 결과를 전투에 등록하기

DEC-037: 기존 뭉치에 추가되는 소환도 새 InstanceId의 개체 1개를 생성·등록한다. 이미 있는 1~2개의 개체·공격 타이머를 교체하거나 초기화하지 않는다. B의 선택 UI가 사용할 실제 RangeCm·사거리 기준 위치를 제공해 표시 원과 전투 판정이 일치하게 한다. 뭉치는 선택/배치 단위이며 가짜 공격력 배수로 대체하지 않는다.

**완료할 동작:** 성공한 소환만 전투에 참여하고, 취소된 준비 액터·판매/합성으로 제거된 유닛은 공격하지 않는다.

A는 준비·확정 API와 비활성 UnitActor를 먼저 만들어 B에게 넘긴다. B-03 완성을 기다렸다가 UnitActor 작성을 시작하지 않는다. 각자 준비/실패 경로를 검사한 뒤 실제 소환과 전투 등록을 함께 검수한다.

1. UnitActor에 InstanceId·UnitId·소유·칸의 파생 상태를 둔다. 준비/활성/제거 상태를 구분하고 준비 상태에서는 전투 등록·충돌·복제·VFX를 비활성화한다.
2. `InitializePrepared`에서 검증된 행·배치·Transform을 받는다. BeginPlay·Construction Script·초기화 콜백에서 자동 전투 등록을 하지 않는다.
3. B가 공동 확정한 뒤 `ApplyCommittedPlacement`와 보드 통지를 사용한다. GameMode의 연결부가 `TryGetCommittedUnitActor`로 액터를 확인하고 BattleSubsystem에 등록한다.
4. 같은 ID 재등록은 공격 준비 시간을 초기화하지 않는다. 이동은 기존 유닛을 유지하고 위치/이동 제약만 반영한다. 확인된 이동 제한과 공격 준비 시각의 관계를 명세와 대조한다.
5. 제거 통지에서 전투 목록·표적 관련 예약을 정리한다. EndPlay가 다시 와도 안전해야 한다. 유닛 제거를 EnemyActor 사망 보상으로 연결하지 않는다.

**Unreal 연결:** `/Game/LD/Units/Base/BP_UnitBase`의 부모는 ALDUnitActor다. 메시·머티리얼·애니메이션·VisualId 연결을 담당한다. 준비 액터의 복제/충돌은 C++ 수명 경로가 제어한다. Blueprint에서 임의로 항상 활성화하거나 BeginPlay에 자동 공격 노드를 넣지 않는다. 표시 에셋 누락과 규칙 데이터 누락을 구분해 처리한다.

**검증:** 소환 성공 1회→전투 등록 1회, 생성 준비 실패→등록 0회, 이동→동일 ID·쿨다운 유지, 판매/합성→제거된 개체의 추가 공격 0회. `OnBoardCommitted` 재전달도 확인한다.

**B에게 전달:** UnitActor의 준비·확정·제거 사용법, 사용할 BP 클래스, 필수 초기화 값, 실패 조건.

<a id="a04"></a>

## 7. A-04 — 적 이동·공격·피해·사망 구현하기

**완료할 동작:** 서버가 유효한 적을 선택해 기본 피해를 적용하고, 양쪽 공격이 겹쳐도 사망과 적 수 감소가 한 번만 발생한다.

1. EnemyActor에 EnemyId·SpawnSerial·HP·경로 상태를 초기화한다. 서버가 스폰하고 초기 데이터가 유효해진 뒤 전투에 등록한다. 적은 아군 유닛에 피해를 주지 않는다.
2. DEC-030의 RouteIndex(0=Lower, 1=Upper)를 생성 시 정하고 해당 닫힌 경로를 서버에서 이동한다. DEC-033에 따라 중앙 이후에도 생성 시 RouteIndex를 유지하여 자기 생성 보드 둘레로 복귀·반복한다. 두 그룹 각각 2바퀴 동안 경로 전환·적 중복 생성이 없는지 확인한다. 두 경로의 중앙 구간은 같은 방향이며 생성 그룹으로 표적 소유권을 제한하지 않는다. 경로 끝을 넘어도 진행 방향이 유지되도록 누적 거리와 표시용 나머지 거리를 구분한다. 클라이언트 보간에 쓰는 샘플 시각·경로 값의 출처를 한곳으로 정한다.
3. BattleSubsystem은 서버 권한에서만 논리 스텝을 진행한다. 각 액터 Tick·타이머·AnimNotify가 별도로 피해를 계산하지 않게 한다. 논리 주기와 이벤트 순서는 전투 명세를 따른다.
4. 표적 선택·피해량 계산은 명시적 입력/출력 함수로 분리한다. 후보의 생존·거리·타이브레이크를 확인하고 피해 적용 직전에 다시 유효성을 검사한다.
5. 살아 있음→사망을 EnemyActor의 단일 처리 경로로 확정한다. HP 변경·사망 등록·적 수 갱신과 `FLDCombatDeath` 생성이 반복 호출에 안전해야 한다.
6. GameMode 연결부가 처치 사실을 B의 `EnqueueCombatReward`로 전달한다. A는 보상량을 임의 지급하지 않는다. P0의 고유 스킬·상태이상은 실행하지 않는다.

순수 함수의 시작 예시는 `SelectTarget(UnitSnapshot, EnemySnapshots, Rules)`와 `CalculateBasicDamage(AttackInput, DefenseInput)`다. 이름은 설계 예시이며 실제 결과 타입과 로그는 첫 구현에서 정한다. 계산 함수가 GetWorld나 에셋 경로를 알아야 한다면 입력 분리가 충분한지 다시 확인한다.

**Unreal 연결:** `/Game/LD/Enemies/Base/BP_EnemyBase`에서 메시와 피격/사망 표현을 연결한다. 서버 HP/시각 이벤트에 따라 표시하며 AnimNotify·시각 투사체 충돌로 추가 피해를 주지 않는다. 적 경로 표시를 자체 복제 값으로 보간할 경우 Replicate Movement와 동시에 위치를 덮어쓰지 않도록 이동 표시 경로를 하나로 정한다.

**검증:** 거리 경계·동률 후보·한 대상 동시 공격·사망 대상 재타격·경로 순환·VFX 누락. QA-DMG-01/02·QA-ECO-03·QA-WAVE-04·QA-NET-05/06을 관련 프로파일로 적용한다. P1 강화가 필요한 피해 예시는 계산 함수 검사로 구분하고 P0 인게임에 강화 기능을 켜서 검사하지 않는다.

**B에게 전달:** 처치 결과 구조·중복 식별 기준, 전투 등록 목록을 확인할 로그, 배치 변경 후 기대 동작.

## 8. A-05 — 한 웨이브부터 10웨이브와 승패까지

**완료할 동작:** 서버 시간에 맞춰 웨이브가 진행되고 마감·동시 사망·반복 콜백에도 결과가 한 번만 확정된다.

1. WaveDirector가 읽기 전용 웨이브 데이터를 스폰 예약으로 변환한다. 먼저 한 웨이브 테스트 데이터로 시작하고 임시 데이터임을 표시한다.
2. 예약 시각과 실제 실행 시각을 구분한다. 지연된 프레임에서 마감 이전/이후 예약을 한꺼번에 같은 결과로 처리하지 않는다.
3. [전투 명세 5.4](../design/BATTLE.md)의 스텝/웨이브 경계 순서를 적용한다. 같은 마감 시각의 피해·사망을 먼저 처리하고, 이전 웨이브 판정·보상 후 계속 진행할 때 다음 웨이브를 스폰한다.
4. DEC-034: 집계 대상 생존 수 N이 최대 수 M에 도달하는 증가 이벤트에서 즉시 패배를 검사한다(N ≥ M). 3초 지속/해제 타이머는 사용하지 않는다. 10배수 웨이브 보스를 예약하고 제한 시각에 필수 보스가 살아 있으면 패배한다. 모든 종료 원인은 단일 결과 확정 경로로 모으며 M·제한 초수·집계 대상은 출처가 있는 규칙 데이터로 받는다.
5. P0 FinalWave=10에서 종료하고 11웨이브를 만들지 않는다. 최종 내부 보상 처리와 Result 게시 순서는 공통 계약을 따른다.

**Unreal 연결:** `/Game/LD/Battle/BP_WaveDirector`는 ALDWaveDirector의 데이터·클래스 연결용 BP로 사용할 수 있다. GameMode에 연결한 WaveDirector 클래스가 서버에서 한 번만 생성되게 한다. 맵 배치와 GameMode 스폰을 동시에 사용하지 않는다. 적/보스 클래스·웨이브 테이블·B의 경로/스폰 위치가 모두 연결됐는지 시작 전에 검증한다.

**검증:** 마감 시각에 마지막 보스 사망, 마감 이후 예약 타격, 보스 생존 마감, 최종 일반 적 잔여, N=M-1/M/M+1·상한 도달 뒤 같은 스텝의 처치·10배수 보스 주기, Result 후 타이머 재호출. QA-TIME-01~07의 해당 조건을 P0 최종 10웨이브로 적용한다. 준비/강제 스폰 픽스처는 일반 플레이와 구분한다.

**B에게 전달:** 웨이브·시간·적 수·보스·결과 표시값, 종료 후 허용 입력, 결과/보상 중복 확인 로그.

## 9. A-06 — 전투 정보와 결과 UI 연결하기

1. `/Game/LD/UI/Battle/WBP_BattleStatus`와 `/Game/LD/UI/Result/WBP_Result`를 만든다. A는 위젯 내부를, B는 WBP_HUD의 삽입·로컬 수명을 맡는다.

3. 초기 연결 때 현재 상태를 즉시 표시하고 이후 변경 알림으로 갱신한다. 카운트다운 표시만 로컬에서 갱신하되 서버와 맞춘 시간 기준을 사용한다. 위젯 타이머가 웨이브를 끝내지 않는다.

5. 최종 결과·보스 요약이 관련 액터보다 늦거나 먼저 도착해도 임시 대기/빈 상태를 표시한다. 접근 불가능한 액터를 강제로 역참조하지 않는다.

**검증:** 늦은 HUD 생성, 화면 재생성, Result 중복 통지, 양쪽 표시 일치, 좁은 화면비. QA-VIS-02·QA-NET-05·QA-MOB-04를 B와 함께 수행한다.

**B에게 전달:** 위젯 에셋 경로, 입력 항목·갱신/해제 방법, 결과 복귀 이벤트와 정상 화면 캡처.

## 11. 역할별 제출 기준

각 단계는 [공통 제출 형식](IMPLEMENTATION_SHARED.md#delivery)에 맞춰 코드와 에디터 설정을 함께 남긴다. C++ 설명에는 호출 시작점·권한·상태 원본·수명, Unreal 설명에는 부모 클래스·에셋 참조·설정값과 실제 화면을 포함한다.

| 관찰된 문제 | A가 먼저 볼 곳 | B와 함께 볼 경계 |
|---|---|---|
| 유닛은 보이지만 공격하지 않음 | 확정 후 등록·Running·사거리·공격 준비 시각 | 준비 액터가 확정 통지 없이 표시됐는지 |

| 클라이언트에서 웨이브 UI가 멈춤 | GameState 복제·알림·서버 시간 표시 | 로컬 HUD 구독·재생성 |
| 종료 직후 추가 스폰/보상 | Phase 전이·예약 무효화·종료 후 콜백 | 명령 접수 종료·이미 확정된 응답 처리 |

**A의 P0 제출 체크**

- [ ] 데이터 누락·P0 제외 기능이 명시적으로 처리된다.
- [ ] 준비 액터는 전투에 참여하지 않고 이동·제거·중복 등록이 안전하다.
- [ ] 피해·사망·적 수·웨이브·결과의 권한 있는 원본과 변경 경로가 명확하다.
- [ ] 처치 보상과 종료 경계가 B 기능과 통합 검증됐다.
- [ ] 전투/결과 UI가 원격 클라이언트에서도 동작하고 재생성에 안전하다.
- [ ] B 주관 PC 패키징 2인 검수와 A 주관 Android 검수에 참여했다.
- [ ] 정상/실패 재현, 코드·에셋·설정·실행 증거를 해당 구현 단계에 연결했다.

## 12. P1 이후 이어갈 구현

P0 통과 후 A는 TASK-DATA-02의 공통 구조/전투 데이터, TASK-COMBAT-02의 고유 스킬·효과, TASK-WAVE-02의 확정된 웨이브·적/보스 확장과 후속 10배수 보스 검수(현재80웨이브·사냥/던전 포함)을 이어간다. 스킬 계산·예약·중첩·만료는 전투 명세와 QA-DMG-03~14를 확인하고 원작 검증 범위부터 구현한다.

P1 등급별 공격 강화·소환 확률 강화은 B가 경제에서 확정한 읽기 전용 전투 입력을 A에게 전달하도록 공통 계약을 확장한다. A가 PlayerController에서 임의 강화 값을 읽어 계산하지 않는다. 저장·설정·아트·성능·P2는 작업 보드에서 아직 미배정인 부분을 확인하고 실제 공수에 따라 배정한 뒤 진행한다. 이번 문서로 그 담당이나 일정을 확정하지 않는다.

단계별 후속 범위와 촬영 기능 후보는 [로드맵](../production/ROADMAP.md#phase-plan)을 따른다. P1/P2에서도 각자 보드 순환·해상도 독립 판정·N ≥ M 즉시 패배·10배수 보스/시간초과를 회귀한다. 신규 후보의 상위 TASK 연결은 구현 완료나 역할 추가 배정을 뜻하지 않는다.
