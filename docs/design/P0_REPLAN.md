# P0 재기획 — 확정 규칙과 자동 구현 순서

[결정 기록](../DECISIONS.md) · [현재 진행](../production/PROJECT_STATUS.md) · [데이터 계약](../DATA_SCHEMA.md)

## 1. 현재 기준

DEC-043~047로 이번 사용자 결정을 반영한다. 이전 DEC-019의 8종 제한과 미확인 경제/보스/배치 항목을 대체한다. P0 구현·실행 검수는 아직 미착수이며, 삭제한 과거 구현의 Pass를 이어받지 않는다. [초기화 기록](../production/P0_RESET.md).

P0까지 자동 구현할 때 아래 G0~G4 순서로 진행하며 매 단계의 실제 증거를 남긴다. 문서/데이터 검사만으로 P0를 완료 처리하지 않는다. A/B는 기능별 책임 구분이며 별도 작업 생성이나 담당자/일정의 자동 확정을 뜻하지 않는다. 기존 학습 자료 요구는 새 구현을 기준으로 작성한다.

강화는 [추천 수치](SUMMON_ECONOMY.md)를 적용했다. 사냥 재도전은 소환부터90초, 제한60초, 성공 다음단계/실패 같은단계다. 미션은 [현재 보유·누적 분리/자동 지급](COOP_META.md)다. 던전은 한 마리 입장, 칸당3·칸 전체 복귀·전체 복귀 버튼, 전원 수용 가능할 때 원자적 처리다.

## 4. 데이터와 명령

SchemaVersion2/RulesVersion0.3.0으로 새 로더를 작성한다. 공통 규칙·80웨이브·강화/확률·P0 활성16종과 컨셉 대기 비활성 자료를 분리한다. 마감 시각 타격 인정·보상/명령 중복 방지·순차 처리·소환 전 수용 검사·판매 보충·복귀 사전 검증은 서버 계약이다.

기획용 데이터의 최초 월드 간격은140cm, 칸/길 폭 동일, 각 경로3080cm다. 사거리는 칸 크기에서 파생한다. 두 참가자의 화면 순서에 따른 배치 배열을 쓰며 화면 반전으로 서버 CellId를 바꾸지 않는다. 외형·타이머 이전과 서버/클라이언트 표시까지 UE에서 검증해야 한다.

## 5. 구현과 검수의 경계

현재 갱신 범위는 기획·데이터 생성/정적 검사다. UE 코드/UMG·맵·PC/Android 실행은 새 구현 단계에서 진행한다. 기존 작업38개 상태를 문서 수정만으로 완료 처리하지 않는다. 기본 프로젝트/도구와 사용자 보유 에셋을 보존하고 실제 Android 기기 정보는 첫 실기기 검수 전 확보한다.

## 6. A/B 동시 개발과 단계별 산출물

**공통 기반도 각 브랜치에서 직접 구현한다는 사용자 요구를 유지한다.** 동시에 작성하되 같은 계약을 사용한다. 공통 파일의 두 구현은 통합 시 비교하여 하나로 정리하며, 두 GameState/명령 처리기를 함께 실행하지 않는다.

| 단계 / 통과 지점 | A: 전투·웨이브 | B: 경제·보드 | 교환할 산출물 |
|---|---|---|---|
| G0 계약 | 매치/적/처치 이벤트/시간의 최소 타입과 초기화 | 보드/자원/명령 결과/레이아웃의 최소 타입과 초기화 | 각 브랜치의 독립 구현 + 공통 헤더·데이터 예시·초기화 순서 대조. 미완성 상대 기능은 Stub임을 표시 |
| G1 구도 | 새 경로를 읽는 생성/이동과 두 그룹 구분 | 넓은 보드·중앙 길·카메라·터치 좌표 시연 | 두 참가자 화면의 무장식 전장, 화면비별 캡처, 좌우/중앙/전체 셀 입력 확인. **다음 전투 확장 전 통과** |
| G2 조작/공격 | 기본 공격·공유 적·체력·처치 이벤트 | 동일 뭉치 추가/새 뭉치·선택 UI, 이동·합성·판매와 원자적 소비/복제 | 상대 준비 전에는 고정 픽스처로 개발, 준비 후 실제 계약으로 교체. 이번 확정 경계의 정상/실패 동작 검수 |
| G3 한 판 | 10웨이브·보스·과밀/결과 상태 | 자원·인구·HUD·거절 표시·결과 복귀 | PC 2인 패키징, 재전송/동시 명령, 원작 대조 범위와 축약 범위 구분 |
| G4 모바일 | Android 빌드·기기 기록 주관 | 터치·SafeArea·UI·PC 2인 검수 주관 | Android 실기기 핵심 조작과 10웨이브 완주. 미실행이면 P0 최종 통과 보류 |

각 단계의 학습 자료는 **목표 → 선행 계약 → 구현 위치 → C++ 핵심 → Blueprint 연결 → 예상 화면 → 직접 검증 → 실패 원인 → 통합 차이**로 구성한다. A/B 각각의 수업에서 상대의 코드 전체가 필요하지 않도록 입력/출력 예시를 제공한다. Stub 통과와 실제 2인 통합 통과는 서로 다른 결과다.

기존 P0 참고·학습 브랜치와 작업 폴더는 DEC-035로 삭제됐으며 새 브랜치는 아직 없다. 구현 착수 시 기본 프로젝트와 최신 기획의 변경을 보존하고 공통 출발 커밋 SHA를 기록한 뒤, 같은 출발점에서 A/B 참고 구현·참고 통합과 실제 학습용 브랜치·작업 폴더를 준비한다. 각 과정의 A/B는 G0 공통 기반을 직접 작성하고 통합 시 비교하여 하나로 정리한다. 참고 완료본을 실제 학습의 출발점으로 사용하거나 과거 SHA를 새 구현 완료로 재표기하지 않는다.
