# 2인 개발 역할과 협업

[기획 허브](../README.md) · [작업별 계획 역할·실제 담당자](BOARD.md) · [진행 상황](PROJECT_STATUS.md) · [로드맵](ROADMAP.md)

역할을 확인한 뒤 [A 구현 설계](../technical/IMPLEMENTATION_A.md) 또는 [B 구현 설계](../technical/IMPLEMENTATION_B.md)에서 실제 작성 순서를 따른다. 공통 API·초기화·유닛/보상 연결·단계별 제출 기준은 [공통 구현 계약](../technical/IMPLEMENTATION_SHARED.md)에 둔다. 이 문서의 역할 배정과 작업 보드의 상태가 원본이며, 새 설계 문서의 단계 번호는 별도의 작업 배정이 아니다.

**실행 문서:** [개발 계획서](DEVELOPMENT_PLAN.md)의 범위·일정에 따라 [A 개발 문서](DEVELOPMENT_A.md)와 [B 개발 문서](DEVELOPMENT_B.md)에서 단계별 작업·전달물·검수를 확인한다. 기존 구현 설계는 클래스/API의 상세 설명으로 유지한다.

## 1. 적용 기준

DEC-027에 따라 **A는 전투·웨이브, B는 경제·보드**를 맡는다. 두 사람 모두 학습을 목표로 하며, 각자 담당 기능의 C++·Blueprint·UI·네트워크 연동·검수를 수행한다. 전투와 웨이브, 경제와 보드처럼 밀접한 기능을 한 담당 범위에 묶어 개발 중 조율을 줄인다.

A/B는 채택한 역할 구분이다. 어느 팀원이 A 또는 B인지와 주 5일 병행은 DEC-038로 확정했으며 하루 작업 시간은 아직 제공되지 않았다. 작업별 계획 역할과 실제 담당자는 [작업 보드](BOARD.md)에서 구분하며, 문서 반영만으로 작업을 Ready·InProgress·Done으로 변경하지 않는다. 이 문서의 유지 담당 Codex는 팀원 A/B에 배정된 사람이 아니다.

## 2. 역할 범위

| 영역 | A — 전투·웨이브 | B — 경제·보드 |
|---|---|---|
| 핵심 C++ | 적 이동·표적·기본 공격·피해·사망, 웨이브·보스·승패 | 소환·비용·확률·보장·재화, 배치·이동·스택·합성·판매 |
| 네트워크 | 매치 시작·종료, 공용 매치 상태, 유닛·적·전투 상태 복제 | 입력·명령 RPC, 직렬 처리·중복 방지, 경제·보드 상태 복제 연동 |
| UI | 웨이브·시간·적 수·보스 정보, 승패 결과 위젯 | HUD 기본 구성, 소환·재화·선택 패널, 이동·합성·판매 조작, 짧은 안내 |
| 월드·Blueprint | 유닛·적·보스 외형과 애니메이션, 공격·피격·사망 연출 | 전장·보드·경로 배치, 카메라·터치 좌표, 소환·합성·선택 연출 |
| 데이터·규칙 확인 | 공통 타입·로딩·검증, 유닛·적·웨이브 데이터와 원작 전투 규칙 대조 | 경제·소환 데이터, 보드·조작·판매 규칙 대조, 해당 표시 데이터 연결 |
| 빌드·QA 주관 | Android 기본 패키징과 P0 전투 빌드·실기기 실행 기록, 전투·웨이브 검수 | PC 패키징 2인·지연 검사 기록, 경제·보드 검수 |

빌드·QA 주관자는 실행 조건·기록·재현을 정리한다. 발견한 오류의 수정은 해당 기능 담당자가 맡는다. Android 터치 UI 오류는 B, 전투·웨이브 오류는 A가 수정하며 플랫폼 주관자에게 모든 수정을 넘기지 않는다. 두 사람 모두 PC 2인 플레이와 Android 터치 검수에 참여한다.

## 3. 클래스·에셋 편집 책임

아래는 앞으로 추가할 디펜스 코드·에셋의 편집 주담당이다. 이름과 런타임 책임은 [아키텍처](../technical/ARCHITECTURE.md), 실제 경로는 [이름·폴더 규칙](../technical/NAMING_AND_STRUCTURE.md)을 따른다. 기존 템플릿이나 아직 생성되지 않은 클래스를 구현 완료로 취급하지 않는다.

| 주담당 | 클래스·에셋 범위 | 상대방과 연결할 경계 |
|---|---|---|
| A | GameMode·GameState·PlayerState | B가 제공한 CommandProcessor·EconomyService와 Controller를 매치 초기화에서 연결. 개인 경제 원본은 B의 EconomyService에 유지 |
| A | BattleSubsystem·WaveDirector·UnitActor·EnemyActor | B의 보드에서 확정된 유닛 생성·제거·배치 결과를 전투에 반영하고, 처치·보상 결과를 전달 |
| A | 공통 데이터 타입·로딩·검증, 전투·결과 위젯, 유닛·적 Blueprint | B의 데이터 요구와 HUD 슬롯에 맞춰 연결. 공통 타입 변경은 B가 함께 검토 |
| B | PlayerController·CommandProcessor | 입력·RPC·요청 추적·직렬 처리·중복 결과 및 공동 확정. A의 GameMode 초기화·전투 보상과 연결 |
| B | EconomyService·BoardManager | 경제·배치의 원본 상태를 각각 소유. 같은 사람이 구현해도 서로 직접 호출·수정하지 않으며 공동 변경은 CommandProcessor가 조정 |
| B | CameraPawn, HUD 기본 구성·경제/조작 위젯, 보드·맵·입력 에셋 | A의 전투·결과 위젯을 연결하고 화면 좌표를 보드 좌표로 변환 |

핵심 규칙·권한·영구 상태 변경은 C++에서 처리하고, Blueprint는 외형·에셋·화면·입력 연결과 로컬 연출에 사용한다. A는 C++ 피해 결과로 피격 연출을 갱신하고, B는 소환 버튼에서 C++ 요청을 제출한 뒤 서버 확정 상태를 표시한다. 실제 데이터 수치와 기능 존재 여부는 DEC-021/022의 원작 대조 기준을 따른다.

같은 .uasset·.umap은 동시에 편집하지 않는다. 공통 C++ 파일·데이터 생성기 변경도 주담당에게 변경 범위를 알리고 순서를 맞춘다. `data/*.json`은 생성 결과이므로 각 기능의 명세와 `tools/build-design-data.mjs`를 수정한 뒤 생성·검증한다.

## 4. P0 작업과 통합 순서

개별 작업의 배정 원본은 [작업 보드의 계획 역할 열](BOARD.md)이다. TASK-NET-01은 A가 매치·공용 복제를, B가 명령 처리·경제/보드 복제를 담당한다. 상위 작업의 주관은 A다. TASK-UI-01은 B가 HUD·조작·안내를, A가 전투 정보·결과 위젯을 담당하며 상위 주관은 B다. 주관 표시는 상대 담당 부분까지 혼자 구현한다는 뜻이 아니다. 나머지 기능은 완결된 단위로 맡고 학습 목적으로 동일 로직을 중복 작성하지 않는다.

| 통합 단계 | A의 산출물 | B의 산출물 | 함께 확인할 결과 |
|---|---|---|---|
| 준비 | 매치·데이터 계약, 전투 규칙 확인, Android 기본 빌드 준비 | 보드·경제 규칙 확인, 전장·카메라, 명령 진입 계약 | ID·좌표·요청/응답·상태 소유·실패 사유 합의 |
| 첫 소환 | 데이터 로딩, 매치 생성·공용 상태와 복제 연결 | 소환·재화·배치·명령 처리와 소환 UI | 두 클라이언트의 소환 결과·재화·배치 일치 |
| 전투 연결 | 적 이동·공격·사망·처치 보상 전달, 한 웨이브 | 이동·합성·판매·입력·경제 보상 처리 | 소환한 유닛이 싸우고 보상이 한 번만 반영됨 |
| P0 통합 | 10웨이브·보스·승패·전투/결과 UI, Android 전투 빌드 | 조작 안내·HUD 통합, PC 2인·지연 검사 | PC 상태 일치·중복 소비 방지·승패 경계와 Android 터치 완주 |

처치 보상은 A가 식별 가능한 전투 결과를 전달하고 B의 CommandProcessor가 서버 내부 명령으로 처리한다. 서버 권한·재시도·보상 중복 방지·경제와 보드의 공동 확정은 기존 아키텍처 계약을 유지한다. 기능 연결을 위해 원본 상태를 직접 수정하는 우회 경로를 만들지 않는다.

표는 통합 순서이며 확정된 날짜나 선행 조건의 대체가 아니다. Android 기기가 없어도 도구·기본 패키징 준비는 진행할 수 있으나, P0 최종 통과에는 실기기 터치 완주가 필요하다. 원작 미확인 보드·소환 수치는 해당 기능 구현 기준으로 확정하기 전에 대조한다.

## 5. 학습·업무량·검토 운영

- 각자 담당 기능을 구현하고, 완료 시 상대에게 설계 이유·상태 변경 흐름·어려웠던 버그를 15~20분 정도 설명한다. 상대는 PR 리뷰와 실패 상황 재현을 맡는다.
- 작업은 반나절~2일 정도로 검토 가능한 크기로 나누고, 진행 중 작업은 한 사람당 1개를 기본으로 한다. 공통 타입·명령 계약은 구현 전에 함께 검토하고 작은 통합 빌드를 자주 확인한다.
- 기존안에서는 B의 입력·명령·경제·보드·HUD 연결 책임이 크다. A가 자신의 위젯·전투 연결·Android 실행을 끝까지 맡고, 통합 오류는 원인 기능의 담당자가 수정한다. B를 전체 통합·QA·아트 전담자로 두지 않는다.
- 주 1회 구현·학습·디버깅·리뷰·에셋·문서 시간을 함께 확인한다. 업무량이 한쪽에 몰리면 미착수 독립 기능이나 검수·에셋 작업을 통째로 재배정하고 보드에 남긴다. 작업 수나 기존 1~2일 추정만으로 50:50이라고 판정하지 않는다.
- P1에서도 전투·웨이브는 A, 경제·보드는 B가 기본 영역을 유지한다. 빌드 주관 교대, A의 저장·설정 또는 B의 보조 봇 참여는 학습 확장 후보이며 P0 실제 공수와 선행 조건을 확인해 배정한다. P1/P2의 계획 배정은 아래 날짜 계획에 연결하며 실제 담당자·착수 상태는 별도로 기록한다.
- P0에서는 임시·공용 에셋을 활용한다. DEC-038로 P1 아트는 기존 에셋의 선정·연동·최적화로 편성한다. A가 수호자/적/보스, B가 맵/UI를 맡고 VFX·음향은 기능별로 분담한다. 기획·QA도 두 사람의 가용 시간에 포함하고 별도 보조 인력을 전제하지 않는다.

실제 담당자·가용 시간은 OPEN-001, 아트 확보는 OPEN-004에서 확인한다. 개인별 학습 시간과 첫 통합 결과를 반영해 [로드맵](ROADMAP.md)을 재산정한다.
