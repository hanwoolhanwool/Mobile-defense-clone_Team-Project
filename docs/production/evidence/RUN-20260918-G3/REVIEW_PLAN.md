# G3 구현 전 독립 검수 계획

상태: **Planned / G3 검수 전부 NotRun**. 작성 시점 공통 출발 코드 `ae6be1b0b06ed733425e01632a341fb4db4cad59`, SchemaVersion `2`, RulesVersion `0.3.0`. 아래 기대값은 G3 구현 결과를 읽어 정한 값이 아니며, G2 통과나 과거 P0 기록을 G3 실행 증거로 사용하지 않는다. 실제 검수 때 각 행에 고정 소스 SHA·파일/함수·검사 이름·실제 결과·증거·미검증을 대응시킨다. 기능 코드·빌드·에디터 실행은 이 계획 작성 범위에 포함하지 않았다.

근거 원본: [전투 5.1~5.3](../../../design/BATTLE.md), [공통 초기화·처치 보상·종료 계약](../../../technical/IMPLEMENTATION_SHARED.md), [A 웨이브·결과 구현 경계](../../../technical/IMPLEMENTATION_A.md), [상태 소유권·명령·성능 예산](../../../technical/ARCHITECTURE.md), [ARCH-01~06](../../../technical/CODING_STANDARD.md), [QA-TIME/WAVE/NET/PERF 및 P0 완료 조건](../../../BACKLOG_QA.md), [현재 P0 범위](../../../design/P0_REPLAN.md), [빌드·패키지 실행 규약](../../../technical/BUILD_RUN.md). 규칙 공통 설명은 원본에 두며, 아래에는 입력·숫자·실패 조건을 기록한다. A 구현 문서의 오래된 `전투 5.4` 표기는 현행 BATTLE `5.3`을 따른다.

## 시각·프로필 계약

- 모든 시각은 서버 매치 시계의 정밀한 예정 시각이다. `L`=Loading 진입, `P`=Preparing 진입, `T`=Running/1웨이브 시작, `S`=10웨이브 보스 생성, `D=S+60`. `ε=0.001초`를 경계 입력으로 사용하며 20Hz의 50ms 스텝에 반올림하지 않는다. 처리 지연과 예정 시각을 별도 로그 열로 남긴다.
- 준비 10초, 로딩 제한 30초, 일반 웨이브 20초·각 진영20마리·0~19초 생성은 현재 시험값이다. `GameRules.Session.FinalWave=80`에 머물지 않고 **P0Overrides.FinalWave=10**을 적용해야 한다. 9개 일반 웨이브를 정상 진행하면 누적 생성은 양쪽180씩 총360, `S=T+180`, `D=T+240`이다. 조기 패배나 생성 실패 실행에서 이 총량을 강제로 채우지 않는다.
- 실제 listen 매치의 Loading 진입을 L로 잡고 `L+30`을 로딩 마감으로 둔다. 필수 서비스와 두 참가자의 준비가 모두 갖춰진 시각 P에 Preparing을 시작하고 `P+10`에 Running으로 전이한다. 매치 참가 전 entry UI 대기에는 매치 시계가 없다.
- 로딩 마감 동률은 G2의 열린 현재 WorldTime 원칙을 확장하는 구현 정책으로 정했다. 준비 완료가 정확히 `L+30`에 접수되고 그 경계가 아직 닫히지 않았다면 준비를 인정한다. 여전히 미준비인 채 `L+30<Now`에서 그 경계를 닫으면 timeout을 단일 확정하며, 뒤늦은 ready로 복구하지 않는다. 30초 제한을 늘리는 정책이 아니며, 예정 시각과 실제 관찰 시각을 구분한다. 이 동률 선택은 2026-09-27 통합 담당이 전달한 현재 구현 계약이며 새로운 P1 기능을 추가하지 않는다.
- G2 생산 경로의 `BeforeExternalCommand(t)`는 `<t` 전투를 반영하고, 타이머는 `WorldNow`보다 이전 격자만 닫는다. G3에서는 이 보장에 **생성·수량 패배·보스 마감·승리·웨이브 전환**도 포함해야 한다. 어떤 내부 클래스에 배치할지는 구현 선택이지만, 아래 시간 순서 결과는 변하지 않는다.

## 독립 기대값과 필수 검사

## G2 시계 결합의 차단 위험

1. **시간 종류별 일괄 처리:** Combat를 Now까지 모두 실행한 뒤 Wave/Deadline을 따라잡으면 D+ε 타격이 보스를 살해하거나, 생성 전 적을 과거 표적으로 잡는다. 각 예정 시각의 전체 사건 순서를 비교하고 D에서 컷한 결과와 hitch 결과가 같아야 한다(R04/R08).
2. **명령 직전 누락:** 기존 `<t` Combat만 호출하면 t보다 앞선 수량 패배/timeout 뒤에도 구매를 받아들인다. 앞선 timeline을 닫다가 terminal이면 외부 명령 경로를 재검증하고 새 거래를 시작하지 않아야 한다(R09). 처리 중 보상 Drain·종료 callback이 Processor를 재진입하지 않는지도 확인한다.
3. **현재 WorldNow 선확정:** G2의 열린 현재 시각을 Wave/Deadline만 먼저 닫아도 판매 우선·D 타격 인정이 깨진다. float/double 비교에 임의 오차를 넣어 D+.001을 D로 바꾸거나, 한 매치의 시간 원점을 섞는 방식은 허용하지 않는다(R08/R10).
4. **생성 배치 후 한도 검사:** 두 생성 뒤 N을 계산하거나 다음 스텝에서 검사하면100 도달 이후 상태를 추가로 바꾼다. terminal callback 후 Director 반복·다음 웨이브·상대 생성·승리 검사도 정지해야 한다(R06/R07/R13).
5. **사망과 종료의 별도 원본:** 마지막 보스 Death가 N/보상/보스 집합에 반영되기 전에 Result를 게시하거나, 보상 큐를 닫은 뒤 Flush하면 최종 보상이 유실된다. 종료 latch와 UI 통지는 분리하되 이미 승인한 보상만 게시 전에 확정한다(R11~R13).

## 패키지·성능·반복 재현의 증거 계약

- 공통 실행 기록에는 소스/데이터/맵/Config SHA·패키지 해시, UE/컴파일러·Windows·CPU/GPU/RAM·해상도/렌더러·FPS/VSync 설정, 서버 역할·두 PID·포트·네트워크 조건과 실행 길이를 남긴다. 명령·전체 빌드/런타임 로그는 파일로 보존하고 요약에는 결과와 실패 구간을 연결한다. root가 실행 자원을 직렬로 조정하며 소유 프로세스만 종료한다.
- 네트워크 검수는 엔진에서 실제 지원하는 지연/손실 설정을 먼저 확인하여 사용한다. 적용 위치·방향·요청 ID·서버 수락 순번·응답/owner snapshot Revision·최종 ID집합을 남긴다. 서버 API 직접 호출, 같은 프로세스 fixture, 화면에 보인 Pending만으로 실제 RTT/손실 Pass를 대신하지 않는다. P0 한 판이10분보다 짧다고 전투 시간·웨이브 수를 바꾸지 않는다.
- 대표 부하는 **40유닛+일반99+보스2**, P0 비활성 스킬0이다. 기존 72유닛/128적/스킬 수치는 후속 스트레스 기준이며 P0 콘텐츠를 확장하지 않는다.20분 유지에 보스60초 마감/HP 등을 고정한 Development fixture가 필요하면 바꾼 항목과 점유 수를 명시하고 승패·자연 플레이 증거와 분리한다. 검수용 우회가 기본 실행/Shipping 명령 경로에 섞이지 않아야 한다.
- 워밍업과 측정 구간을 구분하고 패키지에서 평균/p95/최대 프레임, Game/Render/GPU 시간, Combat/Timeline 스텝 처리, 활성 Actor·타이머, 프로세스/UE 메모리, 초당 송수신량을 수집한다. GPU와 Game 시간을 더해 프레임으로 보고하지 않는다. 열·Android 메모리·모바일30FPS는 PC에서 판정하지 않는다. 서버 전투 p95 10ms 등은 원본의 초기 목표이지 측정 전 보증치가 아니다. 확인된 병목만 한 변경씩 개선하고 같은 장면/조건으로 비교한다.
- 2000회 수명 검사는 예를 들어100회 단위20배치로 기록하고, 워밍업 이후 동일한 정리·GC 시점 표본을 비교한다. allocator의 high-water와 아직 살아 있는 객체/타이머 누수를 구분한다. 단순 시작/끝 RSS 2개나 GC 전후가 다른 수치만으로 누수 없음 판정을 내리지 않는다.
- 5시드 기록은 계획된 모든 판과 실패도 포함한다. 알고리즘 입력 주입/강제 재화/자동 전술의 사용 여부를 명시하고 학습자가 직접 플레이한 것으로 적지 않는다. 결과 복귀 후 새 매치·HUD 재생성 검사는 프로세스 재시작만으로 대체하지 않는다.

## 판정과 게이트 경계

검사 결과는 `문서·데이터 / Unreal 컴파일 / UE 자동화 / PIE / Editor 실행 파일 두 프로세스 / 최종 PKG 두 프로세스 / Android 실기기`를 구분한다. 테스트가 NotRun·실패·결과 파일 없음이면 Pass가 아니다. 중복 명령/보상·시각 경계·100 latch·조기 승리·상태 권한·종료 후 변경·크래시는 G3 차단 항목이며, 파일·함수·재현·영향·수정 방향으로 보고하고 수정 후 해당 회귀를 실행한다.

G3 승인에는 PC 최종 패키지의2인 참가 슬롯 한 판·지연/중복·필수 경계·반복 매치/UI·5시드 관찰·대표 부하/2000회 수명 근거가 필요하다. 조작이 자동인지 실제 사람의 플레이인지 구분하며 자동 검수를 학습자의 플레이로 기록하지 않는다.5판 전승, 특정 원작 밸런스 재현, 근거 없는 성능 목표 달성을 추가 요구하지 않는다. 부하 목표 미달은 실측 병목·개선·남은 영향으로 판단하며 결과를 숨기거나 자동 Pass로 치환하지 않는다.
