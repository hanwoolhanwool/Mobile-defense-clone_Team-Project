# 개발 계획서

**역할별 개발 문서:** [A 개발 문서 — 전투·웨이브·서버](DEVELOPMENT_A.md) · [B 개발 문서 — 경제·보드·계정/로비](DEVELOPMENT_B.md)

이 문서는 전체 범위·일정·공수의 원본이다. 각자의 작업은 역할별 개발 문서에서 시작하고, 클래스·API 구현은 기존 [A 구현 설계](../technical/IMPLEMENTATION_A.md)·[B 구현 설계](../technical/IMPLEMENTATION_B.md)·[공통 계약](../technical/IMPLEMENTATION_SHARED.md)으로 이어간다. 일정 변경 시 역할별 주차표도 함께 갱신한다.

**목표는 2026년 12월 22일(화)까지 P0 → P1 → P2를 완료하는 것이다.** A/B가 주 5일 병행 개발하며, 아트는 기존 에셋을 사용한다(DEC-038). 기존 P0 구현이 삭제된 현재 상태에서 새로 구현하는 기간까지 포함한다. 프로젝트 시작일은 DEC-048에 따라 **2026년 9월 21일(월)**이다. 아래 날짜·공수는 목표를 위한 가용 예산이며 구현 완료 기록이 아니다.

**DEC-049 일정 재배치:** 9/21 시작·12/22 완료와 P0·최종 QA·수정 여유를 유지한다. P1 콘텐츠 초안은10/9, 목록·수량·효과 확정은10/16이다. P1 핵심 기능/검수는11/13, 잔여 연출·안내 정리와 전체 통과는11/20이다. 기존 서비스 준비에 P2 작업을 A/B 각2인일 앞당겨11/6 외부2인 최소 전투를 확인한다. 그만큼의 P1 마무리를11/16~11/20으로 교환하며 총 공수는 늘리지 않는다.

**현재 범위와 상태:** DEC-043~047의 P0 핵심 기획은 정리됐다. 남은 작업은 실제 구현·PC 2인 통합·밸런스 조정·Android 실기기 검수다. P1은80웨이브·사냥/미션/던전·보물/유물/펫 실제 시스템을 포함한다. 시작일 변경에 따른 가용 공수를 아래에 재계산했으며, 확대된 콘텐츠의 소요 공수는 실제 진행과 상세 표로 계속 재추정한다.

67일은 월~금 기준 가용 평일의 상한이다. 휴무 예비 5일과 마지막 수정 7일은 서로 다른 예산이며 중복해서 사용할 수 없다. 임시로 휴무 4일은 P0, 1일은 P1에서 차감했다. 실제 휴무표를 받으면 같은 총량 안에서 이동한다. 시작 변경으로 종전 계획보다 3일/인·팀6인일이 줄었다. 휴무 예비와 최종 수정 여유는 유지하며 P0 가용 예산은19→16일/인이다. 필요한 실제 작업량이 줄었다는 뜻은 아니므로 10/2 중간 통합에서 남은 공수를 재검토한다.

**하루 4시간이면 같은 기간의 팀 본 작업 예산은 440시간으로 절반이다.** 그 경우 이 계획의 범위와 날짜를 그대로 약속할 수 없으며 실제 가용 시간에 맞춰 다시 산정한다. 에셋 도입으로 아트 제작 부담은 줄지만 전용 서버·저장·재접속의 난도까지 줄어들지는 않는다.

## 2. 단계별 마감과 통과 기준

아래는 겹치지 않는 **달력 구간별 가용 시간**이다. P1/P2 기능별 예산과 구간을 구분하여 같은 사람의 시간을 중복 배정하지 않는다.

| 작업 구간 | 기간 | 평일/인 | 휴무 예비/인 | 본 작업/인 | 통과 결과 |
|---|---|---:|---:|---:|---|
| P0 새 구현·핵심 검증 | 9/21~10/16 | 20 | 4 | 16 | G0~G4, 16종·10웨이브·PC 2인·Android 터치 완주 |
| P1 중심·P2 선행 연결 | 10/19~11/13 | 20 | 1 | 19 = P1 배정17 + P2 선행2 | 11/6 외부2인 최소 전투, 11/13 P1 핵심 기능·저장·주요 검수 |
| P2 중심·P1 마무리 | 11/16~12/4 | 15 | 0 | 15 = P2 잔여13 + P1 마무리2 | 11/20 P1 전체 통과와 실제 계정/친구 방 연결, 12/4 서비스 기능 동결 |
| P2 최종 통합 QA | 12/7~12/11 | 5 | 0 | 5 | 실제 외부 접속·지원 기기·장애/중복 지급 검수, 출시 차단 결함 0 |
| 수정 여유·최종 인수 | 12/14~12/22 | 7 | 0 | 별도 여유 7 | 잔여 결함 수정·영향 범위 재검수·최종 빌드와 문서 인수 |
| 합계 | 9/21~12/22 | 67 | 5 | 본 작업55 + 수정 여유7 | 팀 본 작업110인일 + 휴무10인일 + 수정 여유14인일 |

기능별 배정은 **P0 16 + P1 19 + P2 15 + 최종 QA 5 = 55인일/인**으로 유지한다. P1의19일에는 기존 서비스 준비(A2/B1일)가 포함되어 있으며, 이번에 앞당기는 P2 각2일과 별도다. P1은17일을11/13까지, 나머지2일을11/16~11/20에 사용한다. P2는2일을11/2~11/6에, 나머지13일을11/16~12/4에 사용한다. W07은 P1 3일+P2 2일, W09는 P1 2일+P2 3일로 제한한다.

P1 마무리2일은 **A의 추가 연출·음향 정리 및 영향 회귀, B의 안내 문구·UI 표현 정리 및 영향 회귀**에 사용한다. 핵심 전투·경제·던전·저장·필수 경고·조작 안내·판독성·주요 기기 검수는11/13까지 유지한다. 11/13은 핵심 기능 통과이며, 잔여 작업을 검수하기 전 P1 전체 완료로 표시하지 않는다. 이 교환은 필요한 작업량이 감소했다는 의미가 아니다.

**12/4 기능 동결 → 12/11 인수 후보 → 12/22 최종 완료**로 운영한다. 날짜 도달만으로 다음 단계가 통과되지는 않는다. P0의 실기기 검수와 P2의 실제 서비스 검수를 후속 문서 작업으로 대체하지 않는다.

### 3.1 P0 착수 상태와 남은 작업

**P0 구현을 시작하는 데 필요한 핵심 기획 결정은 정리됐다. 현재 완료된 것은 기획 문서·설계 데이터이며, 새 UE 구현·게임 실행 검수는 남아 있다.** 원작의 추가 관찰이나 최종 컨셉 결정을 P0 전체의 선행 조건으로 두지 않는다. 합의된 시험값으로 구현하고 측정 결과에 따라 조정한다.

| 남은 작업 | A 주관 | B 주관 | P0 통과 증거 |
|---|---|---|---|
| 실제 구현 | 두 경로·16종 기본 공격·적/보스·10웨이브·승패·전투 UI | 소환·명령·인구/공간·뭉치·드래그·합성·판매·보상·HUD | G0~G3의 실제 UE 코드/맵/위젯·빌드·동작 |
| PC 2인 통합 | 적·피해·보스 마감·결과 일치와 단일 사망 | 별도 프로세스 검수 주관, 동시 요청·중복 소비/보상·거절 불변 | 지연/재전송 포함 두 참가자의 상태·결과와 로그 |
| 밸런스 조정 | 공격력·간격·사거리 도달·적 HP/방어/속도·보스 처치 시간 | 소환/판매 수입·구성/배치·경제 흐름·같은 시드 비교 | 시험값 변경 이유·데이터 버전·반복 플레이/승패 기록 |
| Android 실기기 | 도구·APK·실제 기기 모델/OS·설치/실행·초기 성능 | 터치·SafeArea·카메라/선택·핵심 조작·화면 가독성 | 실제 기기에서 10웨이브 완주와 정상/실패 조작 증거 |

P0까지 자동 구현할 때도 A/B의 책임과 G0→G1→G2→G3→G4 순서를 따른다. 필요한 기기 연결·도구/실행 조건을 확보하며, 자동 문서/데이터 검사만으로 PC·Android 플레이 검수를 대체하지 않는다. 컨셉에 따른 독자 고유 스킬·신화 재료와 보물·유물·펫의 실제 시스템은 P1 작업이다.

## 4. 주별 A/B 병행 작업

표의 일수는 각 사람의 평일이다. 매주 수요일 중간 연결, 금요일 공동 실행·진척 점검을 각 작업량에 포함한다. 휴무가 겹치면 그 주의 마지막 근무일에 검수한다.

| 주차·기간 | 일수 | A — 전투·웨이브·서버 | B — 경제·보드·계정/로비 | 함께 확인할 산출물 |

## 7. 병행 개발과 학습 운영

- A 전체 완료를 B 착수 조건으로 삼지 않는다. 월요일에는 이번 주 요청/응답·이벤트·상태 필드를 맞추고, 수요일에는 최소 기능을 연결하고, 금요일에는 같은 빌드에서 공동 플레이한다.
- A가 공통 매치/서버 상태, B가 명령·경제·보드 상태를 주도한다. P2에서 A는 매치·복원 API, B는 계정·방·보상 API의 실행 원본을 관리한다. 공유 파일은 주담당이 반영하고 상대가 리뷰한다.
- 한 사람의 진행 중 작업은 기본 1개. 서버 빌드 등 대기 중에는 미리 합의한 에셋/문서 작업을 수행한다. 수정은 플랫폼 주관자가 아니라 원인 기능 담당자가 맡는다.
- 기존 참고 구현→A/B 재현→통합 학습 방식을 유지한다. 참고 수업은 해당 하위 작업 시작 전 준비하고 설명·리뷰 시간은 하루 2시간 배정 안에 포함한다. 참고본 지연이나 학습량 초과는 실제 진척에 반영한다. 참고·실제 개발 SHA와 검수 증거는 별도로 남긴다.
- 금요일에 A/B별 남은 인일·완료 증거·막힌 API·소진 여유를 기록한다. 한쪽이 2작업일 이상 밀리면 미착수 독립 작업을 통째로 재배정하고 보드를 갱신한다.

### 7.1 병합 시점과 완료 판정

병합은 **반나절~2일 크기의 검토 가능한 변경이 준비될 때마다** 한다. 수요일은 최소 기능 중간 통합, 금요일은 공동 플레이·남은 공수 점검일이며, 그날까지 준비된 변경을 쌓아 둘 필요는 없다. 휴무가 겹치면 직전 근무일에 확인한다.

| 구분 | 언제·무엇을 병합하는가 | 통과 조건 |
|---|---|---|
| 역할 브랜치 → 같은 과정의 통합 브랜치 | 공통 계약·첫 소환·전투 보상·웨이브 등 작은 변경마다. 공통 타입/초기화 변경을 먼저 반영하고 소비 기능을 이어서 반영 | 상대 리뷰, 영향 범위 빌드/실행. 미완성 상대 기능은 명시한 Stub/비활성 경계로 연결하고 후속 실제 통합 검수를 남김 |
| 통합 결과 → main | 정식 제품에 채택할 작은 변경의 통합 검증이 끝나면 PR. 단계 종료일까지 기다리지 않음 | 최신 main 반영·필수 CI·상호 리뷰 및 해당 변경의 UE 빌드/플레이 증거. 문서 CI로 게임 검수를 대체하지 않음 |
| 단계 완료 기준점 | P0 10/16, P1 핵심11/13·전체11/20, P2 기능12/4·QA12/11·최종12/22 | 단계별 필수 검수 전체와 통합 SHA/빌드 기록. 코드 병합만으로 단계 완료 처리하지 않음 |

P0 첫 병합은9/23 G0의 공통 타입·초기화·명령 계약을 목표로 한다. 이후10/2 경로/첫 전투·소환,10/9 합성/판매/웨이브,10/16 PC·Android 최종 통합을 확인한다. 각 날짜는 준비와 검수를 통과하는 목표이며 실패한 코드를 날짜 때문에 main에 넣지 않는다.

참고 구현 A/B와 실제 학습 A/B는 각각 자기 통합 브랜치에서 병합하고 SHA·증거를 따로 남긴다. 참고 완성본으로 실제 학습 과정을 덮어쓰지 않는다. 브랜치명·main PR 기준은 [Git 운영](../WORKFLOW.md), 두 과정의 경계는 선택 학습 자료의 운영 기준을 따른다. 같은 .uasset/.umap은 주담당 한 명이 순서대로 편집하고 충돌 시 에디터에서 의도한 내용을 재적용한다. 검증된 통합 변경은 양쪽 역할 브랜치에도 반영하여 다음 작업의 기반을 맞춘다.
