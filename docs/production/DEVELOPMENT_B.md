# B 개발 문서 — 경제·보드·계정/로비

**현행 규칙:** [P0 재기획](../design/P0_REPLAN.md)의 DEC-043~047을 따른다. P0 16종·100/20·보스2/60초, P1 80웨이브·사냥/미션/던전·보물/유물/펫 실제 시스템. P0 핵심 기획은 정리됐고 실제 구현·검수가 남아 있다. 고유 콘텐츠는 컨셉 후 결정한다. 시작은 **2026-09-21(월)**, 최종 완료 목표는 **2026-12-22(화)**이며 가용 예산을 아래에 갱신했다.

[개발 계획서](DEVELOPMENT_PLAN.md) · [A 개발 문서](DEVELOPMENT_A.md) · [B 구현 설계](../technical/IMPLEMENTATION_B.md) · [공통 계약](../technical/IMPLEMENTATION_SHARED.md) · [작업 보드](BOARD.md)

**B의 목표는 플레이어의 터치·소환·배치·합성·판매 요청을 정확한 서버 상태 변경으로 연결하고, 재화·유닛·UI가 일치하도록 완성하는 것이다.** A의 전투와 연결되는 보드·명령·보상을 맡고, P2에서는 계정·친구 방·결과 저장과 로비 흐름을 구현한다.

이 문서는 P0부터 P2까지 B가 따라갈 실행 문서다. 기존 P0 구현은 초기화됐으며 새 코드는 기본 프로젝트에서 작성한다. 아래 구현물·검수·성능 개선은 앞으로 만들 산출물이고 완료 기록이 아니다. 역할 분담을 바꾸지 않으며 상세 상태는 작업 보드에서 관리한다.

## 1. 작업 기준과 읽는 순서

**현재 전장·HUD 기준:** DEC-040의 [인게임 UI v2 요소별 명세](../design/BOARD_UI.md#ingame-ui-v2). 1080×2340 기준, 필드당 6열×3행·칸 120×120px·모든 길 폭 120px를 적용한다. G1에서 칸/길의 비율과 입력을, HUD 통합에서 기본·선택·보스 상태와 SafeArea 대응을 검수한다. 도안의 후속 기능 버튼이 P0 범위를 늘리지는 않는다.

1. [초기 설정](../GETTING_STARTED.md#setup)을 따라 자신의 PC에서 기본 프로젝트 빌드·실행을 확인한다.
2. [개발 계획서](DEVELOPMENT_PLAN.md)에서 이번 주와 단계별 마감·공수·미정 항목을 확인한다.
3. 아래 단계표에서 작업을 고르고 연결된 [B 구현 설계](../technical/IMPLEMENTATION_B.md)와 기능 명세를 읽는다.
4. A와 필요한 입력/출력·실패 조건을 맞춘 후 반나절~2일 하위 작업으로 구현한다.
5. 자기 기능 검사 → A와 실제 연결 → 실행 증거 기록 → 작업 상태 갱신 순서로 마친다.

주 5일, 하루 8시간은 계획 가정이다. 하루 평균 구현·디버깅·에셋 연동 6시간과 학습·리뷰·통합·기록 2시간을 배정한다. 참고 구현을 학습하는 시간도 포함하며, 참고/실제 개발의 커밋과 증거는 구분한다.

| 단계 | 목표일 | B 본 작업 예산 |
|---|---|---:|
| P0 핵심 기능·PC/Android 검수 | 10/16 | 16인일 |
| P1 콘텐츠·에셋·품질 | 핵심11/13·전체11/20 | 19인일 = 11/13까지17 + 마무리2 |
| P2 서비스 기능 동결 | 최소 접속11/6·동결12/4 | 15인일 = 선행2 + 잔여13 |
| P2 최종 QA·인수 후보 | 12/11 | 5인일 |
| 수정 여유·최종 인수 | 12/22 | 별도 7인일 |

본 작업은 **55인일·440시간**, 수정 여유를 모두 쓰면 **62인일·496시간**이다. 휴무 예비 5일은 별도다. 9/21~12/22는 평일67일이며 55+7+5일로 배분한다. P0 예산은 시작 변경으로3일 줄었고, 실제 필요 공수는 10/2 통합 결과로 재검토한다. 범위/공수는 개발 계획서를 따르며 일일 가용 시간이 다르면 재산정한다.

## 2. B의 소유 범위와 협업 경계

소스는 `Source/Mobile_defense_clone/`, 콘텐츠는 `Content/LD/` 아래에 필요한 단계부터 추가한다. 아래 클래스는 구현 설계의 예정 구조이며 존재/완성을 보장하는 목록이 아니다.

| 영역 | B가 작성·관리 | A와 맞출 경계 |
|---|---|---|
| 입력/명령 | PlayerController·CommandProcessor, 입력 의도·RPC·요청/응답·중복 처리 | 서버 참가자 문맥·Phase·초기화/종료 호출 |
| 경제 | EconomyService, 재화·비용·확률/RNG·확률 단계·준비/확정 | 읽기 전용 규칙·처치/결과 사실 |
| 보드 | BoardManager, 유닛 존재·소유·칸·뭉치·이동/합성/판매 | A의 UnitActor 준비/활성/제거·전투 등록 |
| 월드/화면 | CameraPawn·경로/맵·입력·HUD·경제/선택 위젯, 모바일 좌표/가시성 | A의 경로 소비 조건·전투/결과 위젯·실제 사거리 |
| 에셋/품질 | 맵·보드·UI·아이콘·소환/합성 연출·UI/로비 음향, PC 2인 검수 주관 | A의 Android 빌드/기기 기록, 공동 품질/밸런스 점검 |
| P2 서비스 | 인증·기본 프로필·친구 방·서버 검증 결과 저장/보상·로비/복귀 UI | A의 서버 배정·매치 복원·권위 있는 결과 |

경제 원본은 EconomyService, 유닛 존재/소유/칸 원본은 BoardManager다. 두 객체는 서로의 상태를 직접 수정하지 않으며 공동 변경은 CommandProcessor가 조정한다. UI는 서버 확정 상태를 표시하고 피해·승패를 계산하지 않는다. 구체적인 제안 API·상태 소유권은 [공통 계약](../technical/IMPLEMENTATION_SHARED.md#contracts)을 따른다.

## 3. P0 개발 순서 — 9/21~10/16

### 3.1 착수 상태와 B의 잔여 작업

**P0 핵심 기획 결정은 정리됐으므로 확정 규칙과 시험 데이터로 구현을 시작한다.** 현재 문서·데이터 검사 통과는 보드·경제·HUD·PC/Android 실행 완료와 구분한다. 컨셉·신화·메타 시스템의 후속 결정을 기다리지 않고 임시16종 기본 공격과 연결한다.

- 시작100코인·유료 가격20+2n·4등급 확률·웨이브 기본 보상 없음·처치 보상 양쪽 지급을 구현한다.
- 추첨 전 인구/공간 차단, 동일 종류 여유 뭉치 최대1, 판매1마리·일반 다음가격50%·실제 개체 보충을 구현한다.
- 드래그는 전체 뭉치·점유 칸 교환, 합성은 같은 칸3→상위1·여유 뭉치→화면 첫 빈칸이다. 선택 칸 우선/수동 분리 이동은 사용하지 않는다.
- PC 별도2인 통합과 동시/중복 요청·비용/RNG 불변·UI 입력을 검수한다. A와 같은 시드로 경제/전투 밸런스를 조정하고 실제 Android에서 터치·SafeArea·선택·10웨이브 완주를 확인한다.

## 4. P1 개발 순서 — 핵심10/19~11/13·마무리11/16~11/20

DEC-049에 따라10/9 콘텐츠 초안·10/16 목록/수량/효과·상세표를 확정한다. 기존 P1 배정19일 중17일을11/13까지 쓰고, 안내 문구·UI 표현 정리와 영향 회귀2일을11/16~11/20으로 옮긴다. 핵심 전투·경제·던전·저장·필수 경고/조작 안내·주요 기기 검수는11/13까지다. W07에서 그만큼 P2 인증/방 연결2일을 앞당겨11/6 실제 외부2인 최소 전투를 확인한다. 기존 서비스 준비1일은 별도로 유지하며 추가 공수로 중복 계산하지 않는다.

진입 시 P0 통과와 채택 콘텐츠 목록을 확인한다. 강화/룰렛/미션은 채택 시험표, 던전 왕복과 메타 저장은 현재 계약에 연결한다. 신화 재료·P1 콘텐츠별 비용/보상은 컨셉 후 확정한다.

신화·강화·룰렛·설정의 화면 구성은 DEC-041의 [현재 패널 명세](../design/BOARD_UI.md#ingame-ui-panels)를 사용한다. W05의 TASK-UI-02에서 신화/강화/룰렛을, W06의 TASK-UX-01/SAVE-01에서 설정을 연결한다. 미확정 게임 수치·후속 알림/번역의 실제 기능 범위와 화면 배치 채택을 구분하고 기존 일정·담당·완료 상태를 유지한다.

미션 화면은 DEC-042의 [채택한 UI](../design/BOARD_UI.md#mission-ui)를 TASK-UI-02에 연결한다. 수집/수량 진척·보상·완료 표시·스크롤/닫기를 도안과 대조하고, 집계/지급/반복은 DEC-046의 현재보유/누적·자동지급·판당1회로 TASK-ECON-02와 통합한다. 기존 P1 연결과 일정·공수·작업 상태는 유지한다.

## 8. 검수·제출과 개인 기여 기록

- **P0:** 전 셀 터치·두 화면 시점·최대3 뭉치·소환/이동/합성/판매·중복 요청/실패 불변·PC 2인·Android 터치 완주 증거.
- **P1:** 강화/룰렛·미션·던전 복귀·보물/유물/펫 획득/성장/저장·안내/설정·저장 복구·에셋 출처·UI/기기 품질·기존 보드/명령 회귀 증거.
- **P2:** 실제 인증/방/전투 이동·단일 결과 지급·복귀 화면·채택 미니게임 진입/중단/재진입·터치 검수. 상세 기대값은 [QA 원본](../BACKLOG_QA.md).
- **인수:** 빌드/커밋 식별자, 실행 환경·재현 순서, 로그·영상, 실패와 수정 이력, 남은 비차단 결함, A에게 전달한 API 변경을 기록한다. 참고/실제 학습 결과는 별도 SHA로 관리한다.

클라이언트 포트폴리오용 기록은 기존 작업에서 확보한다. 명령/상태/UI 분리, 소환의 원자적 처리와 중복 방지, 보드 좌표/터치 정합성, 화면 재생성/재접속 중 상태 복원 중 대표 사례의 문제·대안·선택 이유·검증 결과를 남긴다. 외부 에셋과 직접 구현한 부분을 구분하고 검증하지 않은 결과는 성과로 적지 않는다.

반나절~2일의 작은 변경이 준비되면 상대 리뷰 후 같은 과정의 통합 브랜치로 병합한다. 매주 수요일 최소 연결, 금요일 공동 실행·남은 인일 점검을 한다. 첫 G0 병합9/23, 이후10/2·10/9·10/16 통합 검수를 목표로 하며 main은 검증된 통합 결과를 PR로 반영한다. 참고/실제 학습 병합과 SHA는 분리하며 자세한 기준은 [개발 계획서의 병합 시점](DEVELOPMENT_PLAN.md#merge-cadence)을 따른다. 학습/환경 문제로 2작업일 이상 밀리면 미착수 독립 작업 재배정이나 범위 조정안을 보드에 기록한다. 개발 계획서의 마감만으로 작업을 Done으로 바꾸지 않는다.
