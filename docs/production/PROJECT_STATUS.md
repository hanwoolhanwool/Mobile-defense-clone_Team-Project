### A3. 작업 집계

집계는 [작업 보드](BOARD.md)의 등록 행을 기준으로 계산한다. 상태·작업 수가 바뀌었을 때만 표를 갱신한다.

| 범위 | 전체 | Backlog | Ready | InProgress | Review | QA | Done | Blocked |
|---|---|---|---|---|---|---|---|---|
| P0 | 11 | 10 | 0 | 0 | 0 | 0 | 1 | 0 |
| P1 | 20 | 20 | 0 | 0 | 0 | 0 | 0 | 0 |
| P2 | 6 | 6 | 0 | 0 | 0 | 0 | 0 | 0 |
| 합계 | 37 | 36 | 0 | 0 | 0 | 0 | 1 | 0 |

작업 크기가 다르므로 등록 건수를 개발 완료율로 환산하지 않는다. Backlog는 진척을 확인하지 않은 등록 상태이며 기존 코드의 부재를 뜻하지 않는다. QA 시나리오 수와 실제 통과 결과는 [검수 기록](TEST_RUNS.md)에서 확인한다.

### A4. 바로 다음 행동 — 가까운 작업만 유지

완료한 행은 B의 이력에 근거를 남긴 뒤 제거하고 다음 행동으로 교체한다. 장기 계획은 C에 둔다. 후보를 적었다는 이유만으로 담당자 배정·착수 상태를 바꾸지 않는다.

| 순서 | 연결 항목 | 다음 행동 | 완료 시 확인할 증거 |
|---|---|---|---|
| 1 | TASK-MOB-01 / OPEN-002 | Android 목표 도구·경로와 모바일 설정 적용 후 기본 APK 패키징 | UE가 실제 선택한 버전·명령·빌드 로그·APK 검사 |
| 2 | TASK-MOB-01 / OPEN-008 | 검증 기기 선정·정보 기록 후 기본 앱 설치·실행 | 모델·OS·GPU·메모리·ABI, 설치·표시·터치·SafeArea 관찰 |
| 병행 | OPEN-009 / 관련 P0 작업 | Android 2.0.11 보통 모드의 보드·이동·분산 합성·소환·판매 대조 | 입력 전후 결과와 연결된 명세·데이터·QA 수정 근거 |

기기 선정 전에도 도구·패키징 준비를 진행할 수 있다. 원작 규칙이 필요한 기능은 해당 규칙을 확인한 범위부터 구현한다.

## C. 전체 개발 과정 — 범위·완료 조건이 바뀔 때만 수정

```text
① 방향·범위와 사전 문서 정리
            ↓
② 환경·기본 실행 준비 ↔ ③ 원작 규칙 확인·P0 기능 구현
                              ↓
                   ④ P0 통합 검수
                              ↓
                   ⑤ P1 MVP 확장·품질
                              ↓
                   ⑥ P2 서비스·출시 준비
```

이 흐름에는 현재 상태를 덧붙이지 않는다. 현재 위치와 완료 여부는 A에서만 갱신한다.

| 단계 | 해야 할 일 | 단계 완료 조건 |
|---|---|---|
| ① 사전 기획 | 제품 방향, P0 범위, 시스템 계약, 작업·QA 기준 정리 | 개발 시작 범위와 남은 선행 조건을 문서로 연결 |
| ② 환경 준비 | 입력 보존, 도구·설정 적용, Editor·PC·Android 빌드와 기본 실행 | 실제 도구 버전·명령·산출물·실행 근거 확보. 양 플랫폼 빌드 후 엔진 고정 판단 |
| ③ 원작 확인·P0 구현 | 필요한 원작 규칙 확정, 보드·카메라·서버 권한·복제·데이터·전투·경제·웨이브·터치 UI 구현 | 기능별 완료 조건과 관련 QA의 실제 통과 |
| ④ P0 통합 | 8종·10웨이브·보스 1종·기본 공격·짧은 조작 안내 통합 | PC 패키징 2인 상태 일치·중복 소비 방지·승패 경계 및 Android 실기기 터치 완주 |
| ⑤ P1 MVP | 30웨이브, 스킬·강화·콘텐츠, 봇·저장·정식 튜토리얼, 아트·사운드·성능·밸런스 | 기능·데이터·모바일 품질과 반복 플레이 검수 |
| ⑥ P2 출시 준비 | 서버·계정·방 코드·재접속·운영·출시 검수 | 서비스 범위·출시 기준을 확정하고 관련 검수 통과 |

환경 준비와 원작 확인은 독립적으로 진행할 수 있다. 미확인 규칙은 해당 기능 구현 전에 확정한다. P1의 에디터·자동화 확장 4개는 Should 범위로 별도 공수를 산정하며 P0 필수 조건에 추가하지 않는다.

P0 결과와 실제 처리량을 근거로 P1 범위·일정을 재산정한다. [로드맵](ROADMAP.md)의 기간은 인력·에셋을 가정한 추정이며 확정 마감일이나 남은 기간이 아니다. 상세 작업·완료 조건은 [작업 정의](../BACKLOG_QA.md)가 원본이다.

## D. 갱신 규칙·복사용 양식

### 누가 언제 갱신하는가

작업을 수행한 사람이 해당 결과를 원본에 기록한 뒤 이 문서를 갱신한다. Codex가 후속 작업을 수행할 때도 같은 규칙을 따른다. 작업 시작·중단·완료, 실제 검사 결과, 다음 우선순위, 미정 항목, 단계·범위가 바뀐 작업 회차에는 응답을 마치기 전에 반영한다. 변경 없는 현황 확인만으로 이력을 추가하거나 날짜만 새로 찍지 않는다.

이 파일은 수동 갱신 문서다. 검사 명령은 현황 표를 자동 수정하지 않으며, A3 집계·InProgress 수·A4의 완료 작업 재등록을 보드와 대조해 오류로 보고한다. 서술 내용의 최신성은 함께 검토한다.

| 발생한 변화 | 먼저 수정할 원본 | 이 문서에서 수정할 곳 |
|---|---|---|
| 작업 착수·상태·담당자·작업 수 변경 | 작업 보드 | A1·A3, 필요한 A2·A4 |
| 빌드·실행·검수 결과 추가 | 검수 기록과 실행 증거 | 영향을 받는 A2·A4·A5, 주요 결과면 B |
| 미정 항목 해결·새 문제 발견 | 결정 기록 또는 해당 작업·검수 기록 | A4·A5, 주요 해결이면 B |
| 도구·설정·기기 변경 | 환경 안내·빌드 절차·세팅 요약 | 영향을 받는 A2·A4·A5, 주요 결과면 B |
| 단계 전환·범위·완료 조건 변경 | 결정 기록·명세·로드맵 | A1·A2·A4와 B, 계획 변경이면 C |
| 오탈자·배치 등 문서 정리 | 해당 문서 | 해당 문장만 수정. 개발 진척으로 집계하지 않음 |

### 갱신 마무리 체크

- [ ] A1의 확인일·갱신자·현재 상황·진행 중 작업·다음 후보가 이번 결과와 일치한다.
- [ ] A3의 단계별·상태별 합계가 작업 보드와 일치한다. 변경 없는 표는 유지한다.
- [ ] 완료한 다음 행동과 해결된 문제를 A4·A5에서 제거하고 필요한 후속 행동을 적었다.
- [ ] 완료·문제 해결 주장은 실행 증거나 결정에 연결했다. 문서 검사 통과를 게임 QA 통과로 표시하지 않았다.
- [ ] 주요 변화는 B에 기록했다. 과거 실행 결과를 현재 값으로 덮어쓰지 않았다.
- [ ] 영향받은 세팅 요약·원본을 갱신하고 `node tools/validate-planning.mjs`로 링크·표·참조를 확인했다.

체크박스는 매 갱신 때 사용하는 양식이며 영구 완료 표시로 누적하지 않는다.

### 행 복사 양식

아래 양식은 코드 블록 안에서 복사해 해당 표에 넣고 실제 값으로 채운다. 근거가 없으면 완료로 적지 않는다.

```markdown
<!-- A4: 다음 행동 -->
| 순서 또는 병행 | TASK/OPEN ID | 구체적인 다음 행동 | 완료 시 확인할 증거 |

<!-- A5: 미해결 항목 -->
| 원본 항목·링크 | 현재 영향 | 해소·재확인 조건 |

<!-- B: 주요 진행 이력 -->
| YYYY-MM-DD | 작업 완료/단계 전환/문제 해결/계획 변경 | 실제 변화 한 문장 | 근거 링크·남은 범위 |
```
