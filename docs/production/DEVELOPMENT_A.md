# A 개발 문서 — 전투·웨이브·서버

**현행 규칙:** [P0 재기획](../design/P0_REPLAN.md)의 DEC-043~047을 따른다. P0 16종·100/20·보스2/60초, P1 80웨이브·사냥/미션/던전·보물/유물/펫 실제 시스템. P0 핵심 기획은 정리됐고 실제 구현·검수가 남아 있다. 고유 콘텐츠는 컨셉 후 결정한다. 시작은 **2026-09-21(월)**, 최종 완료 목표는 **2026-12-22(화)**이며 가용 예산을 아래에 갱신했다.

[개발 계획서](DEVELOPMENT_PLAN.md) · [B 개발 문서](DEVELOPMENT_B.md) · [A 구현 설계](../technical/IMPLEMENTATION_A.md) · [공통 계약](../technical/IMPLEMENTATION_SHARED.md) · [작업 보드](BOARD.md)

**A의 목표는 유닛·적의 전투와 웨이브·승패를 구현하고, Android와 전용 서버에서도 같은 상태가 유지되도록 완성하는 것이다.** B의 소환·배치 결과를 전투에 연결하고 처치 사실·결과를 B의 경제/보상 처리에 전달한다.

이 문서는 P0부터 P2까지 A가 따라갈 실행 문서다. 기존 P0 구현은 초기화됐으며 새 코드는 기본 프로젝트에서 작성한다. 아래 구현물·검수·성능 개선은 앞으로 만들 산출물이고 완료 기록이 아니다. 역할 분담을 바꾸지 않으며 상세 상태는 작업 보드에서 관리한다.

## 1. 작업 기준과 읽는 순서

1. [초기 설정](../GETTING_STARTED.md#setup)을 따라 자신의 PC에서 기본 프로젝트 빌드·실행을 확인한다.
2. [개발 계획서](DEVELOPMENT_PLAN.md)에서 이번 주와 단계별 마감·공수·미정 항목을 확인한다.
3. 아래 단계표에서 작업을 고르고 연결된 [A 구현 설계](../technical/IMPLEMENTATION_A.md)와 기능 명세를 읽는다.
4. B와 필요한 입력/출력·실패 조건을 맞춘 후 반나절~2일 하위 작업으로 구현한다.
5. 자기 기능 검사 → B와 실제 연결 → 실행 증거 기록 → 작업 상태 갱신 순서로 마친다.

주 5일, 하루 8시간은 계획 가정이다. 하루 평균 구현·디버깅·에셋 연동 6시간과 학습·리뷰·통합·기록 2시간을 배정한다. 참고 구현을 학습하는 시간도 포함하며, 참고/실제 개발의 커밋과 증거는 구분한다.

| 단계 | 목표일 | A 본 작업 예산 |
|---|---|---:|
| P0 핵심 기능·PC/Android 검수 | 10/16 | 16인일 |
| P1 콘텐츠·에셋·성능 | 핵심11/13·전체11/20 | 19인일 = 11/13까지17 + 마무리2 |
| P2 서비스 기능 동결 | 최소 접속11/6·동결12/4 | 15인일 = 선행2 + 잔여13 |
| P2 최종 QA·인수 후보 | 12/11 | 5인일 |
| 수정 여유·최종 인수 | 12/22 | 별도 7인일 |

본 작업은 **55인일·440시간**, 수정 여유를 모두 쓰면 **62인일·496시간**이다. 휴무 예비 5일은 별도다. 9/21~12/22는 평일67일이며 55+7+5일로 배분한다. P0 예산은 시작 변경으로3일 줄었고, 실제 필요 공수는 10/2 통합 결과로 재검토한다. 범위/공수는 개발 계획서를 따르며 일일 가용 시간이 다르면 재산정한다.

## 2. A의 소유 범위와 협업 경계

소스는 `Source/Mobile_defense_clone/`, 콘텐츠는 `Content/LD/` 아래에 필요한 단계부터 추가한다. 아래 클래스는 구현 설계의 예정 구조이며 존재/완성을 보장하는 목록이 아니다.

| 영역 | A가 작성·관리 | B와 맞출 경계 |
|---|---|---|
| 매치 | GameMode·GameState·PlayerState, 초기화·Phase·공용 복제·종료 | B 서비스/Controller 초기화, 명령 접수 가능 상태 |
| 데이터 | 공통 타입·로더·검증, 유닛·적·스킬·웨이브 데이터 | 경제/보드 필드 요구, 읽기 전용 규칙과 버전 |
| 전투 | UnitActor·EnemyActor·BattleSubsystem·WaveDirector, 공격/피해/효과/처치 | B의 확정 배치·이동·제거 통지, 처치 사실 전달 |
| 화면·에셋 | 전투 정보/결과 위젯, 수호자·적·보스·애니메이션·전투 VFX/SFX | B의 HUD 슬롯, 선택 UI가 소비하는 실제 사거리 |
| 플랫폼·품질 | Android 빌드/기기 기록 주관, 전투 부하·메모리·봇 | B의 입력/UI 오류 수정 및 공동 플레이 |
| P2 서비스 | 전용 서버 빌드·배정·매치 복원·봇 인계·운영 | B 인증 신원·방/계정 API·결과 저장·복귀 화면 |

경제 원본은 B의 EconomyService, 유닛 존재/소유/칸 원본은 B의 BoardManager다. A는 골드나 보드 상태를 직접 바꾸지 않는다. 처치 사실을 식별 가능한 이벤트로 전달하고 B의 서버 내부 명령이 보상을 처리한다. 구체적인 제안 API·상태 소유권은 [공통 계약](../technical/IMPLEMENTATION_SHARED.md#contracts)을 따른다.

## 3. P0 개발 순서 — 9/21~10/16

### 3.1 착수 상태와 A의 잔여 작업

**P0 핵심 기획 결정은 정리됐으므로 확정 규칙과 시험 데이터로 구현을 시작한다.** 현재 기획·데이터 검사 통과는 새 전투 코드·PC/Android 실행 완료와 구분한다. 최종 컨셉·고유 스킬·신화는 P1이므로 P0 기본 공격 구현의 대기 조건이 아니다.

- 일반~전설 각4종 총16종의 기본 공격과 근접/투사체 표현, 반지름1.25/2.5/3.5칸을 구현한다.
- 일반20초·진영별20마리·1초 간격, 양쪽 보스2마리·60초, 일반 적100·개인 인구20의 계약을 연결한다. 최종 양쪽 보스와 잔여 일반 적 처리를 승리 조건으로 검사한다.
- PC 두 참가자의 적/피해/결과 일치, 마감 시각 타격 인정·단일 사망/보상 이벤트·중복 콜백을 검수한다.
- 공격력·간격·적 HP/방어/속도는 실제 플레이로 조정한다. Android 도구/기본 APK는 첫 주부터 준비하고 실제 기기10웨이브·초기 성능 증거를 남긴다.

- **P1:** 80웨이브·사냥/던전·채택 스킬/메타 효과·봇·에셋 출처·기기 20분 부하·개선 전후 측정·기존 전투 회귀 증거.
- **P2:** 외부 2인·재접속/이탈·보상 재시도·서버 중단/복구·채택 미니게임 검수. 상세 기대값은 [QA 원본](../BACKLOG_QA.md).
- **인수:** 빌드/커밋 식별자, 실행 명령/환경, 로그·영상, 실패와 수정 이력, 남은 비차단 결함, B에게 전달한 API 변경을 기록한다. 참고/실제 학습 결과는 별도 SHA로 관리한다.

클라이언트 포트폴리오용 기록은 기존 작업에서 확보한다. 전투/스킬 구조, 서버 결과와 애니메이션/연출 연결, 모바일 성능 개선 중 대표 사례의 문제·대안·선택 이유·검증 결과를 남긴다. 외부 에셋과 직접 구현한 부분을 구분하고 아직 측정하지 않은 수치를 성과로 적지 않는다.

반나절~2일의 작은 변경이 준비되면 상대 리뷰 후 같은 과정의 통합 브랜치로 병합한다. 매주 수요일 최소 연결, 금요일 공동 실행·남은 인일 점검을 한다. 첫 G0 병합9/23, 이후10/2·10/9·10/16 통합 검수를 목표로 하며 main은 검증된 통합 결과를 PR로 반영한다. 참고/실제 학습 병합과 SHA는 분리하며 자세한 기준은 [개발 계획서의 병합 시점](DEVELOPMENT_PLAN.md#merge-cadence)을 따른다. 학습/환경 문제로 2작업일 이상 밀리면 미착수 독립 작업 재배정이나 범위 조정안을 보드에 기록한다. 개발 계획서의 마감만으로 작업을 Done으로 바꾸지 않는다.
