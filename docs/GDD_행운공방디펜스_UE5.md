## 1. 제품 목표와 원작 참고 범위

### 1.1 한 문장 소개

장난감 공방을 침입한 불량 장난감들로부터 지키기 위해, 두 제작자가 무작위로 나온 수호자 피규어를 합치고 전설 작품을 완성하는 협동 디펜스.

### 1.2 목표하는 재미

| 축 | 플레이어가 느낄 장면 | 구현 수단 |
|---|---|---|
| 기대 | 소환 버튼을 누르기 전의 짧은 긴장 | 등급 확률, 희귀 이상 보장 카운터, 0.35초 결과 연출 |
| 선택 | 당장 딜을 유지할지 상위 등급을 만들지 고민 | 3개 합성, 전설 제작 재료 표시, 보스 예고 |
| 반전 | 밀리던 전장을 상위 유닛 하나가 정리 | 광역 전설·신화 스킬, 획득 알림, 처치 수 피드백 |
| 협동 | 아군 둔화 위에 내 광역 공격이 겹침 | 공용 적 경로, 팀 상태이상, 도움 핑 |
| 수집 | 작은 피규어가 점점 특별해짐 | 실루엣, 움직임, 받침대, 도감 회전 보기 |

순간 조작 능력보다 확률 결과에 적응하는 판단을 중시한다. 수호자는 자동 공격하며, 플레이어가 직접 캐릭터를 이동 조종하거나 공격 키를 누르지 않는다.

### 1.3 원작 재현과 기존 초안의 구분

공식 스토어는 원작의 무작위 유닛 소환, 합성, 룰렛형 도전을 핵심 기능으로 소개한다. Google Play의 소개 기사에서는 협동 상황과 유닛의 확률적 변화를 설명한다. 본 기획은 이 핵심 루프를 출발점으로 사용한다. [원작 공식 스토어](https://play.google.com/store/apps/details?hl=ko&id=com.percent.aos.luckydefense), [Google Play 소개](https://play.google.com/store/apps/editorial?gl=KR&id=mc_editorialmd_launchnontp_lucky_defense_fcp)

다음 표는 원작 대조 전 작성한 프로젝트 초안이다. 공식 소개가 이 표의 확률·보장·재료 수·웨이브 수를 입증하지 않는다. DEC-021 이후에는 원작과 확인된 차이를 기능 명세·데이터·QA에 함께 반영한다.

| 참고할 구조 | 기존 프로젝트 초안(원작 대조 대기) |
|---|---|
| 무작위 소환 | 골드 소환 + 실패 보정이 있는 별조각 도전 |
| 동일 유닛 합성 | 동일 UnitId 3개 → 상위 등급에서 균등 추첨 |
| 협동 방어 | 한 개의 공용 순환 경로와 두 개의 배치 보드 |
| 강한 유닛 완성 | 재료 3종을 소비하는 신화 제작 |
| 짧은 반복 플레이 | 30웨이브 약 15분, 전투 자원은 매판 초기화 |

3D 전환은 자유 카메라나 지형 고저차를 추가하는 방식으로 확장하지 않는다. 전투 판정은 XY 평면에 두고, 피규어의 체적·애니메이션·소환 연출이 3D의 장점을 보여준다. 캐릭터명, 외형, 사운드, 텍스트, 맵 장식, UI 그래픽은 공방 테마로 새로 제작한다.

## 2. 범위와 단계별 완성 기준

### 2.1 P0: 핵심 검증 빌드

DEC-019로 아래 범위를 확정했다. 소환·합성·배치의 기본 전투 루프를 먼저 검증하며, 강화와 희귀 고유 스킬의 재미·밸런스는 P1에서 검증한다.

| 항목 | 수량·범위 |
|---|---|
| 맵 | 회색 박스 공방 1개, 공용 순환 경로 1개 |
| 수호자 | 일반 C01~C04 + 희귀 R01~R04, 총 8종. 기본 공격·능력치 차이만 적용, 고유 스킬 비활성. 외형은 임시 에셋 허용 |
| 적 | 기본 적 1종, 10웨이브 보스 1종 |
| 룰 | 10웨이브, 골드 소환, 일반→희귀 합성, 배치·판매, 공용 적 수 패배 |
| 협동 | 개발 PC 리슨 서버와 클라이언트 1대, 로컬 접속 |
| UI | HUD, 선택 패널, 소환 버튼, 결과 화면과 짧은 조작 안내. 미구현 기능 버튼 숨김 |
| 제외 | 공격 훈련·장치 가속, 희귀 고유 스킬, 정식 3웨이브 튜토리얼, 별조각 도전·신화·계정 성장·인터넷 매칭·상점 |
| 완료 조건 | PC 2인 상태 일치·중복 소비 방지·승패 경계 검사와 Android 실기기에서 P0 전투의 터치 완주 모두 통과 |

P0 데이터는 전용 프로파일을 사용한다. 일반/희귀 소환 비중은 85/15이며 희귀 이상 보장 시 희귀 100%다. 희귀 합성 버튼은 이 빌드에서 비활성화한다. 최종 기획의 영웅이 나와 화면이 깨지는 일을 방지한다.

P0는 강화 레벨을 0으로 유지하고 강화 구매를 서버에서 거절한다. 희귀 SkillId가 전체 데이터에 존재해도 P0에서는 발동·효과·스킬 설명을 활성화하지 않는다. P1용 데이터의 삭제나 능력치 재조정은 이번 범위 결정에 포함하지 않는다. 희귀 합성은 기존 비활성 규칙을 유지하고, 새로 제외한 기능의 버튼은 노출하지 않는다.

첫 Android 검증 기기는 미정(OPEN-008)이다. 기기 선정·실제 터치 완주 전에는 P0 최종 통과를 보류하되 독립적인 문서·PC·빌드 작업은 진행할 수 있다. 상세 판정과 실행 증거는 [백로그·QA](BACKLOG_QA.md) 및 [로드맵](production/ROADMAP.md)에 연결한다.

### 2.2 P1: 제작 가능한 최소 완성 게임

30웨이브, 20종 수호자, 4종 일반 적, 3종 보스, 모든 전투 룰, 2인 네트워크, 튜토리얼, 결과·도감·로컬 저장, 기본 3D 아트 및 성능 측정을 갖춘다. P0에서 제외한 공격 훈련·장치 가속, 희귀 4종 고유 스킬과 정식 3웨이브 튜토리얼도 포함한다. 이것이 문서에서 말하는 **MVP**다. 인터넷 공개 운영과 유료 상점은 별도 단계다.

### 2.3 P2: 온라인 출시 준비

전용 서버, 계정 인증, 인터넷 방 코드, 재접속, 보상 중복 방지, 서버 검증 저장, Android 실기기 QA, 서비스 모니터링을 추가한다. 이후 iOS를 검증한다. 공개 매칭은 인구가 충분할 때 추가하며, 최초에는 친구 방을 우선한다.

### 2.4 이번 범위 밖

PvP, 길드, 채팅, 시즌 패스, 유료 확률형 상품, 장비 옵션 파밍, 오픈월드, 물리 기반 유닛 이동, 자유 카메라, 수호자 수동 궁극기, 보스별 별도 스테이지는 포함하지 않는다. 첫 출시 이후 별도 기획으로 평가한다.

## 3. 플레이 경험과 게임 흐름

아래는 P1 이후의 목표 경험이다. P0에는 2.1절의 허용 기능만 적용하며 강화·고유 스킬·정식 로비/튜토리얼 구현을 P0 완료 조건에 추가하지 않는다.

### 3.1 1판 루프

```text
로비 → 연습/친구 방 선택 → 로딩·준비 → 10초 준비
 → 골드 소환 → 자동 공격 → 골드 획득
 → 배치 / 합성 / 강화 / 별조각 도전 / 신화 제작
 → 10·20·30웨이브 보스 → 승리 또는 패배 → 결과 → 다시 하기
```

### 3.2 시간대별 의도

| 시간 | 목표 행동 | 화면 피드백 |
|---|---|---|
| 준비 10초 | 시작 골드로 5회 소환, 공격 가능한 배치 | 추천 칸 표시, 다음 소환 가격 |
| 0~3분 | 첫 합성, 전투 강화 1단계 | 같은 유닛 3개 강조, 합성 결과 |
| 3~5분 | 첫 보스에 맞춰 딜 유지 또는 합성 | 보스 1웨이브 전 예고 |
| 5~10분 | 역할 분담, 별조각 도전, 전설 확보 | 아군 둔화/방어 약화 보유 아이콘 |
| 10~15분 | 신화 제작, 최종 보스 대비 | 재료 추적, 보스 체력, 위험 경고 |
| 결과 | 실패 이유 이해, 다음 판 시도 | 마지막 웨이브, 패배 원인, 내가 만든 최고 등급 |

이는 목표 경험이다. 첫 전설·신화 획득 시점은 실제 테스트에서 측정하며, 초기 데이터만으로 달성됐다고 판단하지 않는다.

### 3.3 반복 플레이 동기

전투 중의 선택 변화와 도감 발견을 우선한다. 영구 전투력 차이를 두지 않아 친구와 바로 합류할 수 있게 한다. 전투에서 유닛·조합식을 처음 사용하면 도감이 밝혀지고, 계정 레벨은 장식과 연습 안내를 해금한다.

## 4. 전장·카메라·배치

DEC-021에 따라 게임 동작은 [원작 대조 기록](product/ORIGINAL_REFERENCE.md)을 우선한다. 아래 칸 수·스택 상한·자동 배치 순서·이동 타이밍과 12장의 자체 UI는 원작 확인 전 초안이다. `1개 이동` 버튼, 잠금, 보스 우선 토글은 원작에서 확인하기 전 구현을 확정하지 않는다. 위치 교환을 없애는 단순화 제안은 채택하지 않는다. 모바일 화면·카메라의 개발 조건은 유지한다.

### 4.1 좌표와 맵

원작 대조 OBS-01에서 과거 보통 모드의 6열×3행 격자를 확인했다. 아래 4열×3행 좌표는 재현 기준이 아닌 기존 초안이다. 기준 버전·모드를 확인한 뒤 좌표·CellId·데이터·화면 QA를 함께 변경한다.

UE 단위는 cm. 바닥 Z=0, X는 좌우, Y는 위아래다. 모든 거리 판정은 Z를 제외한 평면 거리다.

| 요소 | 기준 |
|---|---|
| 공용 경로 | 닫힌 직사각형 Spline: (-350,-650)→(350,-650)→(350,650)→(-350,650)→시작점 |
| 경로 길이 | 4,000cm. 초기 프로토타입은 모서리 선형 구간 사용 |
| 플레이어 0 보드 | 4열×3행, 중심 Y=-330 |
| 플레이어 1 보드 | 4열×3행, 중심 Y=+330 |
| 칸 중심 X | -210, -70, +70, +210 |
| 보드 0의 행 Y | -470, -330, -190 |
| 보드 1의 행 Y | +190, +330, +470 |
| 칸 크기 | 140×140cm, 보드당 12칸 |
| 적 생성점 | 경로 거리 0과 2,000cm, 각각 생성 그룹 A/B |
| 이동 방향 | 두 그룹 모두 동일한 경로 증가 방향 |

```text
┌──────────────── 공용 순환 경로 ────────────────┐
│  ┌──────── 상대 보드 4×3 ────────┐             │
│  │  □   □   □   □               │             │
│  │  □   □   □   □               │             │
│  │  □   □   □   □               │             │
│  └──────────────────────────────┘             │
│             협동 상태 표시                     │
│  ┌───────── 내 보드 4×3 ─────────┐             │
│  │  □   □   □   □               │             │
│  │  □   □   □   □               │             │
│  │  □   □   □   □               │             │
│  └──────────────────────────────┘             │
└───────────────────────────────────────────────┘
```

두 플레이어는 같은 적을 공격한다. 적의 생성 그룹은 위치를 나눌 뿐, 처치 소유권이나 보상 소유권을 만들지 않는다. 경로 한 바퀴를 돌아도 적은 사라지지 않는다.

### 4.2 카메라

고정 원근 카메라를 사용한다. 기본 피치 -65도, 롤 0도, 수직 방향이 화면 위아래에 대응하도록 회전한다. 초기 수평 FOV 35도를 시작값으로 두고, 월드 전체 경로와 여백 100cm가 전장 패널 안에 들어오도록 거리를 산출한다. 시네마틱 카메라 전환은 도감에서만 사용한다.

각 클라이언트는 자신의 보드가 아래쪽이 되도록 카메라 Yaw를 180도 차이로 설정한다. 월드 좌표와 서버 CellId는 변경하지 않는다. 화면 드래그는 월드 평면으로 역투영한 뒤 칸을 찾는다. 해상도별 네 모서리 가시성을 검사하며 카메라 위치를 한 기기 값으로 고정하지 않는다.

DEC-014에 따라 화면비·DPI·SafeArea를 반영한 실제 전장 패널 영역으로 경로와 두 보드의 구도를 맞춘다. 화면 크기나 안전 영역이 바뀌면 레이아웃과 카메라 맞춤을 갱신한다. 입력 역투영도 갱신된 뷰포트·카메라와 같은 좌표 변환을 사용한다. 고정 카메라는 플레이어가 자유롭게 움직이지 않는다는 뜻이며, 화면 크기 변화에 대응하는 자동 맞춤을 막지 않는다.

### 4.3 슬롯·개체·스택

- 일반/희귀/영웅은 같은 UnitId끼리 한 칸에 최대 3개까지 배치한다.
- 전설/신화는 한 칸에 1개만 배치한다.
- 개체는 각각 InstanceId·공격 타이머·스킬 타이머를 가진다. 스택 수는 공격력 배율용 가짜 숫자가 아니다.
- 보드당 최대 36개체, 팀 최대 72개체. 상위 등급이 늘면 실제 최대 개체 수는 감소한다.
- 동일 칸의 2~3개 모델은 작은 삼각 배치로 표시한다. 피해 범위·사거리는 모두 칸 중심에서 계산한다.
- 자기 보드만 배치·판매·합성할 수 있다. 상대 보드 선택은 정보 조회와 핑만 허용한다.

### 4.4 자동 배치와 이동

원작 영상 OBS-08에서 서로 다른 수량의 유닛이 재배치되는 전후를 확인했다. 다만 터치 제스처·명령 수를 확인하지 못했으므로 단일 교환 요청의 정확한 조건까지 확정하지 않는다. 같은 종류의 수용량 초과 이동·개별 이동 입력은 별도 관찰이 필요하다.

OBS-02/03은 선택 사거리와 합성/판매 UI의 화면 근거다. 아래 자동 배치 순서·이동 단위·0.30초 제한은 이 화면으로 검증되지 않았다. 합성 버튼 존재를 재료 선정·결과 칸 규칙의 근거로 확대하지 않는다.

소환 시 동일 UnitId의 여유 스택 중 CellId가 가장 작은 칸, 그 다음 가장 작은 빈 CellId를 사용한다. 이동은 기본적으로 스택 전체를 옮긴다. 같은 종류 목적지에 전체가 들어가면 합쳐 배치하고, 공간이 부족하면 이동을 거절한다. 다른 종류 칸은 두 스택을 교환한다. 상세 패널의 `1개 이동` 버튼으로만 개별 이동한다.

CellId=`BoardIndex*12+RowIndex*4+ColumnIndex`, RowIndex는 월드 Y 증가 순서다. 화면의 좌우·상하는 카메라 회전과 별개다. 이동은 논리적으로 즉시 처리하고 모델만 0.15초 보간한다. 유닛마다 이동 후 0.30초 공격 금지, 이동 재요청 간격 0.30초. 남은 공격/스킬 쿨다운은 보존하며 이동으로 취소·초기화하지 않는다.

DEC-020의 Move 요청에는 MoveMode=Stack/Single, SourceInstanceId, DestinationCellId를 정의했다. 이는 기존 초안의 전송 계약이다. ExpectedBoardRevision을 검사해 오래된 선택을 임의 적용하지 않는 기술 기준은 유지한다. DEC-021에 따라 전체/개별 이동의 존재·입력·서버 배치 결과는 원작을 확인한 뒤 계약과 함께 확정한다. 미확인 재료 교환 기능의 배치 예외를 새로 설계하지 않는다.

## 5. 시간·웨이브·승패 판정

DEC-021/DEC-022에 따라 게임 규칙은 [Android 2.0.11 보통 모드 대조 기록](product/ORIGINAL_REFERENCE.md)을 우선한다. 아래 화상·유닛 수치와 중첩 방식은 기존 자체 설계 초안이며 원작에서 확인한 규칙이 아니다. 이번 정리는 그 초안의 예약 피해와 만료 처리 간 충돌을 해소하는 기술 명세이며, 원작 확인 없이 해당 스킬의 구현을 확정하지 않는다.

DEC-019의 P0는 FinalWave=10, 일반 4종·희귀 4종의 기본 공격과 능력치 차이만 사용한다. 아래 전체 전투 명세 중 강화·고유 스킬·상태이상·오라는 P1 범위이며 P0에서 발동하지 않는다. Preparing의 강화 구매도 P0에서는 거절한다. 승패·과밀·마감 경계 규칙은 P0에도 적용하되 최종 웨이브를 10으로 치환한다.

### 5.1 상태 전이

| 상태 | 진입 | 종료 |
|---|---|---|
| Loading | 방 인원 2명 또는 연습+봇 확정 | 두 참가자 준비 완료, 30초 초과 시 방 복귀 |
| Preparing | 전장 생성 완료 | 10초 경과 |
| Running | 웨이브 1 시작 | 승패 또는 서버 중단 |
| Result | 결과 확정, 게임 변경 명령 거절 | 각자 로비/다시 하기 선택 |
| Aborted | 서버 종료·필수 데이터 오류 | 오류 사유를 표시하고 로비로 이동 |

Preparing에서는 골드 소환·배치·판매·강화가 가능하다. 전투와 시간 보상은 Running에서 시작한다. 온라인 전투 중 메뉴를 열어도 게임은 멈추지 않는다. 연습 모드에서만 일시정지를 허용한다.

### 5.2 시간 규칙

웨이브 w 시작 시각=`RunStartTime+30*(w-1)`초. 기본 30초마다 다음 웨이브가 시작되며, 이전 웨이브 적이 남아 있어도 계속된다. 일반 웨이브는 시작 후 0~20초에 표에 정해진 적을 분산 생성한다. 모든 시각은 서버 전투 시간을 따른다.

보스 웨이브 10/20/30은 새 일반 적을 생성하지 않고 시작 시 보스 2마리를 생성한다. 기존 일반 적은 남는다. 보스 둘을 30초 안에 모두 처치해야 한다. 10/20웨이브 보스를 일찍 잡아도 다음 웨이브 시작은 앞당기지 않는다.

### 5.3 승패

| 판정 | 정확한 규칙 |
|---|---|
| 과밀 패배 | 살아 있는 적이 100마리 이상인 상태가 연속 3.0초 지속 |
| 과밀 해제 | 99마리 이하가 된 틱에 누적 시간을 0으로 초기화 |
| 보스 패배 | 해당 보스 웨이브 마감 시각에 보스가 한 마리라도 생존 |
| 최종 패배 | 30웨이브 마감 시각에 일반 적 또는 보스가 한 마리라도 생존 |
| 승리 | 30웨이브 생성이 끝났고 적 전체가 0이며 패배가 먼저 확정되지 않음 |
| 중단 | 서버가 복구 불가능하게 종료되거나 필수 데이터 오류 발생 |

아군 수호자는 적에게 공격받지 않으며 HP·사망·부활을 갖지 않는다. 기지 HP나 누적 탈출 횟수는 사용하지 않는다. 패배 UI는 `적 과밀`, `보스 처치 시간 초과`, `최종 잔여 적` 중 우선 판정된 한 원인을 표시한다.

### 5.4 같은 틱의 처리 순서

20Hz 논리 스텝마다 입력 검증·명령 적용 → 스폰 → 이동·상태 만료 → 예정 DoT·화상 만료 정리 → 예정 공격/스킬 → 피해·사망 정리 → 과밀 갱신 → 마감 패배 검사 → 승리 검사 → 웨이브 종료 보상 순서로 처리한다. 화상은 8.3.1에 따라 만료 시각의 예약 틱을 처리한 뒤 제거한다. 다른 상태의 지속시간을 연장하는 규칙은 아니다. 시각 경계를 넘긴 스텝에서는 마감 시각 이하에 예약된 타격만 먼저 처리하고 마감을 판정한다. 마감 이후 타격으로 소급 승리하지 않는다.

동일 시각의 적 사망은 먼저 반영되므로 마감 시각에 정확히 사망한 마지막 보스는 성공이다. 웨이브 경계에서는 이전 웨이브의 마감 이하 이벤트·승패·보상을 먼저 처리하고, 전투가 계속될 때만 다음 웨이브의 같은 시각 스폰을 시작한다. 아직 이전 보스의 실패를 검사하지 않은 상태에서 다음 웨이브 적을 먼저 생성하지 않는다. 이미 Result 상태이면 이후 패킷·타이머·사망 이벤트를 모두 결과에 반영하지 않는다.

## 6. 재화와 경제

DEC-021에 따라 아래 경제·확률·보장·합성 배치 수치는 원작 대조 전 초안으로 보존한다. [원작 대조 기록](product/ORIGINAL_REFERENCE.md)이 우선하며, 특히 모든 등급 골드 환급·원하는 종류 재료 교환·추적 자동 잠금은 원작 규칙으로 사용할 수 없다. 실제 보상·입력·결과 확인 후 생성 데이터와 QA를 함께 갱신한다.

DEC-019에 따라 공격 훈련·장치 가속은 P1 범위다. P0에서는 두 강화 레벨을 0으로 유지하고 구매 UI를 숨기며, 서버도 직접 구매 요청을 상태 변경 없이 거절한다. 아래 강화 비용·효과·상한은 P1 설계값으로 유지한다. P0는 전용 소환 프로파일과 일반→희귀 합성·배치·판매를 사용한다.

### 6.1 전투 재화

| 재화 | 시작 | 수입 | 소비 | 전투 종료 |
|---|---:|---|---|---|
| 골드 | 개인당 140 | 팀의 일반 적 처치마다 각 플레이어 +1, 웨이브 종료 보상 | 일반 소환, 전투 강화, 재료 교환 | 소멸 |
| 별조각 | 0 | 짝수 웨이브 종료 +1, 보스 웨이브 성공 시 추가 +4 | 도전 1회당 2개 | 소멸 |

골드와 별조각은 모두 개인 소유이며 다른 플레이어에게 전송할 수 없다. 전투 종료 시 사라진다. 적을 실제로 때린 플레이어와 무관하게 두 플레이어에게 같은 처치 골드를 주므로 막타 경쟁이 없다. 봇 자리에도 같은 규칙을 적용한다.

웨이브 w 종료 골드=`20+3*w`. 보스의 별도 처치 골드는 0이며 웨이브 보상으로만 지급한다. 보스 둘을 잡는 순간과 웨이브 종료가 중복 지급을 일으키지 않도록 `RewardedWaveIds`를 기록한다. 최종 승리 시에는 30웨이브 보상을 즉시 한 번 정산한다.

### 6.2 소환 가격

원작 대조 OBS-04에 비용 64 화면이 있어 아래 상한 60은 원작 재현값으로 사용할 수 없다. 실제 증가식·상한은 별도 확인하며 64를 새 상한으로 추정하지 않는다.

`Price(n)=min(20+2*n,60)`이며 n은 해당 플레이어가 성공적으로 구매한 일반 소환 횟수다. 첫 5회 비용은 20+22+24+26+28=120골드로 20골드가 남는다. 판매·합성·도전은 n을 줄이지 않으며, 거절된 소환도 n을 늘리지 않는다.

### 6.3 전투 강화

등급 전체가 아닌 **내 모든 수호자**에 적용하는 두 항목으로 시작한다. 전투 시작 시 0레벨로 초기화된다.

| 항목 | 최대 레벨 | 다음 단계 비용 | 효과 |
|---|---:|---|---|
| 공격 훈련 | 8 | 60+40*현재레벨 | 레벨당 기초 공격력 +10%, 합연산 |
| 장치 가속 | 5 | 80+60*현재레벨 | 레벨당 공격속도 +5%, 합연산 |

공격 훈련 8레벨은 공격력 1.8배다. 장치 가속은 기본 공격 간격에만 적용하며 초 단위 스킬 쿨다운은 줄이지 않는다. 타인의 버프와 적용 순서는 전투 절을 따른다.

### 6.4 판매·교환

OBS-07/09에 판매 재화와 개체별 소비의 영상 근거를 추가했다. 아래 전 등급 골드 환급표는 보류한 자체 초안이며, 구현할 판매 테이블은 재화 종류와 수량을 함께 정의해야 한다. 원작 기준 버전·유물 조건을 확인한 뒤 생성기·JSON·검산·QA를 함께 바꾼다.

추가 화면·본문 대조는 [원작 대조 기록](product/ORIGINAL_REFERENCE.md)의 OBS-05와 S7을 따른다. 판매 보상에는 재화 구분이 필요하며, 한 장의 판매 로그로 모든 등급의 환급 수량을 결정하지 않는다.

**원작 대조 대기:** 판매 재화·수량은 등급별로 확인한다. 아래 `재료 교환`은 원작 근거 없는 자체 제안이므로 구현 대상에서 보류한다. 기존 수치 보존은 기능 추가 결정이 아니다.

개체 판매 환급은 일반 5 / 희귀 15 / 영웅 45 / 전설 120 / 신화 300골드다. 최초 획득 경로와 무관하다. 3개 일반을 희귀로 합쳐 팔면 15골드이므로 합성만으로 재화를 늘릴 수 없다. 전설·신화 판매는 길게 누르기 확인을 요구하며, 한 번에 1개체를 판매한다.

보류한 기존 제안: 재료 막힘을 완화하기 위해 영웅 또는 전설 1개를 **동일 등급의 원하는 다른 종류**로 바꾸는 `재료 교환`. 영웅 100골드, 전설 200골드, 둘을 합쳐 개인당 판 전체 2회 제한. 당시 초안은 보장 카운터 유지·새 유닛 기준 스킬 타이머 시작·결과/가격/횟수 사전 표시를 제안했다. 이 문단은 원작 확인 전 구현 명세로 사용하지 않는다.

### 6.5 경제 검산 기준

전체 일반 적을 처리하고 30웨이브를 성공하면 웨이브 골드 총합 1,995를 받는다. 시작 140과 일반 적 882마리 처치 골드까지 합하면 개인당 3,017이다. 최종 웨이브 종료 골드 110을 제외한 전투 중 수입 상한은 2,907이며, 판매 없이 소환만 구매하면 최대 55회다. 동봉 검증 보고서에서 자동 계산한다. 이 상한은 강화·교환을 전혀 하지 않은 가정이며 권장 구매량이 아니다.

별조각은 짝수 웨이브 15개 + 보스 추가 12개 = 총 27개. 다만 30웨이브 종료에 받는 5개는 결과 화면에서 소멸하므로 **전투 중 실제 사용할 수 있는 별조각은 22개, 도전은 최대 11회**다. 30웨이브 보상은 정산 일관성을 위한 값이며 최종 보스 공략 자원으로 계산하지 않는다.

## 7. 랜덤 소환·합성·조합

### 7.1 골드 소환

| 등급 | 내부 코드 | 기본 확률 | 슬롯당 최대 |
|---|---|---:|---:|
| 일반 | Common | 82% | 3 |
| 희귀 | Rare | 15% | 3 |
| 영웅 | Epic | 3% | 3 |
| 전설 | Legendary | 0% | 1 |
| 신화 | Mythic | 0% | 1 |

등급을 뽑은 후 해당 등급의 4종에서 각각 25%로 추첨한다. 예를 들어 특정 일반 1종의 기본 확률은 20.5%다. 연속 일반 결과가 14회이면 **다음 일반 소환은 희귀 85%·영웅 15%**로 변경한다. 희귀 이상을 얻으면 연속 일반 횟수를 0으로 초기화한다. 그 외 횟수 누적과 UI 표시는 서버에서 관리한다.

서버 추첨은 0~9,999 정수를 사용하고 누적 정수 가중치로 등급을 결정한다. 확률 테이블은 각 행 합계 10,000을 보장한다. UI는 보장 적용 여부에 따라 이번 시도의 실제 확률을 보여준다. 보장 카운터를 포함한 장기 실효 확률은 기본 표시 확률과 다르며 별도로 측정한다.

### 7.2 가득 찬 보드에서 소환

**일반 소환과 별조각 도전은 빈 칸이 최소 1칸 있어야 요청할 수 있다.** 일부 스택에 여유가 있어도 빈 칸이 없으면 거절한다. 모든 가능한 추첨 결과를 수용할 수 있게 만드는 단순한 규칙이다. 빈 칸이 있더라도 결과가 기존 스택에 들어갈 수 있으면 먼저 그 스택으로 들어간다.

공간 검사와 비용 검사를 통과한 요청만 자원을 차감하고 RNG를 소비한다. UI 문구는 `새 종류가 들어갈 빈 칸이 필요합니다. 합성하거나 판매해 주세요.`로 통일한다. 결과를 본 뒤 배치 실패를 이유로 다시 추첨하는 동작은 없다.

### 7.3 3개 합성

OBS-06은 한 칸의 재료가 소비된 뒤 그 칸에 결과가 나타난 사례다. 아래 분산 재료 선정 순서·다른 칸 선택·만석 거절 조건까지 원작에서 확인한 것은 아니다. 구현 검수에서는 관찰한 사례와 미확인 경계 조건을 구분한다.

동일 소유자·동일 UnitId의 개체 3개를 소비하여 다음 등급 1개를 생성한다. 일반→희귀, 희귀→영웅, 영웅→전설까지만 가능하다. 성공률 100%, 결과 종류는 상위 등급 4종 중 균등이다. 전설끼리 합성하여 신화가 되는 규칙은 없다.

합성 버튼을 눌렀을 때 선택 개체를 우선 포함하고, 나머지는 같은 UnitId 중 CellId·InstanceId 오름차순으로 제안한다. 사용자는 소비될 3개를 미리 볼 수 있다. **소비 후 결과를 배치할 빈 칸이 생기는 조합만 허용**한다. 선택한 칸이 완전히 비면 거기에 생성하고, 아니면 소비로 비게 되는 가장 작은 CellId에 생성한다. 어느 칸도 비지 않으면 자원·개체·RNG 변화 없이 거절한다.

기존 초안의 `재료 추적 → 자동 잠금 → 합성·판매 제외` 연결은 DEC-021로 보류한다. 공략에서 확인한 것은 신화 필요 재료의 필드 표시이며 소비 제한까지 확인한 것이 아니다. 실제 수동 잠금의 존재와 소비 규칙은 원작 관찰 후 정한다. 합성 중 요청 중복은 동일 RequestId 결과를 재전달하는 기술 기준을 유지한다.

DEC-020에 따라 합성 요청은 SelectedInstanceId와 미리 보여준 정확한 ConsumedInstanceIds 3개를 보낸다. 선택한 ID는 소비 목록에 포함돼야 하며 목록 순서로 선택 기준을 추측하지 않는다. 서버가 선택 개체의 현재 칸과 보드 버전을 검사하고 위 배치 규칙을 적용한다. 사라진 재료를 다른 개체로 대체하거나 클라이언트가 결과 유닛·결과 칸을 지정하는 동작은 허용하지 않는다.

### 7.4 별조각 도전

| 결과 | 기본 확률 | 5번째 보장 시 |
|---|---:|---:|
| 실패 | 50% | 0% |
| 희귀 | 30% | 0% |
| 영웅 | 17% | 90% |
| 전설 | 3% | 10% |

비용은 항상 별조각 2개. 일반 실패는 유닛을 주지 않으며 비용은 반환하지 않는다. **영웅 이상을 4회 연속 얻지 못하면 다음 시도 보장**이므로 희귀 결과도 보장 카운터를 증가시킨다. 영웅/전설을 얻으면 0으로 초기화한다. 골드 소환의 보장 카운터와 별개다.

별조각은 이번 MVP에서 플레이로만 얻는다. 실패 시 짧은 낙하 연출과 `영웅 이상 보장까지 N회`를 표시하고, 성공 시 등급에 맞는 소환 연출을 재생한다. 연출을 건너뛰어도 결과는 이미 서버에서 확정된다.

### 7.5 신화 제작 레시피

| 결과 | 전설 재료 | 영웅 재료 | 희귀 재료 | 역할 |
|---|---|---|---|---|
| 태양 용광로 | 용광로 거인 L01 | 화약 연금술사 E03 | 불씨 마도사 R03 | 광역·지속 피해 |
| 폭풍 지휘자 | 천둥 지휘관 L03 | 폭풍 사수 E02 | 톱니 궁수 R02 | 보스·연쇄 |
| 겨울의 파수꾼 | 서리 여왕 L02 | 서리 기사 E01 | 강철 파수병 R01 | 둔화·안정성 |
| 별빛 설계자 | 별의 설계사 L04 | 태엽 악사 E04 | 태엽 기술자 R04 | 공격 지원 |

각 재료 1개씩 소비하고 추가 비용은 없다. 전설 재료가 점유한 칸을 결과 칸으로 사용하므로 최소 한 칸이 확보된다. 같은 신화를 여러 개 만들 수 있으나 동일 지원 효과는 중첩되지 않는다. 전설을 재료로 소비해 DPS가 바뀌는 것을 미리 볼 수 있도록 제작 패널에 결과 역할과 소비 목록을 동시에 표시한다.

### 7.6 모든 변경 명령의 공통 원칙

소환·합성·제작·판매·교환·강화·이동은 서버 한 트랜잭션으로 수행한다. 검증 실패 시 비용·보드·카운터·RNG 상태가 모두 바뀌지 않는다. 연출 때문에 로직 완료를 기다리지 않는다. 모델 로딩이 늦으면 임시 피규어를 사용하고 확정 결과는 유지한다.

명령별 필수 정보·처리 순서·결과 코드의 원본은 DEC-020의 [명령 계약](technical/ARCHITECTURE.md) 16.2절이다. Summon.Source는 Gold/Star로 구분하며 서버가 모드·비용·확률·보장을 선택한다. P0에서는 Star·Craft·Swap·Upgrade를 거절한다. Swap은 재료 1개 교환 명령이며 이동 중 스택 위치 교환과 구분한다.

응답 유실 시 같은 ConnectionEpoch·RequestId·내용으로 재확인하고 다른 번호로 자동 구매하지 않는다. 결과 기록이 만료됐으면 상태 동기화 후 재선택한다. 별조각 추첨의 실패는 비용·카운터가 반영된 정상 명령 결과이므로 요청 거절·환불과 구분한다.

## 8. 전투·피해·상태이상

### 8.1 공격 판정

수호자는 고정 칸에서 공격한다. 사거리는 칸 중심과 적 중심 사이의 평면 거리다. 표적 후보는 살아 있고 사거리 안에 있는 적이며, 기본은 `보스 우선`을 끈 `가장 가까운 적`이다. 거리가 같으면 SpawnSerial이 작은 적을 선택한다. 선택 패널에서 보스 우선을 켜면 사거리 내 보스부터 찾고, 없으면 기본 규칙으로 돌아간다.

이미 유효한 표적은 다음 공격까지 유지한다. 공격 시작 시 범위·생존을 검사하고 피해를 즉시 적용한다. 애니메이션과 투사체는 결과 표현이다. 시각 투사체가 다른 적에 닿더라도 추가 피해를 주지 않는다. 장거리 발사체는 0.15초 이내에 닿도록 조정하여 피해가 먼저 들어가는 차이를 줄인다.

초기 생성 시 기본 공격 준비 시간은 0.25초다. 기본 공격과 자동 스킬이 같은 스텝에 준비되면 기본 공격 후 스킬을 처리한다. 상태를 가지는 스킬은 서버의 별도 타이머로 관리하고 AnimNotify를 피해 권한으로 사용하지 않는다.

### 8.2 피해 공식

```text
ATK = BaseAttack * (1 + 0.10*AttackUpgradeLevel) * (1 + StrongestAttackBuff)
AttackInterval = BaseInterval / (1 + 0.05*HasteLevel + StrongestHasteBuff)
AttackInterval 최소값 = 0.25초
Raw = ATK * SkillCoefficient
PhysicalMultiplier = 100 / (100 + max(0, Armor - StrongestArmorBreak))
MagicMultiplier = 1 - clamp(MagicResistance, 0, 0.75)
Final = max(1, round_half_up(Raw * 해당 방어 배율))
```

기본 공격 계수는 1이다. 치명타·회피·속성 상성·관통은 MVP에 없다. DoT도 시전 시점 ATK를 저장하고 각 틱에 대상의 현재 저항을 적용한다. 공격 훈련은 기본 공격과 공격력 계수 스킬 모두에 적용된다. 공격속도 강화는 초 단위 자동 스킬·DoT 간격을 바꾸지 않는다.

예: 공격력 100, 공격 훈련 2, 공격 버프 10%, 물리 계수 1, 방어력 50, 방어 약화 20이면 `round(100*1.2*1.1*100/130)=102` 피해다.

### 8.3 효과 중첩

| 효과 | 기본 처리 | 보스 |
|---|---|---|
| 둔화 | 최대 수치 하나 적용, 다른 원천은 남은 시간 별도 관리, 상한 50% | 적용 강도 상한 25% |
| 기절 | 이동 정지, 중첩은 남은 시간과 새 지속시간 중 큰 값 | 면역 |
| 방어 약화 | 가장 높은 절대 감소 수치 하나, 방어력 최저 0 | 동일 적용 |
| 화상 | SkillId+시전자 기준 관리하되 대상당 가장 강한 1개만 피해 | 동일 적용 |
| 공격력 버프 | 수치가 가장 큰 하나, 자신 포함 사거리 안 아군 | 동일 적용 |
| 공격속도 버프 | 수치가 가장 큰 하나, 자신 포함 사거리 안 아군 | 동일 적용 |

효과는 남은 시간이 끝나면 해제하되 화상의 만료 시각 예약 틱은 8.3.1을 따른다. 강한 효과가 끝나도 아직 살아 있는 약한 효과가 있으면 다시 적용한다. 동일 시전자의 재적용은 지속시간을 갱신하며 즉시 DoT 추가 틱을 발생시키지 않는다. 죽은 대상의 상태와 예약 이벤트는 제거한다.

적은 아군을 때리지 않으므로 기절은 적 이동만 막는다. 적 보스 스킬 주기는 이동 상태와 무관하지만 보스는 기절 면역이다. 지원 오라는 0.25초마다 범위 갱신, 빠져나온 대상에서 즉시 다음 갱신에 제거한다.

### 8.3.1 화상의 마지막 틱과 종료 경계

이 절은 P1 상태이상 실행기의 검수 기준이다. P0에는 화상을 활성화하지 않는다. 화상 강도·동률·재적용의 데이터 해석은 [데이터 명세](DATA_SCHEMA.md)의 DT_Skills 계약을 따른다.

- 최초 적용 시각을 T라 하면 첫 틱은 `T+DotIntervalSeconds`다. 재적용·다른 원천·사망·전투 종료가 없는 현재 3초 화상은 T+1, T+2, T+3초에 각각 한 번 피해를 주고 제거한다. T 시점의 광역 직접 피해는 이 3틱에 포함하지 않는다.
- 예약 시각이 `ExpireTime`과 같은 틱은 유효하다. 서버 논리 시간으로 예약 시각 순서대로 처리하며, 프레임 지연으로 실행 시각이 늦어졌다는 이유로 유효했던 마지막 틱을 버리지 않는다. `ExpireTime` 이후 예약은 피해를 만들지 않는다. 전투 마감 이후 예약도 5.4에 따라 제외한다.
- 같은 시각의 화상 원천들은 만료 제거 전 상태에서 강도·동률 규칙으로 활성 원천 하나를 결정한다. 해당 시각에 예약이 있는 활성 원천만 피해를 주며, 억제된 원천의 예약 틱도 소비한다. 그 시각의 예약들을 처리한 후 만료 원천을 제거하므로 약한 원천이 같은 시각에 추가 피해를 주지 않는다. 억제 기간의 피해는 나중에 보충하지 않는다.
- 같은 시각에 기존 틱과 스킬의 화상 재적용이 겹치면 기존 틱을 먼저 소비하고 재적용한다. 재적용 자체는 피해를 만들지 않으며 이미 처리한 예약을 다시 등록하지 않는다. 아직 예정된 NextTickTime은 유지한다. 마지막 틱까지 소비해 제거한 원천을 같은 시각 다시 적용하면 첫 예약은 그 시각에서 DotIntervalSeconds 뒤다. 중복 콜백에서도 동일 대상·원천·예약 틱은 한 번만 소비한다.
- 각 피해 직후 대상의 생존을 갱신한다. 사망한 대상의 후속 예약은 취소하고, 풀에서 재사용한 액터에 이전 대상의 예약을 적용하지 않는다. Result 확정 이후에는 남아 있는 예약으로 피해·사망·보상을 추가하지 않는다.

검수 시 적용 시각, 원천, 예약 시각, 만료 시각, 활성/억제 여부, 실제 피해 횟수와 대상 생존 상태를 기록한다. 특히 [QA-DMG-11](BACKLOG_QA.md#QA-DMG-11)~[QA-DMG-14](BACKLOG_QA.md#QA-DMG-14)는 구현 후 실행할 항목이며 문서 정적 검사로 통과 처리하지 않는다.

### 8.4 공간 검색·정렬

전장 전체 적 목록을 중앙 관리하고 공간 버킷 또는 경로 구간으로 후보를 줄인다. 광역 타격 대상은 중심과의 거리·SpawnSerial 순서로 제한 수만큼 선택한다. 연쇄는 최초 대상 뒤 이전 타격점 250cm 이내의 가장 가까운 미타격 대상을 고른다. 같은 적을 한 연쇄에서 두 번 때리지 않는다.

### 9.2 스킬 해석 세부

- 공격 횟수형은 **유효 표적에 수행한 기본 공격**만 센다. 추가탄·연쇄·DoT는 카운터를 증가시키지 않는다. 카운터가 N이 되면 발동하고 0으로 초기화한다.
- 추가탄 R02는 현재 표적이 살아 있으면 다시 타격하며 죽었으면 사거리 내 새 표적 하나를 찾는다. 없으면 소멸한다.
- 초 단위 스킬은 생성 뒤 전체 쿨다운이 지나야 처음 준비된다. 준비됐지만 표적이 없으면 준비 상태를 유지하고 유효 표적 발견 시 발동한다. 공격속도는 주기를 줄이지 않는다.
- 광역 중심은 현재 유효 표적의 위치다. 기본 공격과 독립적으로 대상을 찾는다. 둔화 전용 E01/L02는 직접 피해가 0이다.
- 연쇄 계수는 각 대상에 동일 적용한다. E02/L03은 기본 공격과 별도의 추가 스킬 타격이며 첫 대상에도 연쇄 피해가 한 번 들어간다.
- 오라는 최대 중첩 규칙을 사용한다. 악사 여러 명이나 설계사·설계자를 함께 놓아도 공격력 버프는 30%까지다.

## 10. 적·보스·웨이브 구성

### 10.1 일반 적

일반 적 기준 HP=`round_half_up(70*1.12^(w-1))`. 각 적의 최종 HP는 이 기준값에 유형 배율을 곱한 뒤 반올림한다. 속도와 방어는 유형의 고정값이다.

| ID | 이름 | HP 배율 | 속도 cm/s | 물리 방어 | 마법 저항 | 특징 |
|---|---|---:|---:|---:|---:|---|
| N01 | 먼지 인형 | 1.00 | 150 | 0 | 0% | 기준 적 |
| N02 | 질주 팽이 | 0.75 | 220 | 0 | 0% | 사거리 체류 시간 감소 |
| N03 | 철갑 장난감 | 1.60 | 120 | 60 | 0% | 마법·방어 약화 필요 |
| N04 | 절연 인형 | 1.20 | 150 | 0 | 35% | 물리 화력 필요 |

적은 서로 밀거나 충돌하지 않는다. 경로 거리로 이동하고 약간의 옆 오프셋만 시각적으로 부여한다. 적의 시각 크기는 일반 45~65cm, 보스 110~140cm다. 유닛 또는 적의 외형 크기가 사거리·공격 범위를 바꾸지 않는다.

### 10.2 웨이브 수량과 혼합

일반 웨이브는 생성점당 `12+floor((w-1)/3)`마리, 팀 전체는 두 배다. 보스 웨이브는 보스 2마리만 새로 생성한다. 1~3은 N01 100%, 4~9는 N01/N02=75/25%, 11~19는 N01/N02/N03=50/25/25%, 21~29는 네 유형 25%씩이다.

구성 비율은 실제 정수 개체 수로 변환한다. 각 유형의 수량을 내림한 뒤 남는 수를 소수 부분이 큰 유형부터 배정하며 동률은 N01→N04 순서다. 스폰 순서는 유형별 편중을 줄이도록 이미 배정한 수량의 비율이 가장 낮은 유형부터 골라 고정 순서를 만든다. RNG를 사용하지 않는다.

생성점당 K마리는 `t_i=20*i/(K-1)`, i=0..K-1 시점에 생성한다. 두 생성점은 동일 시각·구성이다. 생성점별 잔여 수량과 예약 시각은 웨이브 시작 때 확정한다.

### 10.3 보스

| 웨이브 | 보스 | 각 HP | 속도 | 방어/마저 | 패턴 |
|---:|---|---:|---:|---|---|
| 10 | 고철 골렘 B01 | 6,000 | 100 | 20 / 10% | 별도 능력 없음. 첫 화력 검사 |
| 20 | 폭주 기관장 B02 | 30,000 | 150 | 35 / 15% | 8초마다 3초간 이동속도 1.5배 |
| 30 | 균열 감독관 B03 | 90,000 | 120 | 40 / 20% | 10초마다 4초간 일반 적 전체 속도 +20% |

모든 보스는 기절 면역, 둔화 최대 25%. B02의 속도 폭주는 기본 속도×1.5×(1-둔화) 순서다. B03은 보스 자신과 다른 보스를 가속하지 않으며, 같은 효과 두 개는 겹치지 않는다. 30웨이브 신규 일반 적이 없으므로 B03 패턴은 이전 웨이브 잔여 적을 빨리 정리하도록 유도한다.

보스는 각 생성점에 한 마리씩 나타난다. 상단 UI는 두 체력을 별도 막대로 표시하고 남은 제한 시간 하나를 공유한다. 화면에 한 마리가 가려져도 남은 수와 체력을 확인할 수 있다.

### 10.4 밸런스 기준

기본 적의 한 바퀴 시간은 약 26.7초다. 10웨이브 보스 두 마리는 30초 동안 총 12,000HP, 20은 60,000HP, 30은 180,000HP를 처리해야 한다. 최종 보스의 **저항 적용 후 팀 평균 실효 DPS 하한은 6,000**이며, 준비 시간·사거리 이탈을 포함하면 필요한 보유 화력은 더 높다. 기본 공격 표의 DPS 합계를 클리어 가능 화력으로 그대로 보지 않는다.

검증 시 팀별 DPS, 사거리 내 체류율, 보스에 적중한 피해 비중, 도전 보장 발동 횟수, 전설·신화 완성 시각을 함께 기록한다. 첫 밸런싱은 보스 HP·웨이브 HP 성장률·골드 수입을 순서대로 조정하고, 한 실험에서 모든 변수를 동시에 바꾸지 않는다.

## 11. 협동·매칭·이탈 처리

### 11.1 협동 규칙

공용 적 수와 승패를 공유한다. 둔화·방어 약화는 누구의 공격에도 도움이 되고, 지원 오라는 범위 내 상대 수호자에게도 적용된다. 개인 골드·보드·강화 수준은 분리한다. 아군 유닛을 강제로 합성하거나 재화를 사용하지 않는다.

핑은 `보스 집중`, `둔화 필요`, `합성 준비`, `좋아요` 네 가지로 제한한다. 최근 핑을 3초 표시하고 개인당 2초 쿨다운, 큐에 최대 3개만 둔다. 일반 채팅은 포함하지 않는다.

### 11.2 접속 단계

P0/P1에서는 PC 개발 빌드의 리슨 서버 + 로컬 접속으로 검증한다. 호스트 종료 시 세션이 끝나며 호스트 이전은 구현하지 않는다. 연습 모드는 로컬 서버와 보조 봇으로 같은 전투 코드를 사용한다.

P2에서는 친구 방 생성 → 6자리 방 코드 → 코드 입력 → 준비 완료 → 전용 서버 배정 → 전투로 이어진다. 방 코드 만료 10분, 정원 2명, 전투 시작 후에는 원래 참가자의 재접속만 허용한다. 무작위 타인의 중도 입장은 없다. 매칭 SDK만으로 전용 게임 서버 호스팅이 자동으로 해결된다고 가정하지 않는다.

### 11.3 재접속·이탈

전용 서버에서 접속이 끊기면 기존 수호자 공격과 전투 시간은 계속 흐른다. 5초 뒤 해당 자리에 보조 봇을 활성화한다. 60초 동안 원래 계정의 복귀를 허용하고, 복귀하면 현재 보드·재화·보장 카운터·쿨다운의 전체 스냅샷을 전송한 뒤 다음 논리 스텝부터 봇을 끈다.

60초 경과 뒤에는 복귀를 거절하고 그 자리는 결과까지 봇이 맡는다. 이탈자에게는 이탈 확정 시점까지 완료한 웨이브 기준 실패 보상만 지급한다. 남은 참가자는 실제 최종 결과 보상을 받는다. 자발적 나가기는 즉시 이탈 확정으로 처리한다. 둘 다 확정 이탈하면 서버를 종료한다.

### 11.4 보조 봇의 명시적 우선순위

1초마다 한 번 판단하고 명령은 인간과 같은 서버 검증 경로를 이용한다. 우선순위는 빈 칸 없고 합성 가능하면 합성 → 빈 칸 있고 골드가 다음 소환 가격의 2배 이상이면 소환 → 공격 훈련 현재 레벨이 `floor(Wave/5)`보다 작고 비용이 있으면 강화 → 가능한 신화 제작 → 영웅 이상 보장 도전 또는 별조각 4개 이상이면 도전 → 가능한 합성 순이다. 어느 것도 불가능하면 대기한다.

봇은 재료 교환과 판매를 하지 않으며 추적 잠금을 무시하지 않는다. P0에서는 존재하지 않는 행동을 건너뛴다. 결과 화면에 봇이 참여한 시간을 표시하여 플레이 테스트 분석에서 사람 2인 세션과 구분한다.

## 12. UI·조작·튜토리얼

DEC-019의 P0 UI는 HUD·선택·소환·결과와 짧은 조작 안내까지다. 소환·선택·합성·이동·판매를 안내하고 강화·도전·제작 등 미구현 기능 버튼과 희귀 고유 스킬 설명은 숨긴다. 희귀→영웅 합성은 기존 P0 비활성 규칙을 따른다. 아래 전체 화면 구성·강화/도전/제작 버튼·정식 로비 및 12.5절의 3웨이브 튜토리얼은 P1 범위다. P0의 테스트 진입·결과 복귀는 터치로 가능해야 한다.

| 화면 | 주요 정보·행동 | 진입/종료 |
|---|---|---|
| 로비 | 플레이, 친구 방, 도감, 설정, 계정 레벨 | 실행 시 / 모드 선택 |
| 대기실 | 두 참가자, 연결 상태, 준비, 나가기 | 방 입장 / 전투 로딩 |

| 유닛 상세 | 개체·스택, 현재 DPS 참고, 스킬, 합성·판매·이동·잠금 | 칸 선택 / 닫기 |
| 제작 패널 | 신화 4종, 재료 충족, 추적, 제작 결과 | 제작 버튼 / 닫기 |

### 12.2 세로 HUD 배치

DEC-014에 따라 **세로 고정, 다양한 세로 화면비 대응, SafeArea 적용, 터치 우선**을 확정한다. 1080×1920(9:16)은 UI 설계 기준이며 실제 렌더링 해상도를 고정하거나 지원 화면비를 9:16으로 제한하는 값이 아니다. 실제 뷰포트 크기·DPI 스케일·안전 영역을 기준으로 레이아웃을 계산한다.

핵심 정보와 조작 UI는 UMG Safe Zone 안에 배치하고 노치·시스템 표시 영역을 피한다. 장식 배경은 안전 영역 밖으로 확장할 수 있다. 하단 버튼을 안전 영역 안의 하단에 배치하며, 위젯 표시 영역과 실제 터치 판정 영역을 함께 확인한다. Safe Zone과 DPI 적용 방법은 [Epic Safe Zones](https://dev.epicgames.com/documentation/unreal-engine/umg-safe-zones-in-unreal-engine?lang=en-US), [DPI Scaling](https://dev.epicgames.com/documentation/en-us/unreal-engine/dpi-scaling-in-unreal-engine)을 따른다.

| 영역 | 높이 가이드 | 내용 |
|---|---:|---|
| 상단 | 12% | 웨이브/남은 시간/적 수, 보스 생성 시 HP 두 줄 |
| 전장 | 62% | 공용 경로와 두 보드 전체, 상대 재화 간단 표시 |
| 선택·상태 | 10% | 선택 정보 1줄 또는 팀 역할 아이콘 |
| 하단 행동 | 16% | 소환 대형 버튼, 강화, 도전, 제작 |

위 비율은 안전 영역 안의 사용 가능한 높이에 대한 기본 배치 가이드다. 화면비가 달라지면 영역 크기와 간격을 조정하며, 버튼과 글자를 일괄 축소해 공간 부족을 해결하지 않는다. 기본 HUD에서는 공용 경로 네 모서리, 두 보드, 핵심 정보와 행동 버튼이 보여야 한다. 남는 공간은 여백·영역 간격으로 활용하고, 부족한 공간은 장식·여백을 먼저 줄인 뒤 전장 영역에 맞춰 카메라를 조정한다.

패널을 열어도 상단 적 수와 보스 제한 시간을 남긴다. 세부 패널은 최대 안전 영역 높이의 40%이며 펼칠 때 전장 일부를 가릴 수 있지만 과밀/보스 경고와 패널의 핵심 조작·닫기는 안전 영역 안에 유지한다. 기본 HUD의 전체 전장 가시성과 패널을 연 상태의 의도된 가림을 구분한다. 전설 획득 팝업은 입력을 막지 않는다.

### 12.3 입력

DEC-014에 따라 로비부터 결과 복귀까지 모든 핵심 기능을 터치만으로 완료할 수 있어야 한다. 마우스 오버로만 보이는 정보는 탭 상세로 제공하고, PC 단축키는 화면에 있는 동작의 개발 보조 입력으로 둔다. 터치와 PC 입력은 같은 게임 명령·거절 사유를 사용한다.

| 행동 | 터치 | PC 개발 입력 |
|---|---|---|
| 선택 | 짧게 탭 | 좌클릭 |
| 이동 | 0.25초 누른 뒤 드래그 | 좌클릭 드래그 |
| 개별 이동 | 상세 패널 `1개 이동` 후 목적지 탭 | 동일 |
| 소환 | 소환 버튼 | Space |
| 합성 | 선택 패널 합성 | F |
| 패널 닫기 | 빈 공간/닫기 | Esc |
| 목표 우선순위 | 상세 토글 | 상세 토글 |
| 도움 핑 | 핑 버튼 후 항목 | 핑 버튼 |

핫키는 전투 컨텍스트에서만 작동한다. UI에서 텍스트 입력 중에는 Space/F를 명령으로 전달하지 않는다. 드래그 임계값은 12 논리 px, 임계값을 넘기면 탭을 취소한다. 핵심 버튼 최소 터치 영역은 48dp 수준을 목표로 실기기에서 검사한다.

Enhanced Input으로 전투·메뉴 컨텍스트를 나누고, 터치/마우스 선택 위치는 공통 선택 함수에 연결한다. 입력 컨텍스트와 액션 데이터 에셋의 역할은 Epic 문서를 따른다. [Enhanced Input](https://dev.epicgames.com/documentation/en-us/unreal-engine/enhanced-input-in-unreal-engine)

DPI 적용 후 표시 위치와 터치 위치가 일치하는지 확인한다. 버튼·패널에서 처리한 터치를 뒤의 전장 선택·이동으로 중복 전달하지 않는다. 화면 이탈로 드래그를 취소하는 기존 QA-MOB-01 규칙과 터치만으로 핵심 기능을 완료하는 QA-MOB-04를 함께 검증한다. 마우스로 터치를 흉내 낸 결과는 실기기 터치 검증과 별도로 기록한다.

검증은 9:16, 9:19.5, 9:20과 세로 태블릿 비율(예: 3:4)에서 수행한다. 노치·하단 시스템 영역 유무, 기본 HUD·상세 패널·제작/도전·결과 화면, 두 플레이어 카메라 관점을 확인한다. 이는 검증 조합이며 특정 기기 지원을 보장하는 목록은 아니다. 실제 뷰포트 크기·SafeArea·DPI·기기/OS와 화면 캡처, 터치 완료 결과를 남긴다. 현재 설정·위젯·카메라 적용과 실기기 검증은 NotRun이다.

### 12.4 상태별 문구

| 상황 | 문구·처리 |
|---|---|
| 골드 부족 | `골드가 N 부족합니다.` 버튼 비활성 |
| 빈 칸 없음 | `새 종류가 들어갈 빈 칸이 필요합니다.` |
| 재료 부족 | 부족한 재료만 회색, `R02 1개 필요`처럼 표시 |
| 잠금 재료(기존 자체 제안) | DEC-021: 재료 추적과 잠금의 연결 보류. 원작 확인 전 안내 문구·소비 거절 구현 미확정 |
| 요청 처리 중 | 버튼에 짧은 진행 표시. 중복 클릭은 새 요청을 만들지 않음 |
| 응답 미확인 | 같은 세대·요청 번호·내용으로 재확인, Pending/타임아웃만으로 실패·환불 표시하지 않음 |
| 요청 기록 만료 | `처리 기록을 확인할 수 없습니다. 현재 상태를 확인한 뒤 다시 선택해 주세요.` 상태 동기화 전 변경 입력 차단 |
| 요청 내용 충돌 | 해당 재전송 거절·클라이언트 오류 기록, 원래 처리 중 요청이나 결과는 유지 |
| 오래된 보드 | `배치가 바뀌었습니다. 다시 선택해 주세요.`와 최신 상태 적용 |
| 과밀 80 이상 | 주황색 카운터 |
| 과밀 100 이상 | 빨간 카운터와 3초 게이지 |
| 보스 10초 이하 | 시각 점멸 대신 테두리 강조, 짧은 경고음 1회 |
| 연결 끊김 | `재연결 중… 전투는 계속 진행됩니다.` |

상세 잠금·표적 토글은 화면 조작 형태다. DEC-020에 따라 서버에는 개체 ID와 DesiredLocked=true/false 또는 DesiredPriority=Nearest/BossFirst를 전달하며 현재 서버 값을 뒤집으라는 명령을 보내지 않는다. 보드 버전 검사를 통과한 뒤 이미 같은 값이면 NoChange로 응답한다. UI의 선택·미리보기는 서버 확정 상태와 구분한다.

상태 갱신 뒤 다시 선택하는 과정은 새 사용자 의도다. 이전 요청을 새 번호로 자동 실행하지 않는다. 응답의 생성·소비 목록으로 복제된 개체를 다시 추가·삭제하지 않으며 오래된 Revision 응답이 최신 보드·경제 표시를 되돌리지 않게 한다. 캐시 응답의 EventId도 연출을 한 번만 재생한다. 상세 기준은 [명령 계약](technical/ARCHITECTURE.md) 16.2절을 따른다.

### 12.5 튜토리얼

첫 진입에서 연습 튜토리얼 3웨이브를 제공한다. 실제 확률과 별도의 `Tutorial` 모드로 명확히 구분하고 유닛 지급 순서를 고정한다. 온라인 전투에서 첫 결과를 몰래 강제하지 않는다.

| 순서 | 학습 | 성공 조건 |
|---|---|---|
| 1 | 소환 | C01 3개를 지급하는 튜토리얼 버튼 3회 |
| 2 | 합성 | 3개가 R01 1개로 바뀜 |
| 3 | 배치 | 표시한 칸으로 R01 이동 |
| 4 | 강화 | 제공 골드로 공격 훈련 구매 |
| 5 | 협동 | 봇의 둔화와 함께 적 처치, 공용 카운터 설명 |
| 6 | 다음 목표 | 신화 제작 패널을 열어 재료 구조 확인 |

3웨이브 종료 뒤 도감 발견만 기록하고 일반 매치 보상을 주지 않는다. 튜토리얼은 중단·다시 보기·건너뛰기를 허용한다. 가이드 완료 상태는 프로필에 저장한다.

## 13. 성장·저장·보상

### 13.1 MVP 영구 성장

영구 공격력 강화는 없다. 모든 수호자는 첫 일반 매치부터 소환·합성·제작 가능하다. 도감은 발견 여부만 가리고 잠긴 유닛 때문에 확률 풀이나 레시피가 달라지지 않는다.

계정 레벨은 1~20, 다음 레벨에 필요한 경험치는 `100+50*(현재레벨-1)`이다. 최대 레벨에서는 경험치를 더 쌓지 않는다. 장식 해금은 레벨 2/5/10/15/20에 각각 받침대 색·프로필 프레임·공방 깃발 등 5개를 제공한다. P1에서는 텍스트 해금만 먼저 구현해도 된다.

### 13.2 결과 보상

완료 웨이브 수 W는 제한 시간 종료까지 생존한 웨이브 또는 조기 최종 승리 시 30이다. 일반 매치 경험치=`10*W + (승리면100, 아니면0)`. 보스 시간 초과로 10웨이브에서 실패하면 W=9다. 연습은 경험치 0, 도감 발견만 기록한다.

온라인 중단 Aborted는 결과 보상을 확정하지 않고 재시도 안내를 한다. 정식 서비스에서 별도 보상 정책을 도입하면 운영 규칙으로 관리한다. 클라이언트 로컬 저장을 온라인 보상의 신뢰 근거로 사용하지 않는다.

### 13.3 저장 구조

로컬 프로필은 SaveVersion, ProfileId, Experience, Level, TutorialStep, DiscoveredUnitIds, CosmeticIds, EquippedCosmeticIds, Settings를 갖는다. 진행 중 온라인 매치는 로컬에 저장해 복원하지 않는다. P2 재접속은 살아 있는 서버 상태를 복원한다.

결과 지급 키는 MatchId+AccountId다. P1 로컬에서도 처리 완료 키를 저장해 결과 화면 재진입으로 경험치를 중복 수령하지 않게 한다. P2는 서버의 결과 커밋 및 계정 서비스의 원자적 중복 검사로 대체한다.

## 14. 3D 아트·애니메이션·사운드

### 14.1 아트 방향

키워드는 목재 공방, 금속 태엽, 도자기 피규어, 따뜻한 바탕과 선명한 스킬색이다. 캐릭터는 2.5~3등신, 큰 머리·무기·어깨로 역할을 구분한다. 탑다운에서 얼굴 디테일보다 실루엣·무기 궤적·받침대 등급 표시가 읽혀야 한다.

등급은 일반 회색, 희귀 청록, 영웅 보라, 전설 금색, 신화 분홍빛 흰색을 기본으로 한다. 색만으로 구분하지 않고 받침대 문양과 로마 숫자 대신 1~5개의 작은 돌기를 함께 쓴다. 등급이 높아져도 모델이 타일 밖 2칸을 가리지 않게 한다.

DEC-013의 Mobile Forward·사전 계산 조명 중심 방향을 따른다. 고정 배경의 조명은 베이크하고 이동 유닛의 밝기와 바닥 그림자는 모바일 화면에서 따로 확인한다. 기본 공격마다 광원을 추가하지 않는 기존 기술 제작 기준을 따르며, 머티리얼·VFX는 모바일 렌더링에서 경고와 실루엣이 읽히도록 제작한다. 설정 적용과 조명 빌드는 아직 수행하지 않았다. [렌더링 기준](technical/ARCHITECTURE.md)

### 14.3 애니메이션과 연출

| 상태 | 길이 가이드 | 처리 |
|---|---:|---|

### 14.4 VFX·사운드

VFX 우선순위는 보스·과밀 경고 > 내 신화 스킬 > 협동 상태 > 기본 타격이다. 동시 저우선 VFX는 40개를 목표 상한으로 두고 초과하면 오래된 저우선 효과부터 생성을 생략한다. 논리 피해는 생략하지 않는다. 불투명/마스크 표현을 우선하며, 넓은 반투명 겹침을 줄인다.

필수 사운드는 UI 확인/실패, 소환 등급 5종, 합성, 제작, 판매, 강화, 도전 실패, 기본 공격 4계열, 적 사망 3변주, 보스 등장·경고·사망, 승리/패배, 로비·전투 BGM이다. 같은 기본 공격 사운드는 0.08초 내 반복을 합치고 동시 발음 상한을 둔다. 신화 연출마다 장시간 음성을 추가하지 않는다.

### 14.5 아트 납품 목록

MVP는 수호자 20 외형, 적 4 외형, 보스 3 외형, 맵 1세트, 타일·받침대, UI 아이콘 20개+공용 행동 8개, 소환 등급 VFX 5개, 스킬 계열 VFX 약 10개가 필요하다. 구매·외주 에셋을 사용할 경우 파일별 출처·사용 범위·수정 여부를 에셋 목록에 기록한다.

### 15.1 프로젝트 설정 방향

DEC-008에 따라 현재 `Mobile_defense_clone.uproject`와 C++ 모듈 `Mobile_defense_clone`을 유지하고 디펜스 전용 구조를 추가한다. 기존 TopDown·Strategy·TwinStick 템플릿은 초기 참고용으로 보존하고 사용 여부와 참조를 확인하며 정리한다. TASK-CORE-01은 현재 프로젝트의 기반 확인과 빌드 경로 검증으로 시작한다.

## 16. 서버 권한·복제·명령 처리

### 16.1 서버가 결정하는 것

RNG·소환 결과·재화·합성 소비·스킬 발동·HP·사망·웨이브·승패·보상은 서버가 결정한다. 클라이언트는 선택 강조·드래그 미리보기·카메라·소리·VFX를 처리한다. 확정 전 결과 모델이나 재화를 예측 확정하지 않는다. UE의 서버 권한 구조와 초기부터 멀티플레이를 고려하는 권고를 따른다. [Networking Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine)

### 16.2 명령 계약

DEC-021: 서버 권한·중복 소비 방지·재시도 계약은 프로젝트 기술 기준으로 유지한다. 아래 Single/Lock/Target/Swap은 기존 초안의 예약 계약이며 원작 기능의 존재를 입증하지 않는다. [원작 대조](product/ORIGINAL_REFERENCE.md) 전에는 이 필드를 근거로 자체 버튼·기능을 추가하지 않는다. 원작에서 확인한 입력·결과에 맞춰 필요한 명령과 검수 기준을 함께 갱신한다.

DEC-020에 따라 공통 요청 정보와 명령별 payload를 분리한다. 아래는 구현할 논리 계약이며 실제 RPC/직렬화 코드를 생성한 것은 아니다. 명령 타입과 일치하는 payload 하나만 허용하고 필수값 누락·다른 타입의 필드·알 수 없는 enum은 거절한다.

```text
FLDCommand
  ConnectionEpoch: uint64        // 서버가 부여한 현재 연결 세대
  RequestId: uint32              // 세대 내 1부터 증가, 재시도에는 같은 번호
  CommandType: enum              // Summon, Merge, Craft, Sell, Swap, Upgrade, Move, Lock, Target
  ExpectedBoardRevision: int32   // Upgrade는 -1, 나머지는 현재 자기 보드 버전
  Payload: CommandType별 구조    // 아래 표의 필수 항목만

FLDCommandResult
  ConnectionEpoch: uint64        // 응답 대상 요청의 세대, 새 세대 발급과 구분
  RequestId: uint32
  ResultCode: enum
  NewBoardRevision: int32        // 이 응답을 확정한 시점의 자기 보드 버전
  EconomyRevision: int32         // 이 응답을 확정한 시점의 개인 경제 버전
  CreatedInstanceIds: uint64[]
  RemovedInstanceIds: uint64[]
  EventId: uint64                // 재전달 시 동일, 연출 없으면 0
```

#### 명령별 필수 정보

| 명령 | Payload | 서버가 확인·결정할 내용 |
|---|---|---|
| Summon | Source: enum Gold/Star | 모드에서 허용된 재화 종류인지 검사. 가격·확률 프로파일·보장·결과·배치 칸은 서버 결정. P0는 Gold만 허용 |
| Merge | SelectedInstanceId: uint64, ConsumedInstanceIds: uint64[3] | 선택 ID가 소비 목록에 포함되고 3개가 서로 다른 동일 소유·동일 UnitId인지 검사. 선택 개체의 서버상 칸을 결과 배치 기준으로 사용 |
| Craft | RecipeId: FName, ConsumedInstanceIds: uint64[3] | 정확한 서로 다른 재료 3개·레시피 일치 검사. 결과와 전설 재료의 배치 칸은 서버 결정. P1 |
| Sell | InstanceId: uint64 | 지정한 1개체만 판매, 환급액은 서버 데이터로 계산 |
| Swap | InstanceId: uint64, TargetUnitId: FName | 영웅/전설 재료 1개를 같은 등급의 다른 종류로 교환. 비용·횟수 서버 검사. 스택 위치 맞교환을 뜻하지 않음. P1 |
| Upgrade | UpgradeId: FName | 허용된 강화 항목·현재 레벨·비용·상한 검사 후 한 단계 구매. 목표 레벨·가격을 클라이언트가 지정하지 않음. P1 |
| Move | MoveMode: enum Stack/Single, SourceInstanceId: uint64, DestinationCellId: int32 | SourceInstanceId의 현재 칸을 서버에서 조회. Stack은 해당 칸 전체, Single은 해당 개체만 이동. 자기 목적지와 영향받는 모든 개체·수용량 검사 |
| Lock | InstanceId: uint64, DesiredLocked: bool | 해당 1개체의 원하는 잠금 상태 설정. 잠긴 개체에도 소유자의 해제 요청 허용 |
| Target | InstanceId: uint64, DesiredPriority: enum Nearest/BossFirst | 해당 1개체의 원하는 표적 우선순위 설정. 실제 적 ID·피해는 클라이언트가 결정하지 않음 |

InstanceId는 0이 아닌 서버 발급 논리 ID다. 합성·제작 목록은 정확히 3개이며 중복을 제거해 받아들이지 않는다. 목록 순서는 의미가 없고 서버는 RequestId 내용 비교 시 오름차순으로 정규화한다. 합성의 기준은 목록 첫 원소가 아니라 SelectedInstanceId다. 소비 대상이 바뀌면 다른 개체로 자동 대체하지 않고 거절·재선택한다. 데이터 ID는 UTF-8 기준 최대 64바이트, 공통 필드와 payload의 직렬화 크기는 전송 헤더를 제외하고 최대 1,024바이트를 초기 상한으로 사용한다. 디코딩 시 길이를 먼저 제한하고 FName은 해당 명령의 서버 허용 데이터 목록에서만 해석한다. 새 유닛 목록은 명령당 최대 1개, 소비 목록은 최대 3개다.

클라이언트는 플레이어 소유 PlayerController의 Server RPC로 보낸다. 소유권이 없는 BoardManager에 직접 서버 RPC를 호출하지 않는다. 발신자·플레이어 인덱스·현재 MatchId는 서버의 연결·참가자 문맥에서 얻는다. ConnectionEpoch는 그 문맥과 일치하는지 검사하는 값이며 클라이언트가 새 세대를 발급하지 않는다. 가격·RNG·결과 유닛·소유권을 payload로 지정할 수 없다.

Move의 Stack/Single 구분은 전송 계약이다. 4번 보드 규칙 검토는 임의 예외 선택 대신 원작 동작 대조로 진행한다. 미확인 재료 교환의 결과 배치를 먼저 설계하지 않는다. P0/P1 범위는 DEC-019를 따르되 DEC-021의 원작 대조 조건을 함께 적용하며, 계약에 존재해도 해당 모드에서 제외되거나 원작 근거가 없는 기능은 실행 대상으로 확정하지 않는다.

#### 처리 순서·버전

| 검증 순서 | 검사 |
|---|---|
| 1 | 연결·참가자·ConnectionEpoch 일치, payload 크기·타입·필수값·목록 길이 검사 |
| 2 | 요청 키와 정규화한 내용 비교. 캐시/처리 중 요청은 재실행 없이 응답, 오래된 번호는 거절 |
| 3 | 새 요청을 참가자별 직렬 처리에 등록. 명령 수 제한과 Preparing/Running·모드별 기능 허용 검사 |
| 4 | Upgrade 외에는 ExpectedBoardRevision 일치 검사. 각 DataId·CellId의 허용 범위 검사 |
| 5 | 정확한 개체의 존재·소유·명령별 잠금/예약 상태, 목적지 수용 가능 여부 검사 |
| 6 | 골드·별조각·강화 레벨·구매/교환 한도 검사 |
| 7 | 가상 적용으로 변경 후 보드 유효성 확인. 거절 시 게임 상태·RNG 변화 없음 |
| 8 | 자원·개체·RNG·변경된 Revision과 확정 응답을 함께 반영한 뒤 결과 전송 |

보드의 배치·구성·Locked·TargetPriority가 바뀐 트랜잭션은 자기 BoardRevision을 한 번 증가시킨다. 경제 상태가 바뀌면 EconomyRevision도 한 번 증가시킨다. 변경이 없는 거절·중복 응답·이미 같은 값인 Lock/Target은 버전을 증가시키거나 새 EventId를 만들지 않는다. 잠금·우선순위 요청도 버전 검사를 먼저 통과해야 한다. Upgrade는 보드 버전 비교를 하지 않고 서버의 현재 경제 상태로 구매 가능 여부를 검사한다. 자동 처치 보상으로 경제 버전이 바뀌는 것만으로 보드 명령을 거절하지 않는다.

#### 중복·응답 유실

개인별 동시 변경 요청은 클라이언트에서 1개로 제한하고 서버도 참가자별 명령 적용을 직렬화한다. 서버는 초당 8명령·순간 버스트 12명령의 기존 제한을 유지하며 재확인 트래픽에도 전송 제한을 적용한다. 핑은 별도 제한이다. 재전송은 같은 연결 세대·번호·내용을 보존하고 중복 클릭으로 새 요청을 생성하지 않는다.

요청 키는 서버 문맥의 `(MatchId, 참가자, ConnectionEpoch, RequestId)`다. 내용 비교에는 CommandType·ExpectedBoardRevision·명령별 모든 필수값을 포함한다. 최근 **확정 결과 256개**는 성공·거절 모두 내용과 응답을 캐시한다. 처리 중 요청은 별도로 보관하며 확정 전에 기록을 퇴출하지 않는다. 같은 키·같은 내용이 처리 중이면 Pending, 완료됐으면 원래 응답을 반환한다. 같은 키·다른 내용은 RequestIdConflict로 거절하고 원래 요청·응답을 보존한다. 결과 캐시 조회는 현재 Phase·보드 버전 검사보다 먼저이므로 성공 뒤 Result 전환이나 보드 변경이 있어도 원래 결과를 재전달한다.

캐시에서 빠진 요청의 실행을 막기 위해 세대별 HighestAdmittedRequestId를 별도로 보관한다. 유효한 형식의 새 번호를 등록할 때 최댓값을 갱신하고, 등록 후의 RateLimited·게임 규칙 거절도 확정 결과로 남긴다. 캐시·처리 중 목록에 없고 최댓값 이하인 번호는 RequestExpired로 거절한다. 이 거절은 과거 실행 여부가 미확인이라는 뜻이며 다시 실행하지 않는다. 새 번호는 최댓값보다 커야 한다. uint32를 순환 재사용하지 않고 소진 전 처리 중 요청을 정리한 뒤 서버가 새 세대를 발급한다.

응답이 불명확할 때 클라이언트는 같은 요청만 재확인한다. RequestExpired이면 응답 시점의 보드·경제 Revision 이상인 복제 상태를 각각 받은 후 사용자가 다시 선택하도록 안내한다. ConnectionEpoch가 바뀐 경우에도 이전 요청을 새 번호로 자동 재실행하지 않는다. 새 연결의 초기 상태 동기화가 끝나기 전에는 새 변경 입력을 막는다. 별도 결과 조회 명령은 추가하지 않고 기존 상태 복제를 사용한다. Pending이나 타임아웃을 실패·환불로 단정하지 않는다. 서버 재시작 등으로 캐시·번호 상한을 잃으면 동일 세대를 계속 사용하지 않는다. 이 계약은 프로세스 장애를 넘는 영속 명령 복구를 제공하지 않는다.

캐시 응답의 Revision·생성/소비 목록은 과거 결과 식별용이다. UI는 더 오래된 응답으로 최신 복제 상태를 덮어쓰거나 유닛을 다시 생성/제거하지 않는다. EventId는 매치 내에서 중복 재생을 막는다. 새 거절에는 생성/소비 목록을 비우고 EventId=0을 사용한다.

#### 결과 코드와 UI 대응

| 코드 | 의미·대응 |
|---|---|
| Success / NoChange | 정상 확정 / 원하는 Lock·Target 값과 이미 동일. 복제 상태를 반영하고 요청 종료 |
| Pending | 동일 요청 처리 중. 새 명령을 만들지 않고 대기 |
| RequestIdConflict | 같은 번호에 다른 내용. 실행·원래 캐시 변경 없이 거절, 클라이언트 요청 생성 오류 기록 |
| RequestExpired / InvalidEpoch | 기록이 없는 오래된 번호 / 연결 세대 불일치. 최신 상태 반영 후 재선택 |
| InvalidPayload / InvalidData / InvalidCell | 구조·필수값·enum 또는 데이터/칸 범위 오류. 요청 구성 오류 기록 |
| PhaseNotAllowed / FeatureDisabled | 현재 매치 단계 또는 P0/P1 모드에서 불허 |
| StaleBoard | 보드 버전 불일치. 최신 보드 반영 후 다시 선택 |
| MissingInstance / NotOwner / Locked / Busy | 개체 없음·소유권·소비 잠금·예약/이동 제한에 따른 거절 |
| NoSpace / InsufficientResource / LimitReached | 배치 공간·재화·구매/교환 상한 사유 표시 |
| RateLimited | 등록된 요청은 실행하지 않음. 대기 후 사용자 새 입력만 새 번호로 처리 |

별조각 도전의 추첨 실패는 명령 거절이 아니다. 비용·카운터를 정상 반영한 Success이며 생성 목록이 비어 있을 수 있다. 결과 연출로 실패를 표시하더라도 비용을 환불하거나 같은 요청을 새 추첨으로 처리하지 않는다.

### 16.3 복제 데이터

| 대상 | 빈도 목표 | 데이터 |
|---|---|---|
| 매치 상태 | 변경 시, 시간은 종료 시각만 | Phase, WaveIndex, WaveEndTime, 결과 |
| 공용 적 수·보스 HP | 5~10Hz 또는 의미 있는 변화 | 카운트, 두 보스 체력 |
| 보드 | 변경 시 | 슬롯의 InstanceIds, UnitId, 개체별 Locked·TargetPriority, BoardRevision |
| 개인 자원 | 변경 시 소유자 | Gold, Stars, 업그레이드, 보장 카운터, EconomyRevision |
| 아군 자원 요약 | 2Hz | Gold, Stars, 역할 태그 |
| 적 이동 | 초기 10Hz 기준 | 경로 거리, 속도, 서버 시각, 이동 상태 |
| 공격 연출 | 묶음 또는 낮은 빈도의 비신뢰 이벤트 | EventId, 공격자, 표적, VFX 종류 |

신뢰 RPC는 구매처럼 낮은 빈도의 명령과 응답에 사용한다. 모든 일반 공격을 Reliable Multicast로 보내지 않는다. 영속 상태가 진실이며 연출 패킷이 누락돼도 HP·유닛·승패는 맞아야 한다. 복제 도착 순서를 가정하지 않고 Revision을 비교하며, 연출 대상 액터가 아직 없으면 짧게 보류하거나 생략한다.

### 16.4 적 이동 동기화

서버가 이동 상태를 20Hz로 계산하고 클라이언트는 받은 경로 거리·시각·속도로 보간 표시한다. 일시 둔화·스턴·속도 변경은 새 기준점을 복제한다. 일반 위치 ReplicateMovement와 자체 경로 보간을 동시에 사용하여 두 체계가 위치를 덮어쓰지 않게 한다.

경로를 여러 바퀴 돌 수 있으므로 누적 이동 거리를 별도로 갖고 표시 위치만 `distance mod 4000`으로 변환한다. 3990→10 구간을 보간할 때 경로를 반대로 가로지르지 않도록 누적 거리 기준으로 보간한다. 논리 위치는 클라이언트 예측값을 받아 수정하지 않는다.

### 16.5 액터 풀링

첫 구현에서는 서버 권한 Spawn/Destroy로 정확성을 검증한다. 모바일 성능에서 생성 스파이크가 확인되면 적 최대 128개 및 VFX 풀을 도입한다. 풀링 시 HP, 효과, 타이머, TargetId, SpawnSerial, NetDormancy, 가시성, 충돌, GenerationId를 재초기화한다. 재사용된 액터에 이전 세대의 연출/피해 이벤트가 도착하면 버린다.

### 16.6 전용 서버 전환

리슨 서버는 제작 검증에 쓰고, 온라인 프로필 보상과 안정적 재접속이 필요한 P2에서 전용 서버로 전환한다. Epic의 전용 서버 튜토리얼은 엔진 소스 빌드와 C++ 멀티플레이 프로젝트를 요구하므로 이 준비를 P2 일정에 포함한다. [Dedicated Server 설정](https://dev.epicgames.com/documentation/en-us/unreal-engine/setting-up-dedicated-servers-in-unreal-engine)

전용 서버는 배틀 상태만 유지한다. 계정 서비스·방 관리·서버 프로세스 배정·결과 저장은 별도 책임이다. 서비스 선택과 실제 운영 비용은 CCU 목표와 배포 지역이 정해진 뒤 산정한다. 이 문서에는 확인하지 않은 고정 서버 요금을 넣지 않는다.

## 17. 데이터·디버그·운영

### 17.1 데이터 원본

`data/DT_Units.json`, `DT_Skills.json`, `DT_Recipes.json`, `DT_EnemyTypes.json`, `DT_Waves.json`, `DT_SpawnProfiles.json`, `DT_SummonProfiles.json`, `DT_Upgrades.json`을 동봉한다. 행 이름은 Name이며, 문자열 ID는 FName으로 읽는다. 타입과 단위는 DATA_SCHEMA 문서가 정의한다.

DataTable을 가져오기 전에 대응 Row Struct가 필요하고 필드 이름을 맞춰야 한다. 기본 데이터 가져오기 방식은 Epic의 Data Driven Gameplay 문서를 참고한다. 시각 에셋은 별도 DataAsset에 연결하여 밸런스 표가 무거운 에셋을 직접 로딩하지 않게 한다. [Data Driven Gameplay](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-driven-gameplay-elements-in-unreal-engine)

### 17.2 재현성·버전

각 매치는 MatchId, BuildVersion, RulesVersion, DataHash, 서버 전용 MatchSeed를 기록한다. 플레이어별로 골드 소환·합성·별조각 도전 RNG 스트림을 분리해 상대의 입력 순서나 VFX·스폰 순서가 개인 추첨 결과를 바꾸지 않게 한다. 실서비스 추첨 결과는 서버에서 로그를 남기고 시드를 클라이언트에 배포하지 않는다.

동일 seed만으로 전체 3D 전투가 비트 단위로 재현된다고 약속하지 않는다. 재현 테스트에는 입력 명령 순서·서버 스텝·버전·스냅샷을 함께 사용한다. 테스트 시드는 Development 빌드에서만 직접 입력할 수 있다.

### 17.3 필수 디버그 화면

현재 웨이브, 적 수, 서버 스텝 시간, 골드·별조각, 소환 횟수, 두 보장 카운터, 유닛 수, 보드 버전, 선택 대상, 적 상태이상, 추첨 로그를 한 화면에서 확인한다. QA 명령은 특정 웨이브 진입, 자원 지급, 유닛 지급, 적 99/100/101개, 보스 HP 1, 패킷 지연 시나리오를 포함한다. Shipping에서 명령 진입점을 제거한다.

### 17.4 분석 이벤트

| 이벤트 | 필수 필드 |
|---|---|
| MatchStart | MatchId, BuildVersion, Mode, DeviceProfile, BotPresent |
| SummonResolved | PlayerIndex, Source, OutcomeTier, UnitId, PityBefore/After, Cost |
| MergeResolved | 입력 UnitId/3개, OutputId, Wave, Time |
| CraftResolved | RecipeId, Wave, Time |
| UpgradePurchased | UpgradeId, NewLevel, Wave |
| WaveEnded | Wave, AliveCount, TeamDamageByType, PlayerGold |
| MatchEnded | Result, Reason, CompletedWaves, Duration, 보스 잔여HP, BotSeconds |
| PerformanceSample | GameThreadMs, RenderThreadMs, GPUms, Memory, DeviceProfile |

로그는 디버깅에 필요한 최소 계정 식별자를 사용하고, 채팅 내용이나 장치의 불필요한 개인정보를 수집하지 않는다. 분석 이벤트가 실패해도 전투를 막지 않는다. 보상 기록은 일반 분석 로그와 별도의 신뢰 가능한 저장 경로로 처리한다.

### 17.5 초기 플레이 테스트 지표

튜토리얼을 완료한 신규 플레이어의 첫 일반 모드 승률 목표는 40~60%, 숙련된 고정 듀오는 70~90%로 가정한다. 아직 측정된 수치가 아니다. 신규 20팀 이상·숙련 10팀 이상의 반복 세션을 우선 모으고 표본이 작다는 점을 기록한다.

첫 합성 시간, 10웨이브 보스 실패율, 전설·신화 최초 시각, 재료 교환 사용률, 가득 찬 보드 체류 시간, 두 플레이어 피해 비중, 이탈 원인을 함께 본다. 높은 피해량만으로 지원 유닛의 기여를 평가하지 않는다. 평균 외에 최악·최선 시드와 하위 10% 결과를 따로 확인한다.

## 18. 성능 예산·검증

### 18.1 모바일 렌더링 기준

DEC-013에 따라 **Mobile Forward와 사전 계산한 조명 중심의 단순 라이팅**을 모바일 렌더링 기준으로 확정한다. 작은 고정 전장의 배경 조명을 베이크하고 실시간 광원·그림자 비용을 제한하는 제작 방향이다. 기존 Lumen·Nanite·Virtual Shadow Maps 비활성 제작안을 유지하며, 모바일 머티리얼과 일반 메시·LOD로 표현한다.

Directional Light 1개와 단순 환경광을 중심으로 구성한다. 정적 배경의 조명은 베이크하고 움직이는 수호자·적의 밝기와 바닥 그림자는 별도로 확인한다. 캐릭터 바닥 그림자 또는 제한된 동적 그림자를 사용하며, 기본 공격마다 Point Light를 생성하지 않는 기존 제작 기준을 유지한다. 베이크 조명만으로 움직이는 액터의 조명·그림자가 완성됐다고 판단하지 않는다.

Epic은 사전 계산 조명을 사용하는 프로젝트에 Mobile Forward를 권장하며, 복잡한 동적 조명에는 Mobile Deferred가 유리할 수 있다고 설명한다. 이번 선택은 현재 전장·조명 설계에 따른 판단이며 모든 기기에서 Forward가 더 빠르다는 의미는 아니다. 동적 광원 중심으로 아트 방향이 바뀌거나 기기 실측에서 병목이 확인되면 같은 장면·기기 조건으로 비교하고 결정을 갱신한다. [Epic 모바일 렌더링 비교](https://dev.epicgames.com/documentation/en-us/unreal-engine/mobile-rendering-and-shading-modes-for-unreal-engine)

현재 프로젝트는 `r.Mobile.ShadingPath=1`, `r.AllowStaticLighting=False`이므로 결정된 방향을 적용하기 위한 설정·맵 작업이 남아 있다. 적용할 키·현재값·후속 검증은 [개발 환경 안내](technical/DEVELOPMENT_SETUP.md)에 기록한다. `r.ForwardShading`은 데스크톱 렌더러 설정이므로 Mobile Forward 선택과 구분한다. 이 결정 반영에서 Config·맵·머티리얼을 변경하거나 조명을 베이크하지 않았다. DEC-018로 초기 OpenGL ES 3.2·Mobile HDR On·MSAA 2x를 확정했으며 실제 적용·표시·기기 성능 검증은 남아 있다.

### 18.2 초기 예산

| 항목 | 목표·상한 |
|---|---|
| 일반 모바일 | 30FPS, 장시간 p95 프레임 33.3ms 이내 목표 |
| 상위 모바일 | 선택 60FPS, p95 16.7ms 이내 목표 |
| 서버 논리 | 20Hz, 스텝 50ms; 전투 처리 p95 10ms 이내 목표 |
| 테스트 액터 | 수호자 72 + 적 128 + 핵심 VFX 동시 부하 |
| GPU/스레드 | 30FPS 목표에서 각 병목 경로 p95 약 25ms 이하, 여유 포함 |
| 메모리 | 모바일 총 프로세스 1.2GB 이내를 첫 측정 목표로 설정 |
| Draw Call | 모바일 전투 화면 약 200 이하부터 시작, 실측 후 프로파일별 조정 |
| 네트워크 | 클라이언트당 평균 다운로드 40KB/s 이하를 초기 목표로 측정 |
| 로딩 | 전장 첫 로딩 10초 이하 목표, 캐시된 재진입 5초 이하 |

이 값들은 보증치가 아니다. 최소 지원 기기는 첫 실기기 빌드 결과를 바탕으로 확정한다. 기준 기기 제안은 Galaxy A54급 Android 6GB, 상위 비교 기기는 Galaxy S23급, iOS 후속은 iPhone 12급으로 둔다. 구매 권고나 성능 보장 의미는 없다.

### 18.3 측정 방법

에디터 FPS가 아닌 패키징한 Development 빌드에서 Unreal Insights, stat unit, stat gpu, 메모리·네트워크 프로파일을 기록한다. GPU와 게임 스레드 시간을 단순 합산해 프레임 시간으로 오해하지 않고 병목 경로를 판단한다.

최악 부하 장면에서 20분 연속 실행하고 평균·p95·최대 프레임, 메모리 증감, 열로 인한 성능 저하를 기록한다. 낮은 VFX 모드에서도 경고·상태·피해 판정이 동일해야 한다. 풀링·LOD·VFX 절감은 한 번에 한 항목씩 적용해 효과를 측정한다.

### 18.4 핵심 기능 검수

확률 합계·레시피 ID·데이터 타입 같은 정적 검증과 실제 UE 플레이 검증을 구분한다. 동봉 스크립트는 정적 데이터 및 경제 계산만 검사한다. 전투 밸런스, 모델 애니메이션, 서버 동기화, 모바일 성능 검증은 프로젝트 구현 후 수행해야 한다.

실행해야 할 상세 사례는 BACKLOG_QA에 제공한다. 특히 동일 개체 동시 합성, 가득 찬 보드 소환, 보장 직전 실패, 99↔100 적 수 경계, 보스 마감 시각 타격, 경로 한 바퀴 보간, 재접속 보상 중복을 필수로 둔다.

## 19. 개발 일정·출시 판정

착수 범위와 작업별 선행 조건은 [개발 전 문서 검토 종합](production/DEVELOPMENT_READINESS.md)을 따른다. 현재 다음 행동은 [진행 상황](production/PROJECT_STATUS.md)의 A4를 따르며, 원작 미확인 게임 규칙은 해당 구현 전에 대조한다. 아래 전체 콘텐츠·경제·밸런스 사례도 DEC-021/DEC-022보다 우선하지 않는다. P1 도구 확장 4개는 별도 공수 미산정으로, 기존 8주 추정에 포함된 것으로 보지 않는다.

### 19.1 팀·일정 가정

기본 일정은 UE 프로그래머 1명 + 3D/테크아트 1명 + 기획/QA 파트타임, 일부 공용·구매 에셋 사용을 가정한다. 작업량은 추정이며 플랫폼 경험·에셋 준비도에 따라 달라진다. 1인 개발로 20개 외형을 모두 새로 만들면 동일 달력 일정으로 끝난다고 보지 않는다.

| 기간 | 마일스톤 | 완료 증거 |
|---|---|---|
| 1~2주 | P0, 8종·10웨이브 기본 공격 협동·짧은 조작 안내 | PC 2인 상태 일치·중복 소비 방지·승패 경계 검사 및 Android 실기기 터치 완주 |
| 3~4주 | 30웨이브 전투 룰과 데이터 | 희귀 4종 고유 스킬을 포함한 전체 스킬, 모든 등급·도전·신화 제작·공격 훈련·장치 가속, 데이터 검수 |
| 5~6주 | 3D 아트·HUD·튜토리얼 통합 | 20종 판독성, 전체 화면 흐름, 저장 |
| 7~8주 | P1 MVP 품질·밸런스 | Android 1종 실기기, 지연 테스트, 30웨이브 반복 |
| 별도 4~8주 | P2 온라인 출시 준비 | 서버·계정·방 코드·재접속·기기 확장·운영 검수 |

네트워크 또는 모바일 경험이 부족하거나 에셋을 전부 직접 제작하면 위 일정에 30~50% 예비를 우선 잡는다. 1인 개발은 P1 약 12~20주를 출발 추정으로 재산정한다. 첫 2주 실제 처리량으로 남은 일정을 업데이트한다.

### 19.2 프로토타입 합격선

친구 두 명이 게임 안의 짧은 조작 안내만으로 소환과 합성을 찾고, 첫 보스에 실패해도 `합성을 너무 일찍 했다`, `마법/물리가 부족했다`처럼 다음 행동을 설명할 수 있어야 한다. 10웨이브 반복 테스트에서 소환 결과와 배치 선택이 의미 있게 바뀌어야 한다. 피규어가 예쁜지와 별개로 이 조건이 맞지 않으면 콘텐츠를 늘리기 전에 루프를 수정한다.

DEC-019의 P0 합격에는 PC 패키징 2인 검증과 Android 실기기에서 10웨이브 전투의 터치 완주가 모두 필요하다. 기본 맵 실행만으로 전투 완주를 대신하지 않는다. PC 두 프로세스 또는 두 장치의 실제 접속 구성을 기록하고, 서버·클라이언트 상태 일치, 중복 소비 방지, 승리·과밀·보스 시간초과·최종 잔여 적 경계를 확인한다. 기존 5판 반복 계획은 시드·승패·관찰 기록이며 모든 판의 승리를 요구하지 않는다. 완주와 경계 검사는 별도 실행으로 증거를 남길 수 있다.

첫 Android 기기는 OPEN-008로 미정이다. 실기기 검증 전에는 P0 최종 통과를 보류하며 일정 경과만으로 완료 처리하지 않는다. 1~2주 및 첫 10일 계획은 작업 순서·추정이고, 실제 가용 인력·도구 준비·기기 확보에 따라 갱신한다. 개별 PC 작업의 검증 완료와 P0 전체 통과를 구분한다. 강화·희귀 고유 스킬·정식 튜토리얼은 P1이며 P0 합격에 요구하지 않는다.

### 19.3 MVP 합격선

30웨이브 승패가 서버와 두 클라이언트에서 일치하고, 재화·합성 중복 버그가 없어야 한다. 모든 레시피는 디버그 지급으로 제작 가능하며 실제 플레이에서도 목표 시점에 완성 가능한지 확인한다. 낮은 확률 결과만으로 대부분의 판이 해결 불가능하면 수입·보장·교환 한도를 조정한다.

한 기기에서 평균 FPS만 통과해서 완료로 보지 않는다. 터치 입력, 가림, 작은 글씨, 열 부하, 패킷 지연, 백그라운드 복귀까지 검수한다. 인터넷 공개 출시에서는 별도의 P2 체크리스트가 모두 끝나야 한다.

### 19.4 범위 축소 우선순위

일정이 밀리면 도감 3D 회전·장식 해금·추가 사운드 변주·보스의 시각 연출부터 줄인다. 두 플레이어의 일관된 전투 상태, 소환·합성 원자성, 실패 원인 표시, 모바일 판독성은 유지한다. 20종 구현이 과도하면 P0 8종의 재미 검증 기간을 늘리고 새 마감일을 정한다.

## 20. 우선 의사결정과 근거

### 20.1 프로토타입 작업 기준

DEC-021을 우선 적용한다. 아래 게임 수치와 편의 규칙은 원작 대조 전의 초안이며, 원작과 같다는 근거가 아니다. 사용자 확정 개발 조건·P0 중간 범위는 유지하고 게임 동작은 [원작 대조 기록](product/ORIGINAL_REFERENCE.md)에 따라 검증한다.

UE 5.8.2를 기준 후보로 두고 PC·Android 빌드 통과 후 고정한다(DEC-009). 모바일 세로 화면, 공방 테마, 2인 공용 경로, 30웨이브 약 15분, 일반 소환 82/15/3, 동일 유닛 3개 합성, 레시피 신화 4종, 20Hz 서버 로직, 고정 카메라, P0 10웨이브부터 제작한다.

첫날에는 기존 프로젝트 기반을 확인하고 디펜스 전용 24칸·경로·임시 적·카메라를 추가한다. 다음으로 두 클라이언트가 같은 적 수를 보게 하고, 이후 골드 소환과 공격을 연결한다. 아트 완성이나 계정 서버 설계를 기다릴 필요가 없다.

### 20.4 근거 사용 범위

DEC-021에 따라 공식 소개뿐 아니라 버전·모드가 확인된 원작의 실제 조작과 결과를 재현 근거로 사용한다. 공식 소개·외부 공략·직접 관찰·자체 설계를 구분하며, 자료가 없으면 미확인으로 남긴다. 최신 모드·숨겨진 공식·정확한 확률을 추정으로 확정하지 않는다. UE 자료는 아키텍처와 데이터 가져오기 접근의 근거이며 클래스명·성능 예산·일정은 프로젝트 설계안이다. 공식 문서가 가리키는 버전과 실제 설치한 버전의 차이는 착수 시 고정 버전 문서로 확인한다.
